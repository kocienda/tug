### Phase Overview {#phase-overview}

#### Context {#context}

The dash-hardening round (`1ca5e225e`) landed the operation log (`tugrust/crates/tugdash-core/src/oplog.rs`) and conflicts-as-data (`resolve.rs`, `workshop.rs`, `tugrust/crates/tugcast/src/feeds/join_resolver.rs`). A post-join audit read jj's implementation of the same ideas and found four places where jj is ahead or where our round left a seam open:

1. **The marker predicate has false positives, and the round made it load-bearing.** `has_conflict_markers` (`resolve.rs`) flags any line starting with `<<<<<<<`, `=======`, `>>>>>>>`, or `|||||||`. But `=======` is a setext heading underline in markdown, and two repo files carry such lines today: `dash/archive/tugplan-app-test-cleanup.md` and `dash/archive/file-tracking-improvements.md`. Before the round, the ground truth for "resolved" was the index (`diff --diff-filter=U`); now it is this content scan — `Workshop::unresolved()` and `Workshop::marker_paths` (workshop.rs), `Workshop::commit`'s candidate gate and `Workshop::checkpoint`'s stray check (workshop.rs), `is_clean_merge` at the four ladder rung exits (resolve.rs), and `marker_paths_in_tree` feeding `conflict_summary` (ops.rs). If a setext-underlined file conflicts in a join, it can never read as resolved: the resolve wedges, the checkpoint refuses, the candidate gate refuses.

**And it bites a rung earlier than that.** `is_clean_merge` is what rungs 3, 4, and 5 use to *validate their own output* before accepting it (`merge_file_rung`, `driver_rung`, and the AI seam's acceptance check), and what the rerere sweep uses to claim a scratch-worktree file. So an already-conflicted markdown file that `git merge-file` merges perfectly cleanly is still rejected — its clean output contains a `=======` underline — and the path falls through every machine rung to `unresolved`. The predicate does not merely wedge the workshop; it withholds resolutions the machine already computed, and the human or AI seam is then handed a conflict that rung 3 had settled.

jj parses markers *structurally* (`parse_conflict` in jj's `lib/src/conflicts.rs`): a conflict exists only where a well-formed block does — opener through closer in order — and content that merely looks marker-ish is content.
2. **The conflict chain is not in the op log's keepalive.** `capture_before` and `tips_of` (`oplog.rs`) record base tip, dash tip, and candidate — not the conflict chain tip. A join or discard over a half-finished resolve records an op whose keepalive commit does not parent the checkpoints, and teardown deletes the conflict ref (`clear_conflict` folded into `clear_candidate`, resolve.rs). Undo restores the branches but the committed resolution work is unreachable and gc-able — the exact failure mode the op log was built to end, still open for the one ref family the round itself created.
3. **Base motion discards checkpoint work that could be salvaged.** Conflict validity is strict head equality (`conflict_is_valid`, resolve.rs), so a base advance invalidates the chain and the ladder re-runs from scratch. Rung resolutions survive via the rerere teach-back (`record_rerere`, resolve.rs), but the resolver loop's turn-by-turn work — the expensive AI-seam resolutions committed as checkpoints — is never taught to rerere and dies with the chain. jj survives this because a conflict is an algebra over stage ids that rebases; we get most of that benefit without the algebra by reusing a prior chain's resolved blob wherever the three stage oids are unchanged.
4. **No redo.** Undo ops record a full outcome but are excluded from undo candidacy (`OpPayload::is_undoable`), so an accidental `dash undo` of a good join is the one operation in the system with no reverse gear. jj pairs undo with redo and explicit undo-stack semantics (jj's `cli/src/commands/undo.rs`: undoing an undo restores what that op restored, never building a linked list to walk).

The jj comparison also confirmed what *not* to change: the keepalive-ref pattern matches jj's `refs/jj/keep/` mechanism exactly, the CAS-refuse-by-name discipline is the right substitute for jj's divergent-op-head merging at our scale, and jj adoption stays declined (its workspaces are still not git checkouts). Those decisions are settled and not reopened.

#### Strategy {#strategy}

- Fix the predicate first: it is a latent wedge with two tripwire files already in the tree, it is one function with one signature, and every call site inherits the fix without moving.
- Keepalive before salvage: salvage reads a prior (possibly invalidated) chain, and the keepalive work is what guarantees that chain is still reachable when a join or discard intervened between the invalidation and the next resolve.
- Redo is pure oplog work — a new verb, a candidacy predicate, per-verb re-application of recorded after-state — and touches nothing in the conflict machinery, so it lands independently.
- Every reversal and re-application stays a compare-and-swap with a named refusal, in the vocabulary the landed round established; nothing forces.
- All tests at the Rust layer in `tugdash-core`'s tempdir-git fixture style (test modules at the bottom of `oplog.rs`, `resolve.rs`, `workshop.rs`, `ops.rs`). Marker-parser tests run against real `git merge-file` / `git merge-tree` output, never hand-typed marker text alone. No app-tests: no UI surface changes.

#### Success Criteria (Measurable) {#success-criteria}

- A file containing a bare `=======` (or `<<<<<<<`, `>>>>>>>`, `|||||||`) line at column 0 with no enclosing conflict block reads clean: `has_conflict_markers` false, `Workshop::unresolved()` empty for it, `Workshop::checkpoint` accepts it (Rust tests, Step 1).
- A conflicted markdown file whose *content* legitimately contains setext `=======` underlines resolves end-to-end: the ladder or resolver settles it, the candidate commits, nothing wedges (Rust test, Step 1).
- Real `git merge-file` output — default style and `--diff3` — is still detected as conflicted, and its resolution detected as clean (Rust tests, Step 1).
- After a join or discard over a dash with a half-finished resolve, the chain tip is still `git cat-file -e`-reachable, and `tugutil dash undo` restores `refs/tug/conflict/<name>` to its recorded tip (Rust tests, Step 2).
- A resolve interrupted by base motion arrives at the next resolve with every checkpointed path whose three stage oids are unchanged already resolved — `ResolvedBy::Salvage` in the report — and the resolver sees only the remainder (Rust test, Step 3).
- `tugutil dash redo` after an undo restores the undone operation's recorded after-state; `undo → redo → undo` lands each recorded state in turn; redo refuses by name (`nothing-to-redo`, `superseded`, `tip-moved`, `base-dirty`, `worktree-dirty`) when the world moved on (Rust tests, Steps 4–5).
- A conflicted markdown file whose clean `git merge-file` output carries a setext `=======` underline is settled by rung 3 rather than withheld to `unresolved` (Rust test, Step 1).
- `cd tugrust && cargo nextest run` green with `-D warnings` throughout; `tugutil plan lint` exit 0 on this document.

### Risks and Mitigations {#risks}

#### [R01] The parser diverges from what git actually writes {#r01-parser-divergence}

Marker text has variants: default vs `diff3`/`zdiff3` conflict style, `conflict-marker-size` attribute changing marker length, CRLF files. A parser tested only on hand-typed fixtures would pass its tests and miss real output. **Mitigation:** Step 1's tests generate marker text by running real `git merge-file` (default and `--diff3`) and real `git merge-tree` in tempdir repos, and the parser accepts marker runs of ≥7 characters so enlarged `conflict-marker-size` values still detect. CRLF fixtures included.

#### [R02] Strict block detection lets orphan marker lines land {#r02-orphan-markers}

A resolver that deletes some marker lines but not all leaves a malformed block, which strict detection reads as content — so sloppy resolution garbage could pass the candidate gate. jj makes the same trade (`update_from_content` treats wrong-arity markers as resolved content). **Mitigation:** the failure is cosmetic and visible — every resolution lands as a reviewed diff in the join report — where the old predicate's failure was a permanent wedge on legitimate content. Step 1 additionally appends an advisory warning (never a refusal) to `ResolveOutcome.warnings` when a conflict-set file carries orphan marker lines without a complete block.

**Where the advisory reads from, and where it deliberately does not.** The scan runs in `resolve_ladder`'s partial arm over the conflict-set paths in `staged_tree`, via an `orphan_marker_paths_in_tree` helper mirroring the existing `marker_paths_in_tree` — `ResolveOutcome.warnings` is already the outcome's warning channel, so nothing new is plumbed. The workshop side, where a sloppy resolver would actually produce orphans, is *not* given an advisory: `Workshop::commit` and `Workshop::checkpoint` return bare `Result` with no warnings channel, and widening two signatures to carry an advisory nobody refuses on is scope the risk does not justify. That side is covered by the join report's per-file diffs, which put every resolution in front of a reader before anything lands.

#### [R03] Salvage replays a resolution whose surroundings changed {#r03-salvage-staleness}

Stage-oid equality guarantees the three *inputs* are byte-identical, not that the project around them still wants the same answer. **Mitigation:** this is strictly narrower than what rung 2 already does — rerere replays on textual preimage match, salvage on exact oid match — and every salvaged file still rides the candidate through `commit_candidate`'s marker/stage/report refusals and appears in the join report's per-file diffs with its rung named.

#### [R04] Undo's conflict-ref restore collides with a newer chain {#r04-restore-collision}

Between a join and its undo, a new resolve may have parked a fresh conflict chain at the same ref. Overwriting it would destroy newer work to restore older work. **Mitigation:** the restore is conditional — if `refs/tug/conflict/<name>` exists and does not point at the recorded tip, undo leaves it and appends a warning naming both tips ([P04]). The recorded chain stays reachable through the op's keepalive either way.

#### [R05] Redo re-applies into a world that moved on {#r05-redo-races}

After an undo, the user may land new commits, rebuild the dash, or run new operations; a redo that re-applied blindly would trample them. **Mitigation:** redo refuses `superseded` when any newer completed non-undo op touches the same dash after the undo being redone, and every per-verb re-application is a CAS against the recorded tips with the existing refusal vocabulary ([P08]).

### Design Decisions {#design-decisions}

#### [P01] A conflict is a well-formed block, detected structurally (DECIDED) {#p01-structural-blocks}

**Decision:** `has_conflict_markers` returns true iff the content contains at least one complete conflict block: an opener line (`<` run), optionally a base-section separator line (`|` run, diff3/zdiff3 style), exactly one separator line (`=` run) after the opener (and after the base separator when present), and a closer line (`>` run) — in that order. A *marker line* is a run of ≥7 identical marker characters starting at column 0, followed by end-of-line or a space (opener/closer carry ` <label>`; `=======` and `|||||||` are bare or labeled). Marker-ish lines outside a complete block are content. The parse shape ports jj's `parse_conflict` (jj `lib/src/conflicts.rs`): scan lines, remember an open block's start, emit only when a closer completes a well-formed sequence.

**Rationale:** git only ever writes complete blocks, so completeness is exactly the signature of a real conflict; bare `=======` setext underlines, doc examples, and test fixtures stop being false positives. Detection-only is sufficient — unlike jj we never reconstruct stages from marker text (the stage table lives in the conflict record), so `parse_conflict`'s hunk extraction and jj's marker-length escalation on write are deliberately not ported.

#### [P02] One predicate, same signature, internals swapped (DECIDED) {#p02-one-predicate}

**Decision:** the fix lives entirely inside `has_conflict_markers(bytes: &[u8]) -> bool` (resolve.rs); no call-site signatures change. Call sites inheriting the fix: `is_clean_merge` (four ladder rung exits in resolve.rs), `marker_paths_in_tree` (resolve.rs, feeding `conflict_summary` in ops.rs), and `Workshop::marker_paths` (workshop.rs, feeding the candidate gate in `Workshop::commit`, `Workshop::unresolved`, and `Workshop::checkpoint`'s stray check).

**Rationale:** the landed round already routed every marker question through this one function ("the ONE predicate"); keeping that property means the fix cannot half-land.

#### [P03] The conflict chain tip joins the op record (DECIDED) {#p03-chain-in-keepalive}

**Decision:** `OpBefore` gains `conflict: Option<String>` (`#[serde(default)]`) — the tip of `refs/tug/conflict/<name>` at capture time, read via `read_conflict` *without* the validity gate: even an invalidated chain's checkpoints are work worth keeping alive. `tips_of` appends it to the keepalive parents. `capture_before` populates it.

**Rationale:** the keepalive exists so no verb can strand commits; the conflict chain is the one commit family the landed round left outside it. Reading raw rather than `valid_conflict` is deliberate — validity answers "may this chain be opened?", keepalive answers "may this work be collected?", and the second question has a broader yes.

#### [P04] Undo restores the conflict ref for join and discard, conditionally (DECIDED) {#p04-conditional-restore}

**Decision:** `undo_join` and `undo_discard` — the two verbs whose teardown deletes the conflict ref via `clear_candidate` — restore `refs/tug/conflict/<name>` to `op.before.conflict` when it is recorded. The restore is skipped with a warning naming both tips if the ref currently exists pointing elsewhere ([R04]). `undo_replay` leaves the ref untouched: a replay never deletes it, and restoring the dash tip is precisely what re-validates the chain under `conflict_is_valid`'s head-equality test.

**Rationale:** restore what the verb destroyed, only what it destroyed, and never at the cost of newer work — the same shape as the branch restores, with the same never-force discipline.

#### [P05] Salvage is a ladder rung between the replay probe and rerere (DECIDED) {#p05-salvage-rung}

**Decision:** `resolve_ladder` reads the prior chain (`read_conflict`, raw) at its start and threads it to a new salvage rung placed above rerere. For each still-unresolved path, salvage applies when the prior record's `ConflictPath` for that path has byte-identical stage oids and modes (base, ours, theirs) to the current stages *and* the path is marker-free at the prior chain tip (i.e. a checkpoint resolved it, per [P01]'s predicate). The resolution is the prior chain tip's blob for that path (`git show <old-tip>:<path>`), reported as `ResolvedBy::Salvage`.

**Reading at ladder entry is required, and two different writers are why.** `resolve_conflicts` clears the ref through `clear_candidate` (which folds `clear_conflict`), *and* `resolve_ladder` itself calls `clear_conflict` directly on its fully-resolved arm before returning. An entry read is upstream of both; a read taken anywhere later races one of them.

**Salvage is computed as a batch, above `rerere_rung`, not as a per-file check inside the loop.** `rerere_rung` is not a per-file rung despite its position in the ladder's numbering: it runs once, before the per-file loop, and spins up a scratch worktree and a real merge to build the `rerere_resolved` map that the loop then consults. A salvage check placed only inside the loop would therefore still pay for the rerere worktree even when every path salvages. So: build the salvage map first, skip the `rerere_rung` call entirely when salvage covers every conflicted path, and consult salvage ahead of `rerere_resolved` inside the loop.

**Rationale:** the ladder is ordered by descending trust, and exact-oid replay of a reviewed resolution outranks rerere's textual preimage replay — identical inputs, previously accepted output, deterministic. It is also the cheapest rung above the loop: no scratch worktree, no merge machinery, one blob read per path.

#### [P06] Salvage harvests checkpoint work only (DECIDED) {#p06-salvage-scope}

**Decision:** the salvage source is exactly the prior record's `paths` list (the paths that were unresolved when that record was composed) filtered to those marker-free at the prior chain tip. Machine-rung resolutions from the prior run (its `resolved` list) are not salvaged; those re-derive through their own rungs, and rung 2 already replays what the teach-back recorded.

**Rationale:** checkpoint work is the only category that is both expensive (AI-seam and human turns) and otherwise unrecoverable across invalidation; re-deriving the cheap deterministic rungs keeps salvage's precondition simple and its trust story airtight.

#### [P07] Redo is a verb with jj's undo-stack bookkeeping (DECIDED) {#p07-redo-bookkeeping}

**Decision:** `OpVerb` gains `Redo`. `OpPayload` gains `reverses: Option<u64>` (`#[serde(default)]`), set when recording an Undo (the seq it reverses) and when recording a Redo (the undo seq it reverses). A redo candidate is the newest completed op with `verb == Undo` and `undone_by == None`, per-dash filtered like undo. Performing redo sets `undone_by = redo_seq` on the undo op and **clears `undone_by` back to `None` on the original op**, making it undoable again. `is_undoable` excludes both `Undo` and `Redo` verbs from undo candidacy; redo candidacy considers only `Undo` ops.

Two mechanical consequences the implementer must not miss, both in `oplog.rs`:

- **`record_undone_by` only sets.** Its current signature writes a `u64`; clearing needs `Option<u64>` (or a sibling `clear_undone_by`). Whichever shape, the payload rewrite stays the existing read-modify-write-atomically pattern.
- **`undo_in`'s candidate filter is a second copy of the predicate.** It reads `.filter(|op| op.verb != OpVerb::Undo)` today, independently of `is_undoable`. It must exclude `Redo` as well, or a redo record becomes an undo candidate and a plain `dash undo` after a redo reverses the bookkeeping instead of the join. Keeping two spellings of one rule is what makes this a hazard; collapsing the filter to call `is_undoable`'s verb test is the safer edit.

**Rationale:** this yields jj's semantics without jj's description-string parsing: `undo, redo, undo` toggles one operation; repeated undo walks progressively deeper; no linked list of undo-of-undo ever forms because an undo is never itself undone — it is *redone*, and the original's candidacy flag is the single source of truth for what a second press means. The `reverses` field makes the pairing explicit in the record rather than derived by searching `undone_by` backlinks.

#### [P08] Redo re-applies recorded after-state behind CAS, per verb (DECIDED) {#p08-redo-cas}

**Decision:** redo re-applies the *original* op's recorded `after`-state, verifying the world matches what its undo left (the original's `before`-state) and refusing by name otherwise. Per verb:

- **Redo of an undone join:** verify the base branch sits at the original's `before.base_tip` and the base checkout is clean on affected paths; then re-perform the recorded motions — base branch to `after.base_tip` (the landed squash, reachable via the undo op's keepalive), delete `tugdash/<name>` (CAS: it must sit at `before.dash_tip`), remove the recreated worktree, clear the four branch config facts, delete candidate and conflict refs the teardown would have cleared.
- **Redo of an undone replay:** `cas_reset` the dash branch from `before.dash_tip` to `after.dash_tip` from inside the worktree (`no-worktree` refusal if it is gone, as undo-replay already states) — **and nothing else.** In particular it does *not* re-run `reconcile_ledger_cells`. The ledger's commit cells live in the plan file, which is committed content on the branch, so moving the branch moves them; `undo_replay` correspondingly does no ledger work either, and the two directions stay symmetric. A forward reconcile would be worse than redundant: `reconcile_ledger_cells` can land a bookkeeping commit, which would leave the tip *past* `after.dash_tip` and make the next undo's CAS refuse `tip-moved` — the same bookkeeping-commit trap round 1 of `dash/dash-hardening.md`'s review caught in undo-of-replay. `after.mapping` stays a record, not an input.
- **Redo of an undone discard:** delete the branch (CAS at its recorded tip) and remove the worktree; the hand-back is **not** repeated — the files were copied into the base checkout by the original discard and pulling or re-pushing them is out of bounds; the outcome names them, as undo already does.

**Refusal vocabulary:** `nothing-to-redo`, `superseded`, `worktree-dirty` ([P10]), plus the existing `tip-moved`, `base-dirty`, `no-worktree`, `incomplete-op` where each applies.

**The CAS is the real guard; `superseded` is a courtesy.** `superseded` fires when a newer completed non-undo op on the *same* dash postdates the undo, which is the legible common case. The guarantee, though, comes from the per-verb compare-and-swap, and it covers what a per-dash scan cannot: undo the join of dash A, then join dash B onto the same base, and redoing A would reset the base over B's landing — but redo-join verifies the base branch sits at A's `before.base_tip`, finds B's squash there instead, and refuses `tip-moved`. Cross-dash interference is caught by the tip check, not by the op scan, and neither guard is load-bearing alone.

**Rationale:** the reachability argument is the load-bearing fact: the undo op's own `capture_before` ran in the post-original world, so its keepalive parents the original's after-tips — the landed join commit survives the undo *because the undo itself recorded it*. Redo is therefore always materially possible while the undo op remains in retention, and refusals are about consent, not capability.

#### [P10] Redo refuses over a dirty restored worktree (DECIDED) {#p10-redo-worktree-dirty}

**Decision:** redo-join and redo-discard refuse with `worktree-dirty`, naming the paths, when the worktree the undo restored carries uncommitted changes. They do not hand the work back, do not sweep it into a commit, and do not delete over it. Asked of the owner 2026-08-24 and decided: refuse.

**Rationale:** both verbs delete the worktree, and between the undo and the redo the user may have started working in the dash the undo gave back. `discard_in` hands uncommitted work back to the base checkout rather than refusing, but that is a *user-initiated teardown of work they are looking at*; a redo is an undo-of-an-undo, where a surprise costs more than a second gesture, and moving files into somebody's checkout as a side effect of a bookkeeping verb is exactly what this engine does not do. Refusing keeps redo inside the never-force discipline every other refusal follows and keeps [L23]'s obligation — teardown never silently loses user state — satisfied by not tearing down at all.

#### [P09] `tugutil dash redo` mirrors undo's CLI shape (DECIDED) {#p09-redo-cli}

**Decision:** `DashCommands::Redo { name: Option<String>, list: bool }` in `tugrust/crates/tugutil/src/cli.rs`, handled by `run_redo` in `tugrust/crates/tugutil/src/dash.rs`, mirroring `run_undo`/`print_undo`. `--list` prints the op log annotated with both undoable and redoable flags (the existing `print_oplog` gains the redoable column, asking `is_redoable` rather than re-deriving).

**Rationale:** the pair should read as a pair; and `print_oplog` asking the predicate rather than re-deriving is the lesson the landed round already learned once (its review fixed exactly this lie in the undoable column).

### Specification {#specification}

#### S01 — Structural marker grammar {#s01-marker-grammar}

A **marker line** is, at column 0, a run of ≥7 identical characters from `{'<', '=', '>', '|'}` followed immediately by end-of-line (LF or CRLF) or a single space (rest of line is label text). A **conflict block** is a sequence of lines: one `<` marker line; zero or more content lines; optionally (one `|` marker line, zero or more content lines); one `=` marker line; zero or more content lines; one `>` marker line. Nesting does not occur in git output; on encountering a second `<` marker line while a block is open, the parser abandons the open block and starts fresh from the new opener (jj's parser takes the same recovery). `has_conflict_markers` = "at least one complete block exists". A helper `orphan_marker_lines(bytes) -> bool` = "at least one marker line exists outside any complete block", used only for the [R02] advisory warning.

#### S02 — Op payload additions {#s02-payload-additions}

```rust
pub struct OpBefore {
    // existing fields unchanged …
    #[serde(default)]
    pub conflict: Option<String>,   // refs/tug/conflict/<name> tip at capture, validity-ungated
}

pub enum OpVerb { Join, Replay, Discard, Undo, Redo }

pub struct OpPayload {
    // existing fields unchanged …
    #[serde(default)]
    pub reverses: Option<u64>,      // Undo: the seq it reversed; Redo: the undo seq it reversed
}

impl OpPayload {
    pub fn is_undoable(&self) -> bool {
        self.after.is_some()
            && self.undone_by.is_none()
            && !matches!(self.verb, OpVerb::Undo | OpVerb::Redo)
    }
    pub fn is_redoable(&self) -> bool {
        self.after.is_some() && self.undone_by.is_none() && self.verb == OpVerb::Undo
    }
}
```

`tips_of` appends `before.conflict` when present. Old payloads parse forward via the defaults; `list_ops` tolerance is unchanged.

#### S03 — Salvage rung contract {#s03-salvage-contract}

Inputs: the current stage table (`BTreeMap<String, RawStages>` as `resolve_ladder` computes it), the prior chain (`Option<ConflictChain>` read at ladder start). For each conflicted path `p`: salvage applies iff the prior `record.paths` contains a `ConflictPath` for `p` whose `(base, ours, theirs)` `ConflictStage` oids and modes all equal the current stages for `p`, and `p` is absent from `marker_paths_in_tree(repo, prior_chain.tip, [p])`. On application the resolution bytes are `git show <prior_chain.tip>:<p>`, recorded as `ResolvedBy::Salvage`.

`ConflictRecord`'s shape is unchanged — `ConflictResolved.rung` is already a free `String` — so no `conflict_version` bump.

**The new variant costs three edits, and the compiler names two of them.** `ResolvedBy` derives `Serialize` but its stored spelling comes from two hand-written exhaustive matches in `resolve.rs`: `ResolvedBy::as_str` (add `Salvage => "salvage"`) and `ResolvedBy::parse` (add the inverse, which `record_resolved_rung`'s round-trip depends on). Both fail to compile until extended. **The resolver charter needs no edit at all:** the charter line is rendered generically as `"- \`{}\` — resolved by the {} rung\n"` from `rung.as_str()` in `join_resolver.rs`, so it reads "resolved by the salvage rung" the moment `as_str` knows the word. There is no rung-to-prose map to extend — the third edit is the variant itself.

#### S04 — Redo flow {#s04-redo-flow}

`redo_in(repo, dash: Option<&str>) -> Result<RedoOutcome, String>` in `oplog.rs`, mirroring `undo_in`'s structure: find the candidate (newest `is_redoable` op, per-dash filtered), refuse `nothing-to-redo` / `superseded` / `incomplete-op` with the same three-state diagnostic care `undo_in` takes; locate the original via `candidate.reverses` (fallback: the op whose `undone_by == candidate.seq`, for payloads written before this round); record the redo op (`capture_before`, `record_begin` with `OpVerb::Redo`, `reverses = candidate.seq`); dispatch per-verb re-application ([P08]); on refusal `abandon` the redo record; on success `record_complete`, set `undone_by = redo_seq` on the undo op, clear `undone_by` on the original, append a `redone` dash-log line. `RedoOutcome` mirrors `UndoOutcome`: seq redone, verb, dash, `recorded_as`, resulting tips, warnings.
