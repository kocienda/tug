# Focus Foundation Brief — findings and seams for the keyboard/focus/first-responder rework

This is a standalone brief. It gathers everything learned across the 2026-07-24 focus-activation round (drag/activation fixes, dash `tugdash/focus-activation`, joined to main) and the app-test triage that followed, to drive a `/devise` for foundational work on the keyboard/focus/first-responder model. It assumes no context beyond this file and the repo.

## 1. Why this work exists

The focus engine round (`6db87810a`, "Keyboard as engine state") and the focus-activation round (joined as `71fc04e8d`) fixed real user-visible failures, but every fix required custom hacking at a different layer: gesture classification, the theft gate, the raw event stream, the projection. The user's verdict: the model did not land in the simple, easy-to-build-on / hard-to-get-wrong place it was aiming for. The mandate for this next round: **isolate the parts of the web stack we don't control, and assert control over those touch points.** The expectation is not clean-code miracles — it is a real codebase (in the `NSWindow`/`UIScrollView` sense) that handles the issues as they come, in one place, on purpose.

## 2. The core diagnosis

The prior rounds unified the **write** side of focus but left the **read** side plural, and they kept two competing definitions of truth alive. Every bug found since lives on one of those two seams.

### 2a. One writer, many readers

What exists and held up: one focus-write primitive (`FocusManager.place`), one parking register (the key sink, `data-tug-key-sink`), one corrector (the watchdog, `checkFocusInvariant`), one permission gate ([A8], `focus-theft-gate.ts`). None of the recent bugs were two writers fighting.

What does not exist: a single gesture interpreter. The pane-focus-controller classifies pointerdowns for activation/deselect. The responder-chain-provider classifies the same pointerdowns for chain promotion, and again for key-view placement (`placeFromPointer`). `TugListView` classifies them for selection. Each rides its own capture-phase document listener; correctness depends on all of them reaching the same conclusion in the right registration order. The bug taxonomy so far is exactly the ways that fails: layers disagreeing about drags (activation `preventDefault` killed native drag starts), a subsystem refusing another subsystem's own register (the theft gate vs the parked sink), and every layer riding an event WebKit deleted (the missing post-drag `pointerdown`).

### 2b. Two ontologies of truth

The engine's model: FocusManager state (key card, key view, cursor, first responder, per-card contexts) is the truth; `document.activeElement` is a register the engine parks (engine-routed → sink) or grants (dom-granted → text surface). The older model, still live in the gate, the watchdog, and many tests: `document.activeElement` is the truth about where the user is. Both models operate simultaneously. The theft gate's branch 5b is literally a treaty clause between them — a nine-branch decision tree enumerating every configuration where DOM focus is "really" the engine and not the user. The triage found the same seam in **tests**: a whole category asserts `el.contains(document.activeElement)` to mean "the keyboard is here," which is false-by-construction whenever the engine parks the sink (see §4, cause 4).

### 2c. Essential vs accidental complexity

Some scar tissue is irreducible — the browser is a co-author that cannot be fired. Known load-bearing WebKit behaviors, each now handled in exactly one place with doctrine written next to it:

- Re-`focus()`ing an already-focused contenteditable blurs to `<body>` → idempotent grants (`if (!view.hasFocus) view.focus()` in `state-preservation.ts` / `tug-text-card-editor.tsx`).
- Mousedown's default focuses the nearest tabindex'd ancestor (or clears to body) after pointerdown → activation-click `preventDefault`, no-tabindex rules, watchdog re-park.
- **A native drag session consumes the pointer stream's release** — the first click after a native drag emits no `pointerdown`, only `mousedown` (the release delivers the catch-up `pointerup`). Healed centrally by the resync shim in `pane-focus-controller.ts` (synthesizes the missing pointerdown, registered before all other listeners). Doctrine: focus-language.md § "Drag and the keyboard"; per-component mousedown fallbacks are banned.

The rest of the pain was accidental: distributed classification and the dual ontology. Those are ours and fixable.

## 3. Proposed foundational moves (from the diagnosis; /devise should pressure-test these)

1. **One gesture interpreter.** A single capture-phase controller owns the raw pointer/mouse stream (it already owns the resync shim), classifies each gesture exactly once — activation, deselect, selection, drag-arm, content click, chrome — and dispatches a typed intent. Pane-focus-controller, responder-chain-provider promotion/placement, and TugListView selection become consumers of the classified intent rather than independent classifiers. Kills the "layers must agree" failure class structurally.
2. **Fold the theft gate into the engine.** `canProgrammaticallyFocus`'s nine branches reverse-engineer from `document.activeElement` what the engine already knows, because it placed it. Make theft protection a property of `place()` querying engine state; branch 5b (the treaty clause) evaporates.
3. **Declare one truth; make the DOM a projection.** Engine state is authoritative; `document.activeElement` and the `data-key-view`/`data-key-cursor`/`data-first-responder` attributes are write-through projections the engine maintains. The watchdog stops being a thief-catcher and becomes the reconciler of the projection ("does the DOM match the model? if not, reproject"). This also answers [Q02] (body-stranding is a projection gap, reprojected like any other) and directly fixes the projection split-brain in §5 seam 1.

## 4. Triage results — what was red, why, and what got fixed

Starting claim was 19 red app-tests; the measured truth on joined main was 16 red among the candidates (several fixed by the joined round), plus 2 more discovered outside the candidate list (at0050, at0221). **Six distinct root causes** were found across them — every one initially mispredicted, which is itself a finding: in this subsystem, only direct instrumentation distinguishes plausible causes.

1. **The default-focus walk selected focus-refusing controls** (engine defect, FIXED). `DEFAULT_FOCUS_SELECTORS` in `tugdeck/src/default-focus.ts` — every rung can match a `data-tug-focus="refuse"` control (a switch in a focus group carries `data-tug-focus-key`; rung 4 is literally `button:not([disabled])`). Activating a card seeded the key view onto a checkbox/switch. Fix: `resolveDefaultFocusTarget` skips candidates inside `[data-tug-focus="refuse"]` (checked per-candidate via `closest`, since the attribute sits on the Radix root wrapping the match).
2. **`refuse` semantics were incomplete** (doctrine decision, FIXED). User decision: clicking a refuse-marked leaf must not move the key view (AppKit: a button is not a key view; clicking one never moves the insertion point out of the field beside it). [D01]'s "one attribute, one semantic" widened from two behaviors to three, documented in `responder-chain-provider.tsx`: chain-promotion-skip, **key-view-placement-skip** (new guard in `placeFromPointer`), browser-focus-prevention. The three are one idea: the control is outside the key loop, so no pointer gesture on it moves any keyboard register.
3. **Leaf controls were unreachable by keyboard under the engine route** (engine defect, FIXED — user-decided design). Leaves (button/checkbox/switch/slider) rely on native key handling, which needs DOM focus; engine-routed focus parks `activeElement` on the sink; nothing bridged them — Tab to a switch, press Space, nothing happens. Only accessibility mode had a bridge (`mirrorKeyViewFocus`). User chose **engine-synthesized acts** over extending focus-mirroring: `deliverToEngineLeaf` in `responder-chain-provider.tsx` forwards the keydown to the key-view element and completes Space/Enter as a `.click()` press when the component didn't consume it. Wired at the two yield points (arrow-capture [P25] and the leaf branch of `act`). The sink stays parked; DOM focus never becomes truth for a leaf. The re-entrancy latch is load-bearing (the forwarded event must bubble to reach React's root-attached handlers, so it re-enters the same document listeners). This fix also greened the accordion test unprompted — it was a shared gap, not per-component.
4. **The DOM-containment test category** (test defect class, 3 instances FIXED; more may exist). at0150/at0159/at0179 each asserted `container.contains(document.activeElement)` to mean "the keyboard is here/returned." Under the engine route the sink is outside every card and sheet, so the predicate is false while the keyboard is exactly where it should be. In each case the test's own comment stated the correct contract ("focus returned to the opener context", "its responder becomes first responder", "stayed inside the sheet") and the assertion didn't match it. Fixes assert the engine fact (`getFocusedCardId()`, `[data-first-responder]`, `[data-key-view]` containment) with the DOM check kept as the dom-granted alternative. **An unknown number of other tests still encode activeElement-as-truth; a corpus sweep for this pattern belongs in the plan.**
5. **Stale selectors after product renames** (test defect class, FIXED — the biggest single lever). The Route button's `aria-label` was renamed "Route" → "Route this input" (commit `883216849`, the bang-commands mint), silently breaking the selector in **seven** test files; route-menu item ids moved from glyphs (`$`, `❯`) to bang names. This alone accounted for at0140 (0/4 → 4/4) and at0157. Nothing tied selectors to the source they mirror — a `@covers`-like discipline for selectors (or shared selector constants) is worth considering in the plan.
6. **Fixture geometry** (test defect, FIXED). at0112's Focus Walk panel sits below the card's fold; a CGEvent click at the element's laid-out rect landed on empty canvas → `deselectActiveCard` → key card null → wipe. Fixed with a `scrollIntoView` reveal before the click, with the causal chain documented in the test. (`gallery-switch` had already guarded this — its focus demo is deliberately first "so the focusables sit above the fold.")

## 5. The seams — specific fragilities to check when diving in

1. **Per-context key-view state, global DOM projection** (UNFIXED — the sharpest new finding). `FocusContext` holds `keyViewId` per card; `syncKeyViewDomAttribute` clears `[data-key-view]` with a document-wide `querySelectorAll` before restamping, and only the active context projects. Consequence, observed live: any transient `setKeyCard(A → null)` activates the empty default context, whose projection wipes the live context's mark globally — and returning to A does not restamp unless something calls `setKeyCard` again (it only projects on the transition it sees). Engine says "beta is the key view"; DOM says nothing is. This is the dual-ontology split-brain in a third location and is exactly what the projection-reconciler move (§3.3) should subsume.
2. **`deselectActiveCard` is reachable by accident.** A click that misses every pane (portal gaps, below-the-fold geometry, overlay seams) silently clears the key card, with the cascade in seam 1 behind it. The gesture interpreter (§3.1) should make deselect a deliberate classification, and the projection layer should make a transient null key card harmless.
3. **The theft gate still models the pre-sink world.** Branch 5b was patched to permit the parked sink (D1 fix), with live-ring protection relocated to `resolveBagFocus` (returns `none` when the engine already holds the target card's key view). That relocation was found by breaking at0248 three different ways first — the protection had no natural home because the layering is ambiguous. §3.2 is the structural answer.
4. **The default-focus selector chain is DOM-shaped, not engine-shaped.** It walks raw selectors (`data-tug-focus-key`, `data-tug-state-key`, generic focusables) and had to learn the refuse exclusion as a bolt-on. Under an engine-authoritative model, "what gets focus when a card activates with no saved target" should be an engine question answered from the focusable registry, not a DOM query.
5. **Leaf act synthesis is a bridge, not a destination.** `deliverToEngineLeaf` works (dispatch synthetic keydown, complete as click), but it encodes "leaves are operated natively" as a permanent assumption and rides event re-entrancy with a latch. Under §3.1/§3.3 the engine could instead know each focusable's act contract (act/toggle/value-step) and invoke it directly — the "engine synthesizes the act" decision taken to its conclusion.
6. **The watchdog/ledger correction budget and the deferred-gesture window** (`beginDeferredGesture`/`endDeferredGesture`, `ownStop` quiet branch, `REASSERT_BUDGET = 4`, failed-correction ledger keys) are interlocking special cases on the corrector. If the watchdog becomes a projection reconciler, most of these should collapse; any that survive should be named contracts, not carve-outs.
7. **Tests as the fourth ontology.** The corpus contains an unswept residue of activeElement-as-truth assertions (cause 4), mechanism-pinning assertions (the `tabindex="-1"` class fixed in at0121/at0122 — assert "not a Tab stop", not the attribute spelling), and rename-fragile selectors (cause 5). The rework will churn exactly these observables; sweeping the corpus for these three patterns early will prevent weeks of false regressions.
8. **Order-sensitivity in the harness** (at0120) — one observed instance; unknown whether it is per-test state leakage or an app-side residue. Worth one look before trusting big batches during the rework.
