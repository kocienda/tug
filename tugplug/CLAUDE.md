# Tugplug Plugin Guidelines

## Skills

The plugin ships **agentless, main-loop-driven** skills — there are no sub-agents.

Every skill but one carries `disable-model-invocation: true`: they are gestures the user makes, and a model that reached for `/arc` on its own would be starting work nobody asked for. **`brief` is the exception, deliberately** — the user asks for a brief in prose ("write a brief", "brief this") far more often than by typing a command, and a document written where the user said to write one is the narrowest thing a model can be trusted to reach for.

An **arc** is work that leaves the base on a worktree and comes back to it through a join, and it has **one door**: `/arc`. It runs under the wheel — the server-driven sequence that rotates the card's session through stages, each on the model the project declared for it — and it always opens on a brief. An arc takes one of two shapes, differing by **settling time** and by nothing else. A **plain arc** is the short one: the door writes the brief and a **task list**, and the arc opens straight at `implement`, then `audit`. A **planned arc** is the long one: the door writes the brief alone, and the arc runs `devise` → `review` → `implement` → `audit`. The shape is decided at the door and expressed in the documents it leaves; `tugtool arc run <name>` takes no flag and **derives the kind from those documents at the opening** — a task list with no plan beside it is plain, a brief alone or a plan is planned — then records it, so every stage after reads the record rather than sniffing the directory again. (An arc opened before the kind was recorded has none, and the old document sniff answers for it — a `plan.md` outranking a `tasks.md`.)

**The four stage skills are not doors.** Each refuses to run outside an arc, on the same grounds `arc-devise` always did: the discipline a stage works under — one step per turn, no dialogs, a stamp or a mark as its whole product — is only safe when something is reading the result and pacing the next one. There is no one-stage arc, and none is built. A user may dig in and invoke one by hand; nothing prevents that, and nothing goes out of its way to support it.

**The arc family:**

- **`arc`** — the one door, invoked as `/arc [name] [instruction…]`. Orients on what is in flight, sharpens the idea with the user, writes the **brief** in this conversation on the user's own model against the brief skeleton, **decides the arc's shape**, and hands it to `tugtool arc run` as the turn's last act. On a plain arc it also writes the **task list** — a minimal ledger document: an execution-steps section and a step ledger, nothing else — which is never linted, because it exists to make the fraction real and the run resumable rather than to pass `tugtool plan lint`. On a planned arc the brief is the whole output, and the plan is the devise stage's product. The shape decision is the user's own words first, the door's reading of the brief's content and the code it names second, and one `AskUserQuestion` with two options only when both come up empty — never a line inside a document, since a brief's Exit section is its author's expectation rather than the user's instruction, and the hand-off sentence says which shape and why. It **narrates; it does not restate** — the arc's stages are the single source of truth for their own mechanics. Creates no worktree, commits nothing, implements nothing, joins nothing.
- **`arc-devise`** — a planned arc's first stage: author an implementation plan in-thread from the arc's brief, against the devise skeleton (`tuglaws/devise-skeleton.md`). Writes the arc's own `plan.md`, or an explicit path.
- **`arc-review`** — a planned arc's second stage: lint the plan (`tugtool plan lint`), judge it against [`tuglaws/plan-review-rubric.md`](../tuglaws/plan-review-rubric.md) and the real code, **apply the fixups in the plan**, append a Review Record, and stamp it with `tugtool plan stamp` as the last edit — which is what lets `tugtool plan status` say afterwards whether the review still covers the document. The stamp is the stage's whole product and the hand-off: the runner reads it and rotates to implement, so the stage prints no chip. Seated by the wheel, on the model the project declared for the review, and never run inline by the session that wrote the plan: the cold read is the whole point, and handing the reviewer the author's context is what destroys it.
- **`arc-implement`** — the implement stage of every arc: drive a ledger to a tested build on an isolated `tugtool arc` worktree, closing **one step per turn** and committing each, stopping before the join. The ledger is a devised `plan.md` or an `/arc` door's `tasks.md`, whichever the arc has, driven with `tugtool arc step start|done|withdraw|reset|reopen`. Records the green baseline in the arc's documents at setup, so a rotation cannot lose it. Reads `tugtool plan status <name>` for a **plan** and *says* in a sentence when the review is `stale` or `never-reviewed` — it raises no dialog and prints no chip, because an arc does not pause in front of nobody. A task list has no review stage, so this stage is its cold read: before opening step 1 it reads the task list against the brief and the code, and a step that rests on a design decision the brief does not make stops the arc through `tugtool arc ask` rather than being guessed at. A task list whose steps all follow from the brief gets nothing said.
- **`arc-audit`** — the last stage of every arc: read the branch's whole diff **cold** against the ledger it was written from and the brief behind it, fix what does not match as ordinary rounds, verify the fit, refresh the join draft, and `tugtool arc mark <name> audited` as the last act. The mark is the stage's whole product — the predicate reads the arc's own declaration rather than anything the stage said — and an audit that ends without one stops the arc as `audit did not mark`. Raises no dialog, opens and closes no step, and never joins.

The door opens either kind of thing. Both shapes ride the same `tugtool arc` verbs, and the Arcs card, the Changes shade, and the join do not distinguish them — what differs is only how much settling happened before the first step.

**Drafting and authoring:**

- **`draft`** — analyze the working changes, decide per-file dispositions, and author the session's landing draft via `tugtool draft set`. **Never commits** — the user lands the draft with `/commit` in the Session card.
- **`brief`** — write the conversation's settled findings and decisions as a brief, against the skeleton beside it, to the Briefs Directory (`tugtool brief dir`) or an explicit path. The plugin's one model-invocable skill, so the model reaches it when the user says *brief* in prose. Sharpens nothing, opens nothing, and asks once — only when the directory does not exist.
- **`tripwire`** — lay, revise, and shake down a **tripwire**: a standing watch that fires when a landing gesture commits onto the branch it names, answers a brief through a read-only diagnosing session, and raises its hand only when it has something a person should see. Rides `tugtool tripwire` and authors nothing else. **Never joins** — a tripwire may author work on an arc and say so, and landing it is the user's act.
`spike-card` — scaffold a design spike onto the deck — is **not** a plugin skill: it is about `tugdeck/src/spikes/` and nothing else, so it lives with this repository at `.claude/skills/spike-card/` and never ships.

## The standalone contract

Tug ships as `Tug.app`, and the only files a user's session can count on are the ones inside that bundle: the binaries in `Contents/MacOS/` (`tugtool`, `tugcode`, `tugcast`, …) and this plugin at `Contents/Resources/tugplug/`. A user's project has no `tuglaws/`, no `justfile`, no `CLAUDE.md` of ours, and no source checkout, and the machine may have no `jq`, no `bun`, and no `~/.local/bin` symlinks.

So the plugin depends on nothing outside itself and the bundle:

- **Hooks are answered by `tugtool`.** `hooks/pre-tool-use.sh` finds the binary (PATH, which the app seeds with the bundle's `Contents/MacOS/`; then beside the plugin; then `TUG_BUNDLE_PATH`) and pipes the payload to `tugtool hook pre-tool-use`. No `jq`, no other tool. When no binary can be found the hook says so through a `systemMessage` rather than going quiet.
- **Skills cite `tuglaws/` only with an absence clause.** A doctrine document is a pointer into a project that has one; every skill that reads one says what survives when it is absent, and carries those rules inline.
- **Skills never name this repository's build or tests.** What to build and what to run is the project's to declare in `.tugtool/config.toml` (`[tugtool.arc]` `build`, `post_create`, and the surfaces `tugtool arc verify` runs); the skill reads `tugtool arc config` and relays it. In Tug that declaration is `just app-debug`, and the surface checks are in the config file — the skills do not know this, and must not.
- **No `just`, no commit hashes, no `tugdeck/`/`tugrust/` paths, no `/Users/`.** `scripts/tugplug-lint.ts` (`just tugplug-lint`, part of `just lint`) refuses each of these in `tugplug/`, and `tugplug/__tests__/standalone.test.ts` (`just test-standalone`, part of `just test`) drives the real hook script and the real `tugtool arc` verbs from a scratch project with an empty PATH and a fresh HOME.

**This file is the one the lint exempts, deliberately.** It is *about* the contract rather than a party to it, so it has to be able to name the guard (`just tugplug-lint`), the repository's own declaration (`just app-debug`), and the paths a reader needs to find — every one of them a string the lint refuses. Linting it would mean deleting the sentences that explain the rule. Nothing loads it in a user's project: Claude Code reads a `CLAUDE.md` from the working tree, and the plugin's own is not one, so it ships as prose nobody outside this checkout will read. The exemption is therefore a decision with a cost of zero, and the check that keeps it honest is a person editing this file — which is the same check every doctrine document has.

The lifecycle skills run in the seated session and ride the `tugtool arc` CLI (`create` → `step start` → `commit` → `step done` per step, `mark` for the stages git cannot see). The flow starts at the one door, `/arc`, which settles the shape as it writes the documents — a task list settled at the door, or the brief alone for a plan devised and reviewed first — and under either shape the server rotates the stages itself and nothing needs typing between them, up to the user's join gesture in the Session card (the working run leaves the arc's join draft behind for it).

**A stage is handed its coordinates; it never derives them.** Every stage prompt carries a `where` line — the arc's worktree, the seat it is bound to, the stage, and for implement the step in hand and the selection's end — composed by the runner from the records it owns. The five-record comparison runs *there*, at the dispatch: `tugarc_core::doctor` before any stage prompt is sent, and a disagreement stops the arc with the doctor's own sentence rather than seating a stage to discover it. So no stage skill probes for its arc, and none reports having found one. When something does need repairing by hand, `tugtool arc doctor <name>` is the gesture — `/arc-bind` writes one of the five records and answers nothing about the other four, so it is never the first reach.

**The shared working discipline lives in [`tuglaws/arc-work-doctrine.md`](../tuglaws/arc-work-doctrine.md)**, not in the skills: worktree-root discipline, the verification bar, test discipline and the banned shapes, law discipline, round mechanics, the stop-before-join obligation, no plan numbers in durable artifacts. `arc-implement` and `arc` cite it and state only their own flow, so editing one no longer drifts the other.

**Location discipline (critical):** an arc's documents live at `<repo>/.tug/arcs/<name>/` — `brief.md`, `plan.md`, and `tasks.md` — and the **name** is their address on every verb. `tugtool arc documents <name>` reports all three, `--ensure` creates the directory to write into, and nothing is declared, assumed, or asked: there is no directory to choose. The documents are gitignored, so they are never on a diff and never something the user has to clean up. Once a worktree exists it is the **only** working root for *code* — every operation uses an absolute path into it, and nothing is written to the base checkout's working tree until the landing.

The old multi-agent orchestration — a swarm of clarifier/author/critic/conformance/overviewer/architect/coder/committer/reviewer/auditor/arc agents — has been fully retired: no sub-agents, no per-step tugstate database, no inter-agent JSON contracts. Every agent is gone.

## Plan Mode Policy

The policy now ships in `work-grammar.md` beside this file, which tugcode appends to every session's system prompt — so it is enforced on every project the bundle opens rather than only where this file happens to be read.
