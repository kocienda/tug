# Design Decisions

*Each decision records a non-obvious choice and its rationale. Decisions are referenced from [tuglaws.md](tuglaws.md) as `[D##]` and laws are referenced here as `[L##]`.*

## Theme & Token Architecture

**D01.** Theme definitions (color choices + recipe reference) are stored as `.json` files in `tugdeck/themes/` (shipped) and `~/.tugtool/themes/` (authored), not as TypeScript constants. Enables runtime loading without rebuilding and the Prototype pattern for new theme authoring. [L06]

**D02.** Two-directory storage with unique names. Shipped themes in `tugdeck/themes/` (version-controlled, read-only). Authored themes in `~/.tugtool/themes/` (user data, not in repo). Names are unique across both directories — middleware checks authored first, then shipped, but uniqueness means no shadowing.

**D03.** Every theme is a peer — no base layer, no override cascade. Switching themes copies the selected theme's complete CSS file into `styles/tug-active-theme.css`. For brio, the source is `styles/themes/brio.css`. For harmony, the source is `styles/themes/harmony.css`. The active theme file is always complete; it is never empty. [L06]

**D04.** `contrastSearch()`, `darkRecipe()`, `lightRecipe()`, and `RECIPE_REGISTRY` are defined in `theme-engine.ts`. `RECIPE_REGISTRY` is the only derivation dispatch path — all `deriveTheme()` calls route through it.

**D86.** The `formulas?: DerivationFormulas` escape hatch is removed from `ThemeRecipe`. The recipe function is the only derivation path. `RECIPE_REGISTRY` is the extension point for new recipe variants.

**D87.** The theme generator card follows Mac document conventions: New (Prototype pattern, copy existing theme), Open (load from available themes), auto-save (500ms debounce to disk), Apply (inject CSS app-wide). Shipped themes open read-only. No explicit Save button.

**D88.** All theme loading goes through the Vite dev middleware. `ThemeName` is a plain `string` (not a hardcoded union). `themeCSSMap` is populated dynamically at startup via `GET /__themes/list`. Supports arbitrary authored themes without code changes.

**D89.** `canvasColorHex()` accepts derived canvas surface params (`hue`, `tone`, `intensity`) extracted from `ThemeOutput.formulas` after running `deriveTheme()`. The raw JSON `surface.canvas.intensity` differs from the derived `surfaceCanvasIntensity`; callers must use the derived value. The `CANVAS_COLORS` lookup table is removed.

**D90.** A theme's `recipe` field (`"dark"` or `"light"`) is set once at theme creation (copied from the prototype) and is immutable. The generator card displays recipe as a read-only label, not a toggle.

**D91.** The Swift Theme submenu uses `NSMenuDelegate.menuNeedsUpdate(_:)` to populate items dynamically from a cached theme list. The web view pushes updated theme lists to Swift via the `themeListUpdated` bridge message. Eliminates hardcoded menu items and per-theme `@objc` handlers.

**D92.** Bluenote is removed from the entire codebase — Swift menu, action dispatch, theme provider, and any CSS files.

**D70.** Color palette is OKLCH-based. 24 hue families with intensity/tone axes, 5 convenience presets per hue, neutral ramp, P3 gamut support, pure CSS formulas. [L15]

**D71.** Four-prefix token naming: `--tugc-{hue}[-preset]` (palette), `--tug7-*` (seven-slot semantic surface and element tokens), `--tugx-<component>-*` (component alias), `--tug-*` (scale/dimension). [L17, L18]

**D72.** Global dimension scale via `--tug-zoom` multiplier on `:root`.

**D73.** Global timing via `--tug-timing` (duration multiplier) and `--tug-motion` (binary on/off toggle) on `:root`.

**D75.** Achromatic neutral ramp (`--tug-neutral-*`). Alpha via CSS relative color syntax, not separate opacity tokens.

**D80.** `--tug-color()` notation expands to `oklch()` at build time via PostCSS plugin (`postcss-tug-color.ts`). Theme files use the notation; browsers never see it.

**D81.** Token pairings are machine-auditable. Every foreground-on-background relationship is extractable from CSS — either via same-rule `background-color` or via `@tug-renders-on` annotation. `audit-tokens lint` enforces zero violations. [L16]

**D82.** Four semantic contrast roles govern text legibility: `content` (75), `control` (60), `display` (60), `informational` (60). Each role maps to a hue slot derived from the recipe's text and display specs. The pairing map assigns every foreground token a contrast role for threshold enforcement. [L15, L18]

**D83.** Five contrast roles with minimum thresholds: `content` (75), `control` (60), `display` (60), `informational` (60), `decorative` (15). All readable text >= 60. [L16]

**D84.** Theme application uses stylesheet injection (`<style id="tug-theme-override">`), not body class toggling. [L06]

**D85.** Optional palette entries use `var()` fallbacks so themes can omit slots gracefully. [L15]

## Component Model

**D05.** Three component kinds: *wrappers* (thin Radix adapters), *compositions* (assemble multiple primitives), *originals* (built from scratch).

**D06.** `components/tugways/` is the public component API surface.

**D07.** Components are module-scope functions composed via JSX nesting, not class hierarchies or render props.

**D08.** TugButton has two modes: *direct-action* (`onClick` prop) and *chain-action* (`action` prop dispatches into responder chain). [L11]

**D15.** TugPane is composition, not inheritance. It assembles chrome (title bar, tab strip, accessory, content region) around the active Card's content, rendered via `CardHost`. [L09]

**D16.** Card data access via `useCardData()` hook, not render props.

**D17.** Cards compute dynamic min-size from content and report via `onMinSizeChange`.

**D22.** Component Gallery card serves as living inventory — 21 tabbed demos covering all tugways components. [L10]

**D39.** Default button: responder chain designates one button per scope. Enter key routes to it. [L11]

**D43.** Component Gallery is a proper card with tabs, not a floating panel. [L10]

**D105.** "Collapse long content" splits into two primitives along one axis: *does the hidden content stay mounted?* **Logical fold** (`BlockFoldCue` + `useBlockFoldState`) is for known-list bodies — file lines, terminal output, diff hunks — where collapsing must *unmount* the hidden portion for performance (don't mount a CM6 editor for a folded file) and coordinate with the transcript scroller (don't slam the viewport when a huge body folds mid-scroll). It thresholds by item count and is coupled, deliberately, to the tool-block chrome and scroller contexts. **Visual clamp** (`TugClamp`) is for arbitrary content that is cheap to render in full but visually too tall — a wrapped command, an error message, a markdown blurb — where there is no perf reason to unmount and no scroller to coordinate with. It *measures* the rendered height (the visual line count isn't known ahead of wrapping), caps it behind a `data-expanded` + CSS window with a Show more/less reveal, and keeps everything mounted. The two share only the `ChevronsDown/Up` vocabulary, never the machinery — so neither is forced to straddle both jobs. Reach for `TugClamp` in dialogs and inline surfaces; reach for the fold system inside a tool-block body. Tree-shaped per-node collapses (JSON nodes, diff hunks, search-result files) are a third, separate thing and belong to neither. [L06]

## Responder Chain & Actions

**D09.** Responder chain operates entirely outside React state. `ResponderChainManager` is a plain TypeScript class. [L01, L02, L07]

**D10.** Four-stage key processing pipeline: keybinding resolution, responder dispatch, default handling, browser passthrough.

**D11.** Two-level action validation: `canHandle` (fast routing check) + `validateAction` (semantic validation with current state). [L07]

**D61.** `ActionEvent` carries typed payload, sender identity, and phase. [L11]

**D62.** Two dispatch modes: *nil-target* (chain walks until a responder handles it) and *explicit-target* (dispatched to a specific responder). [L11]

**D63.** Controls (buttons, sliders, pickers) dispatch ActionEvents into the chain but never register as responder nodes. [L11]

## State & Mutation Zones

**D13.** DOM utility hooks for appearance zone: `useCSSVar`, `useDOMClass`, `useDOMStyle`. All bypass React state. [L06]

**D40.** DeckManager is a subscribable store. Implements `subscribe()`/`getSnapshot()` for `useSyncExternalStore`. Exactly one `root.render()` call, at construction. [L01, L02]

**D41.** `useResponder` uses `useLayoutEffect` for registration so responder nodes are wired before any events fire. [L03]

**D42.** No repeated `root.render()` from external code. All state changes flow through `notify()` and `useSyncExternalStore`. [L01]

**D64.** Mutation transactions: `begin` (snapshot CSS inline styles) → `preview` (live CSS mutations) → `commit`/`cancel`. [L08]

**D65.** Transaction previews operate in appearance zone only. Commit handler may cross into store/React state. [L06, L08]

**D66.** Style cascade reader (`StyleCascadeReader`) provides `getDeclared()` with four source layers: `token`, `class`, `inline`, `preview`.

## Cards & Layout

**D27.** *(Retired by [D128].)* Window-shade collapse: double-click title bar toggles card between full and title-bar-only. State stored in `CardState.collapsed`. Removed outright when the width presets landed — it was pointer-only (no command, no chord, no menu item), and the chevron's title-bar slot went to the width popup, which is a control the same cluster had room for and the keyboard can reach. Old blobs carrying `collapsed: true` deserialize with the field dropped and the pane expanded.

**D30.** Tab bar visible only when card has multiple tabs.

**D31.** Tabs are a TugPane chrome feature — a UI affordance that appears when a Pane holds more than one Card. Not a data concept. [L09, L10, L25]

**D44.** Progressive tab overflow: three stages — all visible, inactive tabs collapse to icon-only, overflow into dropdown.

**D45.** Card-as-tab merge: dropping a card onto another card's tab bar merges it as a new tab. `detachTab()` reverses.

**D49.** Per-tab state bag preserves `scroll`, `selection`, and `content` across tab switches and reloads.

**D50.** `useCardStatePreservation` hook: card content registers `onSave`/`onRestore` callbacks. Uses `useLayoutEffect` for registration. [L03]

**D95.** A content-owning + engine card has exactly one text-entry surface — the engine's editor (`tug-prompt-entry` for a session card) — and activation focus has exactly one destination: the engine. A content-owning card (`bag.content !== undefined` — every session card is one) carries no `data-tug-focus-key` / `data-tug-state-key` element of its own, so `captureFocus` only ever classifies its focus as `engine` or `none`; the framework-axis save site leaves `bag.focus` absent in both cases. On restore, the single-channel dispatcher `resolveBagFocus` finds no framework-axis snapshot but an engine-managed `componentId`, and routes to the `engine` resolution — `applyBagFocus` invokes the engine's registered `paintMirrorAsActive` hook (`store.registerEngineHooks` / `store.invokeEnginePaintMirrorAsActive`). The engine is a *callable*, not an autonomous claimant: it no longer claims focus from `onCardActivated`. Focusable-but-not-entry content inside the card (a read-only `TugCodeView` viewport, a block button) carries no focus marker, so `captureFocus` classifies it `none` and activation focus correctly returns to the engine — a viewer is not a text-entry surface, and transient selection-to-copy focus is not preserved across activation. The general framework focus axis (`data-tug-focus-key` / `data-tug-state-key`, the `dom` / `form-control` `FocusSnapshot` kinds) still serves non-engine cards (form-control cards, settings cards); it is simply never populated *inside* a content-owning + engine card. See [state-preservation.md § Focus dispatch model](state-preservation.md#focus-dispatch-model), [component-authoring.md § Focus in content-owning cards](component-authoring.md), `card-host.tsx` (`captureFocus`), and `focus-transfer.ts` (`resolveBagFocus` / `applyBagFocus`). Established by Phase E.11 (single-channel dispatcher) and Phase E.12 (single-text-entry rule; per-block Find removed). Supersedes the pre-E.11 framing of this decision (the engine-vs-framework "two axes" model with `kind: "component-owned"` and `resolveActivationTarget`). Previously documented inline as `[D07]` in `card-host.tsx` comments — that local tag has been normalized to reference this decision (the canonical D07 is the JSX-composition rule above; the focus-boundary rule is D95). **D51.** Focused card ID persisted in `DeckState.focusedCardId` for reload restoration.

**D52.** Collapsed state persisted in `CardState.collapsed`.

**D121.** **Layout imposition: a slot is a position anchor, not a rect — the imposer places panes and never sizes them.** The deck's `imposition` is a required `{ kind?, contentWidth?, sidebars, rails? }` record on `DeckState`: `kind` (`"one-up"` through `"six-up"`, absent = off) defines numbered **slots**, `contentWidth` names the width content cards read at ([D128]), `sidebars[componentId] = { side, pinned? }` says which edge each sidebar card holds and whether it is standing there, and `rails[side] = { mode?, order?, shares? }` says how the cards sharing that edge stand against one another ([D134] — absent reads as a stack, which is what every rail was before it could be split). (The legacy `{ lens, lensPinned }` pair reads as `sidebars.lens` — the blob stayed at v4, defensively parsed.) All of them are layout decisions, so all of them are made in one place — the Lens **Layouts** section, whose every option is a scale picture of the resulting deck; there is no app-wide sidebar-side preference. Slots are laid across the **span** — the canvas minus each side's rail width and one imposition gap — so an imposed position is never under a rail even though a free pane may still be dragged there. **A sidebar is itself imposed, as the arrangement's fixed end rather than one of its slots** (`imposeSidebarStyle`): it holds its side at a constant pin with the imposition gap on all four sides, keeps its own width, and never overlaps. It has to be the fixed end — a slotted card can end up overlapped when the deck is crowded, and a card sliding under the Lens is the one outcome the arrangement forbids. **The Lens is draggable, and dragging it by its title bar is what takes it off the pin** (`lensPinned: false`): it becomes an ordinary free pane and the arrangement spans the whole canvas exactly as it does when the Lens is closed. Any choice in the Layouts section puts it back — naming the side, or naming the kind, is the gesture that says the Lens belongs at the end of the arrangement — as does closing and reopening it. Widening the Lens by its deck-facing edge does **not** unpin it: the arrangement keeps laying out against it, live. A sidebar pane carries no marker of its own: it is the pane hosting a card whose registration declares `layoutRole: "sidebar"`, derived by `findSidebarPanes` ([D128]). A slot is an anchor at a fixed fraction of the band: a pane of width *w* in slot *k* of an *N*-slot imposition sits `k / (N − 1) × max(0, band − w)` from the packing edge, and stretches to full canvas height. Slot 0 therefore hugs the far edge and the last slot hugs the Lens, by construction rather than by arithmetic that happens to work out. **A pane's position depends on its own width and nothing else's** — closing, opening, widening, or restacking any other card leaves it exactly where it was. A slot is a place in the arrangement, never a place in a queue, and that is worth more than the earlier rule of pooling all the slack in one margin beside the Lens (which made the arrangement re-pack whenever its membership changed). Slack now spreads evenly between the cards. That is the whole geometry: **the imposer never touches a pane's width, in any code path.** The width **presets** are no exception and were checked against this rule when they landed: a preset is applied by a *command* through `movePane`, the same door a drag-resize uses, and the imposer goes on passing whatever width it finds through untouched ([D128]). Widths stay the user's, which is what keeps the arrangement from re-creating the tab strip's fight for horizontal space — and it is why overlap needs no handling at all: when the assigned cards are wider than their share, the anchors still hold exactly and the cards simply overlap their neighbours, which is ordinary geometry, not a failure. **Slots are stacks:** any number of panes may hold one, clicking a number always assigns *and* raises (never a toggle, never a no-op), and the filterable, metadata-rich Lens list — not a tab strip — is the switching surface. Assigning a card that shares a pane with others **detaches it first** (`_detachCard`); the imposer slots cards, never tab groups. **The arrangement is also the keyboard's:** ⌘1..⌘N puts the selected card at slot N, where N is whatever the chosen kind has — the Layouts section configures the chords by configuring the arrangement, and there is no separate list of shortcuts to keep in step with it. DeckCanvas owns the `move-to-slot` handler because the canvas owns the layout tree, and it converges on the same `assign-slot` the SlotPicker dispatches, so a chord and a click do one thing. The whole digit row is bound even though six-up is the largest arrangement, and every number the current arrangement lacks — along with an empty selection and a selected Lens — is a **silent no-op**: a chord the user has not configured should do nothing, not beep. These chords replaced `jump-to-tab` (⌘1..⌘9 by tab index), which the tab strip's demotion to a switching surface of last resort had already left with little to switch; ⇧⌘[ / ⇧⌘] still walk a pane's tabs. Assignment is **only ever explicit**: nothing is auto-slotted, auto-rebalanced, or auto-evicted. Any manual move **or resize** of an imposed pane evicts it back to free geometry (an explicit option on the commit, never a "position changed" heuristic — a west-edge resize moves `position.x` too). The pinned Lens is the exception: its deck-facing edge resizes it in place, re-laying the arrangement live. `arrangeCards` (Window ▸ Cascade / Tile) skips a **pinned** Lens for the same reason — tiling writes a stored rect, and a pinned Lens paints from its pin; a Lens off the pin tiles with everything else. Turning the imposition off **freezes** every imposed pane at its live on-screen rect rather than scattering them back to stale coordinates. A kind change **clamps** out-of-range slots instead of dropping panes out of the arrangement. Geometry is **CSS-derived, not observed**: the span reaches CSS as `--tug-imposer-inset-left` / `--tug-imposer-inset-right` (the Lens's render width plus one gap) and an imposed frame's pins are `calc()` expressions over them, so a window resize or a Lens drag reflows every imposed pane with no JavaScript and no resize observation anywhere on the deck ([L06]). **Every horizontal pin is emitted as `left`**, including the ones measured from the right edge (as `100% - …`) — a frame positioned by one property can transition between two arrangements, while one that switches between `left` and `right` can only cut. That is what the settle is built on: a change to the `imposition` record marks the frames' container with `data-imposer-settling` for `IMPOSITION_SETTLE_MS`, and every derived frame crosses to its new place instead of teleporting. The duration is one number, written onto the container as `--tugx-imposer-settle-duration` and read back when timing the settle, so overriding it there retimes both. The vocabulary is the printing industry's, chosen deliberately: *imposition* is the arrangement of pages at their correct positions on the press sheet. It is also forced — "layout" is the layout tree and the tugbank domain, "position" is the pane rect's origin. `tugdeck/src/lib/layout-imposer.ts` (`resolvePlacement` / `travelFraction` / `imposeStyle` / `imposeSidebarStyle` / `imposeRect` / `resolveSpan` / `isSidebarPinned` / `allocateSidebarWidths`), `layout-tree.ts` (`imposition` / `slot?` / `widthPreset?`, invariant 6: at most one pane per sidebar componentId, and it carries no slot), `deck-store-selectors.ts` (`findSidebarPanes`), `deck-manager.ts` (`setImposition` / `setSidebarSide` / `setContentWidth` / `setPaneWidth` / `pinLens` / `_unpinSidebar` / `assignCardToSlot` / `movePane` `evictSlot` / `arrangeCards` / `centerPane`), `components/chrome/tug-pane.tsx` (the pinned and imposed style branches, DOM-seeded drag conversion), `components/chrome/deck-canvas.tsx` (the `move-to-slot` handler), `components/tugways/keybinding-map.ts` (⌘1..⌘9), `components/lens/sections/layouts-section.tsx`, `components/lens/layout-miniature.tsx`, `components/lens/slot-picker.tsx`. **D128.** **The layout system speaks two card roles — content and sidebar — and content cards have three named widths.** A registration declares `layoutRole: "content" | "sidebar"` (`card-registry.ts`), defaulting to content. **Content cards are the ones the deck arranges**: they take N-Up slots, answer ⌘1..⌘N, and follow the width presets. **Sidebar cards pin to a deck edge and inset the band the content cards live in** — the Lens and Jots, and whatever registers next. A sidebar takes no slot, is skipped by `arrangeCards`, is refused by `assignCardToSlot`, and carries a `{ side, pinned? }` entry in the imposition record ([D121]). The taxonomy **constrains the layout system; it does not sort every card into two boxes** — the utility cards (settings, keyboard, devtools, gallery, about) declare nothing and are arranged like anything else. This was a *promotion, not an invention*: every piece of it already existed as a Lens-shaped special case (`findLensPane` matching one componentId, `imposition.lens`, `imposeLensStyle`, an allocator with one unknown), and lifting Snippets out of the Lens as its own card is what forced the special case to become a declared trait. **Both edges can carry a rail, and one edge can carry two cards.** Same-side cards **share a rail and stand front-to-back in it**, exactly as two panes sharing a slot do: same pin, same width, same full vertical run, with z-order deciding which one you see and the title bar's stack badge and picker ([D123]) the way to the other. That makes a rail a *place* in the same sense a slot is, which is the whole of why the badge applies to it unchanged. Rails hold a z-band above the free panes (a rail is never occluded by a card) and below the overlay base (or it would bury its own menus); inside the band the members take the deck's array order, so `activateCard` raises one over the other. **Dividing the rail's height between the members was tried first and rejected**: it spends a rail to show two half-cards, which is what the Jots section was already doing *inside* the Lens, only less space-efficient — and the point of lifting Jots out was to give it a whole rail when it is the one you are looking at. The design that lost persisted a seam split and a per-card vertical order; the one that shipped persists neither, because front-to-back has nothing to remember but each card's side. This matters out of the box rather than in a corner: the shipped default puts both Lens and Jots on the right, so the stacked rail is the deck a user meets. **When imposition takes or grants rail space, every visible rail lands on ONE shared width** — never a per-rail solve, so the deck cannot answer with two rails at two widths; sidebars are a uniform class the way content cards are. The shared width may grow to the **slim** content width (675) and no further, whatever Card Width the deck is set to — a rail is a reading surface, and a comfy- or wide-sized sidebar is absurd on its face — and may shrink to a fifth under the width the user chose, floored by the tightest `sizePolicy.min` among each rail's stack members. The chosen width the shrink allowance hangs under is the card's **durable** stored width (`lensStore` for the Lens, `sidebarWidthStore` for every other sidebar), never the live pane width: the live width is where the allocator writes its own answers, and an allocator that reads its output back as the user's preference re-anchors on every solve and ratchets one rail wide. The fifth-under shrink is the SOFT allowance and the refusal on a failed fit is no longer absolute — [D136] grades the licence: crowding deepens the shrink to the hard floor, and an untileable solve still moves the rails as far as visibly helps. **Every Layouts click re-solves**, Card Width included — restamping the content panes moves every seam, so `setContentWidth` runs the same retune the kind rows run — and so does a card JOINING the chain ([D136], narrowed by [D140]: a card already in the chain moving between slots does not). **The widths are slim 675 / comfy 800 / wide 1230**, named constants in `layout-imposer.ts`. Slim is the reading width the Session card's chrome was put on a diet to reach and is therefore also its floor — a card that could go narrower than the narrowest width the deck offers would have a floor no gesture can reach. A preset is applied by a command through `movePane` and held between the pane's own `sizePolicy.min` and `max`, because `movePane` writes the rect it is handed without clamping and a card can beat a preset in either direction (Settings' 720 floor, About's 320 lock). The stamp (`TugPaneState.widthPreset`) records what the user chose even where the card's bounds won, and **any manual resize clears it** — a settled control shows what the geometry holds. Two doors: the **title-bar popup** sets one pane, and **Card Width** in the Layouts section sets the deck's default and puts every content pane on it at once, overwriting per-pane deviations. That asymmetry is the design — you say how wide content reads here, then dissent on the one card you want narrow — and it is why re-choosing the width the deck is already at is a real gesture rather than a no-op. A card registered with `takesContentWidth` opens at the deck's width instead of a number frozen into its registration. The **window-shade collapse was removed outright** to make room for the popup in the title bar: it was pointer-only — no command, no chord, no menu item — and old blobs carrying `collapsed: true` deserialize with the field dropped and the pane expanded. `card-registry.ts` (`layoutRole` / `takesContentWidth` / `isSidebarCard`), `lib/layout-imposer.ts` (`sidebars` / `contentWidth` / `maxRailWidth` / `CONTENT_WIDTH_*_PX` / `resolveContentWidthPx` / `allocateSidebarWidths` / `imposeSidebarStyle`), `deck-manager.ts` (`setSidebarSide` / `setContentWidth` / `setPaneWidth` / `retuneSidebarAllocation`), `components/lens/sections/layouts-section.tsx` (the three axes, sidebar controls built from the registry), `components/chrome/tug-pane.tsx` (the width popup). ## Selection

**D34.** Three-layer selection containment: CSS `user-select: none` baseline, `SelectionGuard` runtime clipping, `data-tug-select` developer API. [L12]

**D35.** `SelectionGuard` is a module-level singleton, not React state. [L01, L12]

**D36.** Pointer-clamped selection uses `caretPositionFromPoint` (with `caretRangeFromPoint` fallback). [L12]

**D37.** Four select modes via `data-tug-select` attribute: `default`, `none`, `all`, `custom`. [L12]

**D38.** Cmd+A scoped to focused card via responder chain `selectAll` action. [L12]

**D122.** **The element marks; the container does not — and the element mark rides Accent while the selection fill rides Key.** Two cross-component rules, recorded together because the second is what keeps the first safe. (a) An **item-group container** — `TugListView`, `TugAccordion`, `TugRadioGroup`, `TugChoiceGroup`, `TugOptionGroup`, `TugTabBar`, `TugTabView`'s sidebar — marks keyboard focus with **nothing on the container**. The whole treatment is the mark on the **cursor item** inside it: a **ring** at full accent on an inline chip, a **leading-edge bar** at full accent on a full-width row. The container is `data-key-view-kbd`, so the global leaf-ring rule would stroke it; each component suppresses that with `outline: none` on its own root at one-class-plus-one-attribute specificity, and names `data-key-within` in the same selector. **Three container marks were tried first, and the record is the point.** (1) A full-accent perimeter: a bright rectangle around a bright ring, two questions in identical vocabulary at two scales, and the eye reads the big rectangle before the small one — backwards, since the cursor is what the next keystroke acts on. (2) A background wash, the two-*kinds* answer, so neither question competed; better on paper and it lost to the surfaces, because an area mark is a colour laid over a whole region and at any strength that reads it also tints every pixel of content sitting on it — brown over a mid-tone sheet, grey-tan over a pale one, each correction toward one surface degrading the next. (3) A toned, thicker stroke against a brighter, tighter element one, separating by *degree*; it shipped and still read as two rings, because tone is not enough separation between two closed rectangles a few pixels apart. The fourth answer is to stop drawing it: what all three were buying was "which container holds the keyboard", and an element mark *inside* the container already answers that. Retiring it also retired the machinery — `TugListView`'s perimeter needed a sticky overlay child, a JS-measured scrollport height and scrollbar width, a two-layer band split by the scroller's clip, a z-index lift, an inner-overlap offset the cursor caret had to read, and a carry-suppression rule, none of which has a subject now. The shape of an element mark follows the shape of the item: full-width row containers (list, accordion) mark the cursor with the bar (`--tugx-focus-cursor-bar-*`, a language-level knob precisely because two components draw it — one component reading the other's slot would breach [L20]); inline chip groups mark it with a ring. The bar is the loudest mark on the surface by design, and its trailing edge comes to a shallow point at the item's mid-height (`-point`) so it reads as an indicator aimed at the row. **The element mark is now the sole focus indicator an item-group has, which makes one registration rule load-bearing:** a group with nothing to cursor must be refused the focus group (the Lens sections gate theirs on `navigable`, the post-filter row count), or it takes the keyboard and paints nothing — a WCAG 1.4.11 failure. That constraint got stricter with this decision, not looser. A selected row still paints its own opaque ground (`--tugx-list-row-ground`) even though nothing paints behind the rows any more — the rule that a selection wins the pixels it covers is general, and the next thing to paint behind a row will find it settled. (b) The focus mark resolves from the **Accent** axis and a committed selection fill from the **Key** axis, and any new theme must keep the two distinguishable. This was already true everywhere — accent is orange in all six themes, the "on" selection token is cobalt in `brio` and blue in `harmony` — but it needed writing down, because the natural move for someone tuning a focus mark is to reach for the selection hue "so it matches." A role-bearing group overrides both from its own role token, keeping them distinct within the role. Full doctrine and the engine-attribute contract: [focus-language.md](focus-language.md). `dash/archive/focus-language-wash.md` [P01]–[P10] records the superseded wash design. [L06], [L20]

## Scroll Behavior

**D93.** Smart auto-scroll for dynamic content uses a six-phase state machine — not scroll-event guessing. `SmartScroll` (a standalone class, not a React hook) owns a scroll container element and tracks six mutually exclusive phases: `idle`, `tracking`, `dragging`, `settling`, `decelerating`, and `programmatic`. The phase is the guard: if the phase is `dragging`, `settling`, or `decelerating` and scroll direction is up, a user is scrolling — disengage follow-bottom. A scroll change is ours only while the phase is `programmatic`, or in `idle` with the post-programmatic one-shot suppression armed for that event; any other `idle` scroll belongs to the **user** — chiefly the native scrollbar, whose thumb drag delivers no pointer or wheel events — and an upward one outside the at-bottom band disengages follow-bottom, while one landing inside the band re-engages it. The full attribution inventory and the supersede rules live in [scroll-intent.md](scroll-intent.md).

**Amended: "any other `idle` scroll belongs to the user" excludes machine-authored displacement that the owning component has identified as its own.** The browser clamps `scrollTop` when the scroll maximum shrinks, and a clamp is shaped exactly like a user scrubbing up — one `scroll` event, no pointer, no wheel, phase `idle`. Where a component can *prove* it caused the movement, treating it as intent converts machine noise into a user decision, and intent is sticky: a single clamp used to end follow-bottom for the remainder of a session. `TugListView` brackets its own commits, and a displacement it detects is attributed via `SmartScroll.noteExternalWrite()` — which syncs the baseline and advances the write counter, so the still-undelivered `scroll` event arrives explained and both disengage rules pass it over. Where no component can prove authorship, the original rule is unchanged and the user still wins.

**Amended again: the clamp is prevented, not repaired, and the bracket is a pure witness.** The clamp fires synchronously at **renderer removal, inside React's mutation phase** — no reader forces it and no scroll API can witness it — which supersedes the earlier "forced layout in the commit-phase gap" model and with it the earlier remedy. The defense is constructive: an extent floor (`.tug-list-view-floor`, written by the commit bracket to the settled extent every commit, up or down) holds the scrollable extent across the mutation gap so there is nothing to clamp against, and a lowering is a *declared rebase* that pins its own clamp and records it. The bracket no longer repairs: an unexplained displacement is counted, traced, and logged at **warn**, and the position is left exactly where the browser put it — a record means the floor has a hole, which is a bug to fix rather than a symptom to counter-write. `notifyRepair`, the repair suppression, and the `repaired` / `priorRepairHeld` fields are deleted. See [scroll-intent.md](scroll-intent.md) for the evidence, the floor's rules, and the witness contract.

Growth pins remain **phase-invisible** by design — `pinToBottom` writes `scrollTop` directly and deliberately stays in `idle`, so the phase machine still reports the user's state rather than the pin's. They are now **counter-visible**: `pinToBottom` advances `programmaticWriteSeq` on the branch that actually assigns, which is what lets the displacement bracket exempt a pin whose deferred `scroll` event has not been delivered yet. The counter counts writes that moved the scroller, not calls — advancing it on `pinToBottom`'s already-at-max early return would hold the exemption open across most streaming commits and blind the bracket exactly when the transcript is most active.

Phase transitions are driven by six DOM listeners: (1) **`scroll`** on container — fires callbacks and drives re-engagement check; (2) **`scrollend`** on container — terminal signal for deceleration and programmatic animation, with 150ms timer fallback for browsers without native support; (3) **`pointerdown`** on container, **capture phase** — enters `tracking`; (4) **`pointerup`/`pointercancel`** on document — exits `dragging` into `settling` (a 50ms window to detect momentum); if scrolls arrive within 50ms, transitions to `decelerating`; if not, transitions to `idle`; (5) **`wheel`** on container, **capture phase** — skips `tracking`, enters `dragging` immediately, starts scrollend fallback timer, disengages follow-bottom on `deltaY < 0`; (6) **`keydown`** on container — all scroll keys (PageUp, PageDown, Home, End, ArrowUp, ArrowDown, Space) enter `dragging` immediately and start the scrollend fallback timer; only scroll-up keys (PageUp, Home, ArrowUp, Shift+Space) disengage follow-bottom.

The two intent listeners run at **capture** so a user disengage is recorded synchronously ahead of every descendant listener of any phase — one that stops propagation (the Cmd-wheel inner-scroller route, [D94]) or one that flushes a commit whose layout effects pin to the bottom. `keydown` deliberately stays at the bubble phase: a key a descendant control consumes is that control's key, not scroll intent, and bubble semantics are exactly that filter. Capture registrations take capture-matched removals in `dispose()` — an options mismatch leaves the listener attached.

The `settling` phase is explicit state: `isUserScrolling` returns true during `settling` (pointer released, momentum outcome pending). The `_scrolledAfterPointerUp` flag pattern is replaced by an actual phase.

Content auto-scroll is **controller-driven**: `TugMarkdownView.doSetRegion` checks `isFollowingBottom` and calls `scrollToBottom()` after content updates. `SmartScroll` has no `ResizeObserver` — it does not observe content changes. Architecture studied from `use-stick-to-bottom` (StackBlitz Labs, MIT — see THIRD_PARTY_NOTICES.md). [L03, L06, L07]

**Scroll anchoring is gated by follow-bottom.** (This replaces "`overflow-anchor` is not used" — WebKit does honor it, and the transcript's reading-position hold depends on it.) Anchoring holds mid-viewport content still when heights change above it, which is definitionally opposed to the pin: while following, the live edge *is* the position and the pin is the only writer entitled to hold the viewport anywhere. `SmartScroll` stamps `overflow-anchor: none` on its container at the follow-bottom transition chokepoint and clears it on disengage, so descendants' opt-in goes quiet while engaged and resumes the moment the user parks to read. An inline style, not a class — the gate belongs to following-the-bottom itself, so every consumer gets it without per-surface CSS. [L06]

**Follow-bottom's polarity**: engaged is the resting state; disengaging requires a direct user action or a user-requested machine scroll that declares itself; re-engaging requires attributed arrival at the bottom. A machine scope that disengaged (an inline dialog's) may not simply restore the flag it suspended at close — it consults `isSettledAtBottom` (the user's position judged against the live geometry *or* the geometry they were last shown, the same judgment behind `growth-at-bottom-reengage`) and engages only if the user never left.

**D94.** **Cmd/Ctrl-wheel bypasses inner block scrollers and routes the wheel delta to the outer scrollport.** Inner block scrollers (FileBlock's CM6 scrollport, DiffBlock's hunks region, TerminalBlock's virtualized scroller, future code-fence viewers, future JSON-tree blocks, future structured-result panels) capture wheel events while the cursor sits over them, which stutters the outer card-scrollport skim across long transcripts. The escape hatch is surface-wide: **holding Cmd (macOS) or Ctrl (Win/Linux) while wheeling routes the delta straight to the outer scrollport, regardless of cursor position.** Plain wheel (no modifier) preserves current behavior — inner captures until exhausted, then bubbles to outer.

Mechanism: `useOuterScrollOnModifierWheel({ innerRef, outerScrollportRef })` (and its imperative twin `attachOuterScrollOnModifierWheel(inner, getOuter)`) attaches a capture-phase, non-passive `wheel` listener on the inner scrollport. On a Cmd/Ctrl-modifier hit, the handler calls `preventDefault` + `stopPropagation` and forwards `event.deltaY` to the outer scrollport via `scrollBy({ top, behavior: "auto" })`. Outer scrollport is read on every event so context-driven node swaps land without re-attaching. The hook is registered in `useLayoutEffect` so wheel routing is live before the first paint a user could plausibly wheel against.

The contract is surface-wide, not body-kind-specific: any new inner scroller a body kind introduces opts in by calling the hook with its inner-scroller ref. The same mechanism applies to pane-scoped scrollers and modal scrollers when those grow into the pattern. Cmd-click (new-tab), Cmd-+/- (browser zoom), Shift-wheel (browser-native horizontal pan), and Alt-wheel are unaffected — the listener is wheel-modifier-specific and intercepts only the Cmd/Ctrl axis.

**Bash render-on-scroll-into-view recovery.** TerminalBlock's virtualized scroller occasionally paints empty when the outer card scrolls it into view — a WebKit layer-invalidation hiccup or an IntersectionObserver-style virtualizer missing the first paint while the outer's clip rect is settling. The fix is a symptom-targeted refit: TerminalBlock subscribes to its outer scrollport via `IntersectionObserver` (root = outer scrollport, threshold 0) and re-runs the virtualizer's `applyUpdate(scrollTop)` on every entering-view transition. A `scroll` listener on the outer (gated on `inView`) covers sub-IO-threshold deltas. Refit is idempotent when no enter/exit ranges change, so spurious fires are free. [L03, L05, L06, L22]

The block carries no tool NAME (the `Shell` row identity already names it; a repeat would be redundant, unlike a `Bash` block under the shared `Code` identity). **Persistence + restore ([P07]):** every settled exchange is recorded to a per-session `ShellLedger` (`shell_exchanges.db`, capped 500/session, oldest evicted) beside `sessions.db`; a Maker ▸ Reload / relaunch re-fetches via the `list_shell_exchanges` → `list_shell_exchanges_ok` CONTROL pair (never feed replay) and mints each row keyed `restored-<sqlite-id>`, interleaving by the exchange's `started_at_ms`. **Interleave is one-directional by design, and the reason is empirical:** shell turns upsert into the append-ordered Claude spine by timestamp (`upsertShellTurn`), and a Claude append slides past trailing shell turns the restore seated ahead of it (`appendTurnInterleavingShell`) — but the Claude stream itself is NEVER timestamp-sorted, because the real on-disk JSONL corpus is ~39% non-monotonic in entry timestamp (sidechains, `--continue`/`--resume` merges, and compaction re-insert older stamps mid-stream). JSONL arrival order is the source of truth for Claude turns; timestamp is a reliable key only for shell turns (a ledger `started_at_ms`) and genuine user submissions (a `submitAt` from the JSONL) — exactly the pair the interleave sorts on. **The interleave also holds for submissions that have not committed yet:** an in-flight turn and the queued-send ghosts live outside the committed transcript, so the row layout merges the transcript's trailing shell rows INTO that pending block by timestamp (`composeRowLayout`), under the same rule the commit will apply — otherwise an exchange the user ran *after* hitting submit paints above their own message for the length of the turn and then jumps. A queued send is stamped when the user submits it, not when the queue flushes (`QueuedSend.queuedAt`), so the shell rows run during its wait stay below it permanently. **Claude never sees a shell exchange implicitly ([P08]):** the only path into Claude's context is the on-demand **Add to context** toggle on a settled exchange row — it composes a fenced `command + output + exit` block (oversized output truncated at a line boundary; the fence lengthens past any backtick run) and stages it on the pending-context queue, where it rides the next `❯` submission as attributed `#s{n}` context. Never auto-sent, and a second click un-stages it. **One gesture, one glyph:** `cloud-upload` marks add-to-context everywhere it appears (shell rows and the `/btw` overlay alike), going `check` while staged. The earlier **Share** affordance — a second, redundant path that seeded the composer directly — is retired along with its `requestShare`/`consumePendingShare` slot; two ways to do one thing is what made the header read as a cluster of near-synonyms. **Richness accretes without a rewrite:** shell rows resolve their renderer through a command-block registry on the [D101] grammar (`session-command-block-registry.ts` — `registerCommandBlock(name, matcher, renderer)` / `resolveCommandBlock(command)`, total default to the generic exchange block, throw on duplicate name); no bespoke renderers ship (`git status` / `ls` / build-progress blocks are follow-ons, [P05]). App-tests: `at0215` (route chrome), `at0216` (exchange e2e + restore interleave). Probe: `tugrust/crates/tugcast/probes/shell-exec/FINDINGS.md`. Originating plan: `dash/route-enhancements.md` ([P04]–[P13], Milestone M03). [D97], [D101], [D108], [D110], [L02], [L06], [L26]

## Dev Prompt Entry

**D98.** Host facts — the backend's network `hostname` and the basename of its login shell — are resolved by tugcast and served at a read-only `GET /api/host` endpoint, then read into tugdeck's `HostFactsStore` through `useSyncExternalStore`. The browser cannot know the backend's real hostname or `$SHELL` (`window.location.hostname` is only the URL host), and the facts are static for a server's lifetime, so the store fires the fetch exactly once and caches the result. The endpoint is loopback-restricted like the other `/api` handlers; the response shape `{ hostname, shell }` is a cross-stack contract, pinned by a Rust serialization test and a `bun:test` parser test. A failed or pending fetch leaves the store empty, and consumers treat an empty snapshot as "not yet known." [L02]

**D99.** Each Dev prompt entry owns a `RouteLifecycle` — a per-prompt-entry pipe that holds the authoritative command route (`❯` Code / `$` Shell) and announces every change. It offers two surfaces over one fire path: a store surface (`subscribe` + `getRoute`) that renderers read through `useSyncExternalStore` ([L02]), and a synchronous delegate/observer surface (`observeRouteWillChange` / `observeRouteDidChange`, `useRouteDelegate`) for imperative reactors. The route is no longer component `useState`: once it has a consumer outside the component that owns it, it is external state and must enter React through `useSyncExternalStore`. Unlike the deck-level `CardLifecycle`, `RouteLifecycle` is scoped per prompt entry, provided through `RouteLifecycleContext`, surfaces a single `(prev, next)` will/did pair, and dispatches synchronously — route consumers re-render content and have no gesture-focus-lock hazard, so there is no `MessageChannel` drain. See [route-lifecycle.md](route-lifecycle.md). [L02], [L03]

## Onboarding & Setup

**D106.** ConfigureTug — the app-modal onboarding wizard (`configure-tug.tsx`, [#step-9] of `dash/onboarding-and-install.md`) — renders as an ordered list of **step rows**, each a **bespoke row** (not a transcript `BlockChrome` [D104]): a left-hand `TugProgressIndicator variant="pulsing-dot"` whose role+state encode the step's lifecycle ([D02]), a requirement/direction **label**, a **detail** line carrying state/progress/completion, and an optional **CTA**. The block shell was evaluated and rejected for this surface — its tool-name/result-summary/copy/chevron affordances are transcript baggage a setup step does not want; the bespoke row keeps the wizard's own rhythm. A step's status is one of `pending | active | busy | error | done`, mapping to the dot as: `pending`→`inherit/stopped` (row dimmed), `active`→`action/running`, `busy`→`agent/running`, `error`→`danger/aborted`, `done`→`success/completed`. The pulsing dot is the *only* role tone on the row; the label/detail inherit panel text ([D104] convention 1 — status is the dot's). The design spike that fixes this surface's copy and rhythm without a clean guest is the **`gallery-configure-tug`** card (`gallery-configure-tug.tsx`), which simulates every state below from local state — it never touches the real `authStore`.

**Flow.** Four steps, each gated on the one before, fed by the app-level `authStore` ([L02]), the `claudeVersionStore` version pair, and the deck card count:

   Sibling app-modal (wins):       VERSION TOO OLD → TugVersionGate ([#step-7])

**Per-state copy (what we show & say).** Label is the requirement/direction; detail is the state/progress/completion line. A `busy` step keeps a **disabled** CTA (not hidden) so the row doesn't empty out; a `done` step swaps the CTA for a green success check (✓) — **unless it carries an offer anyway** (the installed-but-behind row), where the outlined CTA takes the check's slot: the dot already says settled, and a check beside an Update button would be two answers to one question.

**Version, and updating.** Step 1 carries the whole life of the install, not just its presence. `check_claude_version` (sent beside `check_auth` at launch/reconnect, and again on an on-demand open — a launch-time answer goes stale) answers `claude_version_result {installed, latest}`: `claude --version` locally, and the **stable release channel** (`downloads.claude.ai/claude-code-releases/stable`) for what is on offer — the same channel the installer lands, so "up to date" means up to date with what pressing Update would do. Either half may be `null` (no CLI, no network) and the row then says only what it knows; the Update CTA appears only when both are known and `compareVersions` proves the local one older, so a locally built or ahead-of-channel `claude` never reads as behind. **The updater IS the installer** — the official installer always lands the newest stable build — so `update_claude` reuses the install shell-out and differs only in what the row says. A successful update stays `busy` until the version re-probe lands, so the row never flashes the old version back as if nothing happened. State lives in `claudeVersionStore` ([L02]), deliberately apart from `authStore`: the picker gate and per-card banner read auth and have no business re-rendering on a version lookup.

**Logged out on a configured app.** The Log Out gesture (and any relaunch with the login revoked) reopens this wizard with **only steps 1 and 2**. The directory is already chosen and the session step is answered by the deck the user is returning to, so the other two rows would be settled state the user cannot act on while logged out — the wizard shows only what it is actually asking. The condition is a stored default project directory plus a logged-out state; a genuine first run (nothing stored) still gets the whole checklist.

## Changesets & tugdash

**D112.** **Attribution is recorded at the point of change, never reconstructed — and it records provenance only, never judgments.** File authorship for a session is captured in a `file_events` table in `sessions.db` from tugcast's `agent_bridge` relay loop — the one supervised point every tool frame already flows through. Write/Edit/NotebookEdit attribute exactly from tool inputs on a successful `tool_result` — with the row's `project_dir` resolved **per file** from the file's own directory (worktree-aware `file_repo_root`: repo membership is a per-file fact, never the session's project dir, which misfiled every dash session's worktree edits as `.tug/worktrees/…` under the main checkout, invisible to every reader — and a file belonging to **no** repo is not recorded at all, since the fold matches only git's repo-relative dirty paths and such a row could never surface anywhere); `Bash` needs working-tree fingerprint bracketing (snapshot on `tool_use`, delta on `tool_result`); and the **turn-scoped fallback bracket** (`origin='turn'`, `tool_name='Turn'`) snapshots on the `user_message` forward and takes the delta on that turn's non-replayed `turn_complete`, attributing any path no exact/per-call-Bash row already covered — closing the capture gaps a per-call Bash bracket structurally cannot (its pre-snapshot racing a fast command, or a relay crash mid-Bash within a live turn). **All brackets are relay-local**; there is no cross-session bracket registry, and no capture path ever observes or marks another session. The retired alternative — a shared registry cross-marking rows `ambiguous` on repo-root + wall-clock overlap between sessions' brackets — was wrong twice over: unrelated concurrent commands on one checkout false-positived constantly (with several session cards open, essentially everything went ambiguous), and the hazard it aimed at (two sessions writing the same file, each bracket catching the other's delta) *always* manifests as both sessions holding rows for that path anyway. The correct signal is therefore **per-file contention, computed at read time**, and gated on proof: a file is `shared` iff two or more sessions hold **live proof rows** (`exact`/`replay` — the tool input names the file) for that exact repo-relative path. Proof decides ownership; `bash`/`turn` bracket rows are a whole-tree fingerprint *delta* that cannot separate this session's writes from a concurrent save, build churn, **or the user's own hand-save in their editor** (which belongs to no session and can never be claimed back) — so correlation never decides any bucket, **not even for the bracket's own session**: a bracket-only file stays `unattributed`, tagged `likely this session's (bash bracket)` as a hint, and inclusion is the same explicit disposition as any other unattributed file. (Each weaker rule reintroduced the bug through a side door: "any row = authorship" let two sessions' `cargo`/`git` brackets sweep up each other's saves so everything went `shared`; "a bracket attributes its own session when no exact owner exists" would let an agent's bracket auto-commit the user's inflight hand-saves.) A row is live only while it postdates the last commit that touched its path (a commit *spends* the rows it absorbs — a fossil row neither attributes nor contends when the file is re-dirtied later; ties break toward spent, degrading to `unattributed`, visible). The legacy `ambiguous` column remains in the schema but is always written 0 and read by nothing. The ledger itself is **machine-global**: one `changes.db` (`tugcore::instance::changes_db_path()`, independent of `TUG_INSTANCE_ID`; `TUG_CHANGES_DB` is a test-isolation override) attached by every instance's `SessionLedger` — the working tree is machine-global, so per-instance attribution splits the truth (a second app instance on the same checkout saw the first's work as ownerless and its card pre-selected the lot; both halves are fixed — shared ledger + unattributed-defaults-off). All three source rules (exact, `bash`, `turn`) hold the same invariants: point-of-change capture, an upsert keyed `(tug_session_id, tool_use_id, file_path)` so replay/resume converges idempotently, and attribution failures never affecting frame delivery (degrade to "forward unchanged"). Shared rows are excluded from every default commit set (the card's selection and `tugutil commit` alike, opt-in via `--all`/`--tree`/`--paths`) — one session's commit never silently sweeps another's file. The commit *read* side treats no row as a gate: `tugchanges-core`'s join is inverted so `git status` is the universe and the ledger annotates it (a dirty file is never invisible; see `dash/commit-tool-fixes.md` [P01]–[P05]). Full doctrine: [tracking-changes.md](tracking-changes.md). `dash/changesets-plan.md` [P01]–[P06], [P15].

**D113.** **The changeset surface is a process-level aggregate feed, not per-workspace.** `CHANGESET_ALL` (a single process-level snapshot watch, the `spawn_stats_feeds`/`defaults` pattern) aggregates every open project into one `WorkspacesChangesetSnapshot` delivered to every deck, because tugdeck's `FeedStore` holds one value per feed id — a second project's frame on the same id would overwrite the first, so aggregation must be server-side. The project set is exactly the current `WorkspaceRegistry` entries (one per project with a live session card); non-repo dirs surface with an "Initialize git" affordance rather than being skipped. The retired per-workspace `CHANGESET` (0x23) stays reserved, never reused. The card retires the old Git card entirely. `dash/changesets-plan.md` [P09], [P16], [P17].

**D114.** **Dash is its own tool, `tugdash`, not a `tugutil` subcommand.** The worktree-isolated work-unit engine lives in `tugdash-core` (library, callable from tugcast) with a `tugdash` CLI over it (`create`/`commit`/`join`/`release`/`list`/`show`), so the Changeset card drives create/commit/join through the same code as the CLI. A dash *is* a `tugdash/<name>` git branch plus a worktree under `<repo>/.tug/worktrees/<name>` (auto-migrated from the legacy `.tugtree/tugdash__<name>` when clean and unheld); its base branch and description live in git config, its activity in the per-project append-only dash-log — there is no database. `tugutil dash` is deleted; the tugplug skills and docs speak `tugdash`. `dash/changesets-plan.md` [P12], [P13].

**D115.** **A conflicted join is a graded resolution ladder ending in a review-gated AI rung, never a dead end or a hand-off.** `tugdash-core`'s `join` builds the integration commit **off to the side** (`merge-tree --write-tree` stages → resolved blobs → `commit-tree` on the base → staleness-guarded fast-forward), so no checkout is ever half-merged and abort is free. Conflicts escalate: replay probe (round-by-round in-memory replay; a clean replay lands as linear rounds, shape change accepted) → `rerere` (enabled by default; replays recorded resolutions, and the ladder records its own driver/AI resolutions) → per-file `merge-file` → a PATH-discovered structured-merge driver (mergiraf by default, never bundled — AGPL) → the AI rung. The AI rung ([P32]) is a headless per-file scribe merge (base/ours/theirs + the dash's maintained draft as intent) on the existing `ScribeSpawner` seam, deterministically validated marker-free, streamed to the card as a `/btw`-style overlay — **never a Session card, never auto-committed**. The card reviews the pre-built candidate (resolved files badged by rung) and lands it on explicit confirm; non-content conflicts (delete/modify, binary, mode) short-circuit to honest "unresolved". `dash/changesets-plan.md` [P14], [P31], [P32]. [D114]

**D116.** **Every change lands through one lifecycle — Preflight → Draft → Land — and landing is the user's act, from the prompt entry.** The consolidation over [D112]/[D113]: buckets and rounds gather truth; an editable, durable, **machine-global** Draft (message + selection dispositions + edited-provenance in `changes.changeset_drafts` — the same scope axiom as `file_events`) proposes the landing; and the prompt-entry verbs **`/commit`** (main lane, two-beat: draft on the first beat, land on the second) and **`/join`** (dash lane, preview → squash with the join draft as message) execute it. The Changes shade — a modal `TugSheet` presentation over the transcript region with the prompt entry live beneath it — is where drafts are reviewed and edited (`TugMessageEditor` on the `TugTextEditor` substrate; the composer IS the display); an `edited` draft is never machine-clobbered (the shade's confirmed Regenerate is the only overwrite path). Landings are idle-gated at dispatch AND at the affordance; drafting stays live mid-turn. Skills draft, humans land: the `draft` skill (né `commit`) authors via `tugutil draft set` and never commits; `implement` ends by writing the dash's join draft and pointing at `/join <name>`; Claude's built-in `/commit` is shadowed dead by the local verb. Squash is the only join strategy in the UI (merge/rebase stay CLI-expert paths); release is shade-only with a discard preflight, and both join and release clear the dash's draft row so a reused dash name never inherits a dead dash's message. Every landing leaves a non-context receipt in the transcript; History badges joins by the `Tug-Dash:` trailer. The gathering verb is `tugutil preflight` (né `context` — "context" is AI-reserved vocabulary; a hidden alias holds for one release). Full doctrine: [tracking-changes.md](tracking-changes.md) § The landing workflow. `dash/changes-commit-dash-consolidation.md` [P01]–[P17].

**D117.** **The commit route is a `!changes` chip in the composer, orthogonal to the changes glance — the composer IS the message editor.** The realization of [D116]'s "the composer IS the display", refined to a prefix-chip model. There is **one bottom-anchored passive changes sheet** (`TugSheetContent presentation="shade" shadeAnchor="bottom" shadeAutoSize shadePassive`) that rises from the top of Z2 over the transcript (scrim + transcript-`inert`, no focus trap — focus stays in the composer below, [P17]); it is the read-only glance, driven purely by the `ShadeViewController`'s `changes` view. **Two orthogonal axes:** (1) the sheet's *visibility* (card chrome), and (2) the *commit route* — "the composer leads with a `!changes` command chip." The chip IS the route: while present, the prompt entry is the commit-message editor (the payload after the chip is the message), the slash/bang/mention machinery stands down, Z5 swaps to a cancel / auto-message / commit icon rail (the pencil-sparkles Auto-Message guarded by the Replace-message `TugConfirmPopover`), and submit lands the commit (`extractCommitMessage` strips the chip; `matchBangCommandLine` recognizes the same line) instead of sending to Claude. **⇧⌘C** (and `/commit`, `!changes`, Session ▸ Commit…) is the entry: on an empty composer it shows the sheet **and** enters the route (inserts the chip); on a non-empty composer it shows the sheet as a **glance only**, leaving the in-progress prompt untouched; toggled again it hides the sheet and, if the route was active, drops the chip. The session card owns the coupling (`commit-route-controller.ts` no longer knows about the shade); History and the route are mutually exclusive. **D118.** **One row grammar for changed files: `TugChangesList` rows are compact mono `TugListRow`s, every row expands into its diff, and the `/commit` receipt's file list IS a changes list — sha-backed.** The live glance, commit mode, and the durable receipt render the identical row (status letter leading; path + badges content; the monochrome `+N −M` pair, pop-out, and fold cue trailing) — the only differences are the diff source and which affordances are live. **D120.** **A session can *claim* a file — an explicit, intentional attribution act, decoupled from editing.** Changeset attribution has two tiers, and only one claims a file: a **proof** row (`origin: exact`/`replay`) means a tool call named the exact file (Write/Edit/MultiEdit/NotebookEdit); a **correlation** row (`origin: bash`/`turn`) is a whole-tree fingerprint delta around a Bash command, recorded as a "likely" *hint* on the unattributed bucket, never proof (a tree-delta can't tell the session's own write from the user's hand-save during the command, or from another session on the same checkout — `changes.rs::compute_changes`). The gap this exposed: **claiming was welded to editing** — the only way for a session to own a file it touched via `perl`/`sed` (bracket-only) or by hand was to *re-edit it with a proof tool*. `origin: "claim"` fixes that: a third proof origin (`origin_is_proof` on both the writer `attribution.rs` and reader `tugchanges-core/ledger.rs`) that promotes a hinted file straight into the session's entry, written by an explicit claim rather than a side effect of editing. **tugcast owns the write** (tugchanges-core opens the ledger read-only; the aggregate recomputes only on tugcast's process-global bump): the `changeset_claim` CONTROL verb in `agent_supervisor.rs` records one `claim` file-event per repo-relative path via `record_file_event`, then fires `changeset_all_bump`. **Two surfaces, one handler.** The deck sends a `changeset_claim` WS control frame (a **Claim** affordance on each unattributed "likely" row → `ChangesRouteController.claim` → `ChangesetVerbStore.claim`). The CLI (`tugutil claim <paths>`) POSTs `/api/tell {action:"changeset_claim", …}`; `tell_handler` bridges `changeset_*` actions into the same `handle_control` (the single source of truth shared with the WebSocket ingress) under a synthetic client id, since a tell has no connection — gated to the `changeset_` prefix so client-scoped verbs (`spawn_session`) stay off the HTTP surface. Idempotent (re-claiming writes another proof row, composed identically); a self-claim never marks contention. This is the intentional, first-class counterpart to editing — never "write the file to claim it". `feeds/attribution.rs` + `tugchanges-core/ledger.rs` (`origin_is_proof`), `agent_supervisor.rs` (`do_changeset_claim`), `server.rs` (`tell_handler` bridge), `tugutil` (`claim` verb), `changeset-verb-store.ts` / `changes-route-controller.ts` / `tug-changes-list.tsx` (`ChangesFileRow` Claim). [D118], [P03]

**Orphan surfacing — the open-card path is fresh-on-look.** The aggregate composes only projects **open in the `WorkspaceRegistry`** and recomposes only on the process-global bump (the per-workspace FS watcher, ledger writes) — so a working-tree change that lands while no FS event fires can leave the cached snapshot stale ("No changes" while the tree is dirty). Hardening: a side-effect-free **`changeset_refresh`** CONTROL verb fires the same bump (no payload, no reply; emission is diff-suppressed, so a client sees a frame only when the tree actually drifted), and the Session card fires it on **Changes-shade open** (`ChangesRouteController.refresh` → `ChangesetVerbStore.refresh`, wired at the shade-open effect in `session-card.tsx`) — so opening Changes always reflects live working-tree truth. Orphans in a project with **no** open card stay invisible to the UI by design (unwatched, uncomposed); `tugutil claim <paths> --project <dir>` reclaims those headlessly.

**Orphaned bucket — a file stranded on a dead session.** Diagnosis (via the observability endpoint below) corrected the earlier "zero-row/trashed" theory: closing a session does **not** delete its rows (only *trashing* cascades a delete). So a file its author proof-owned stays *owned* after the session closes (`live: false`) — never entering the unattributed bucket — yet no live card surfaces another session's changeset entry, so it falls into a gap and reads as "No changes." Fix: `compose_snapshot` **lifts** a file whose every proof-owner is non-live into a dedicated `orphaned` bucket (`OrphanedFile` carries the dead `prior_owner_name`/`id`); a file any *live* session co-owns stays in that live entry, so a file orphans only when all its owners are dead. The Changes shade renders `orphaned` as a claimable section ("orphaned — claim to bring into this session") with the same per-row **Claim** affordance the unattributed bucket uses. Semantics ([D120] extension, user-locked): closing keeps rows, so re-opening the originating session **auto-re-owns** its untouched orphans (plain composition — a live owner's proof-dirty files show in its entry; a committed/reverted file is spent by the row-liveness rule and won't silently re-attach). But **claim severs the prior owner** — `do_changeset_claim` calls `SessionLedger::sever_file_ownership_except(project_dir, paths, claimant)` to delete other sessions' rows for the claimed paths, so a claimed file is "no longer an orphan, nor owned by the originator." `changeset.rs` (lift + unattributed exclusion), `tugcast-core/types.rs` (`OrphanedFile`, `ChangesetSnapshot.orphaned`), `session_ledger.rs` (`sever_file_ownership_except`), `agent_supervisor.rs` (`do_changeset_claim` sever), `changeset-types.ts` / `changes-route-controller.ts` / `tug-changes-list.tsx` / `session-changes-view.tsx` (orphaned entry kind + Claim).

**Changeset observability.** `GET /api/changesets` (loopback, read-only; `server.rs` → `AgentSupervisor::compose_changeset_aggregate`) returns the live aggregate composed fresh over the registry + ledger — ground truth for "what compose produces right now," independent of emission/diff-suppression. `tugutil host changesets` (`--json` for the full snapshot) prints per-project `changesets`/`unattributed`/`orphaned` counts with each owner's liveness — the tool that pinned the dead-owner gap. `compose_aggregate` also traces per-project counts at debug level. NB: a throwaway `tugcast --source-tree` shares the machine-global `changes.db`, so a live claim through it mutates the real ledger — verify the claim/sever path at the unit layer, not by driving the shared ledger.

**D122.** **The composer has exactly two routes — Prompt and Changes — and the `!` layer is retired with no vestige.** A **route** is defined as *a mode that owns the composer's whole document*. Exactly two things do: typing a prompt, and authoring a commit message. Everything else is either a **one-shot verb** (a slash command — it consumes one submission and leaves you where you were) or lives **outside the composer entirely** (find). The four things previously called "bang routings" — `!shell`, `!btw`, `!find`, `!history` — were verbs wearing a routing's sigil: none ever swapped the document, and calling them routes was the original error. This decision replaces [D110]'s three-recipient group and [D119]'s "commit is a mode, not a bang routing" framing (which was right about commit and wrong only in the company it kept).

**The Z4A group is a view, not a second home for the selection.** `CommitModeController` already swapped the document on enter/exit (stashing the prompt draft in `preCommitDraftRef`, restoring it verbatim, persisting the message through the changeset draft store), so the two-item `TugChoiceGroup` renders `commitActive ? "changes" : "prompt"` and dispatches `SELECT_VALUE` into `enter()` / `exitCommitMode()`. It holds no state, which is what makes every existing entry and exit path — ⇧⌘C, `/commit`, Session ▸ Show Changes, a successful land, Cancel ✕, Escape, the shade's self-close — move the visible tab with zero new code. It is deliberately **not disabled in commit mode** ([D119] disabled the `!` button there): the group is how you leave Changes. **No controller means no group** — `TugPromptEntry`'s `commitMode` prop is optional and the Component Gallery mounts the entry without one, so `Z4A` renders empty there rather than a Changes segment that cannot act. Consequence worth writing down: this quietly makes `CommitModeController` the route selector, which is right for two routes and wrong for three — a third route means lifting the selection into a small route controller with commit mode as one of its values.

**The bang layer retires with no vestige.** `lib/bang-commands.ts` is deleted along with every consumer: the `!` button and its `TugPopupMenu`, the `bangCommandCompletionProvider` and its `"!"` trigger, the ⌃⌘S/B/G/H chip-seed chords and the ⌃⌘C `!changes` alias, `bangCommandSurfaces`, the submit-path `matchBangCommandLine` call, the `isBangCommand` sigil branches in `command-atom.ts` and `slash-commands.ts`, and the `SHOW_SLASH_COMMAND_NOTICE` branch that taught `/shell` → `!shell` (a redirect that pointed the wrong way by the end). Two namespaces with two sigils was a tax paid on every surface — picker, completion popup, chip label, reconstructed command line, help text, unknown-command notice each carried a bang branch. **A leading `!` is ordinary prose again**: `!ls` goes to Claude as text. That is the intended behavior, not a regression — the shell auto-router (`shell-line-classifier`) carries a bare `ls` to the shell, which is a better path than the bang ever was. No notice, no redirect, no deprecation shim: a `!`-specific notice would itself be the vestige.

**`/shell` and `/btw` demote to arg-taking local slash commands**, their surfaces moved verbatim. `/shell <cmd>` is the deliberate override under the auto-router — the classifier decides by default, and a user who knows better can force it, which costs one registry entry and removes the "what if it misroutes" objection to deleting `!shell`. `/btw`'s duplication resolves itself: with the `!` menu gone there is one *place* BTW lives and `/btw` is merely how you *ask* — one feature with two organs, not two doors ([D108] stands unchanged). That place is now the **placard**: the Z2 diet dropped the BTW cell, and the answer surface pops from the top of the Z2 strip, right-aligned to the host card, rather than from a cell of its own. `SideQuestionStore` and the placard body are unchanged — only the anchor moved, and the cell it was anchored to was the widest thing on the row that nothing else needed. **Neither route has a typeable name.** A slash command is a one-shot verb that returns you where you were; a route is a mode you stay in, and the two do not belong in one namespace. `/prompt` could not have worked at all — the Changes route owns the document, so `performSubmit` lands the message verbatim and returns before slash interception, which left it reachable only from the route it already names — and the plan's `/changes`, shipped without a twin, was a half-namespace whose behavior nobody could predict from the other half. Both are gone: the route gestures are the Z4A tabs, ⇧⌘P / ⇧⌘C, and Escape, and `/commit [message]` remains the *verb* (it enters with a seed and is an act of committing, not an act of looking). Every slash command therefore leaves the route alone, which is what keeps "`/` is a typing accelerator" true without making the `/` key itself a route gesture. **`!history` is deleted as a route only** — the History shade, ⇧⌘H, Session ▸ Show History, and the `/tugplug:history` skill are untouched; the route was the unused part, and `/tugplug:history <question>` is a real Claude command that replaces the `!history <question>` variant directly.

**Find lifts out of the composer into a ⌘F bar** (`TugFindBar`, extracted from `TextCardFindBar` — one find face across the deck, over a host-supplied `FindSession`). **Find and Changes are one slot.** Both are modes that take over the bottom of the card, and neither is a shade the other can rise over: opening the bar leaves Changes (through `CommitModeController.leave()`, which persists a typed message the way Cancel and the Z4A tab do), and entering Changes dismisses the bar. **The bar joins the card's focus cycle; it does not bring a walk of its own.** Its four controls — query, options, Previous, Next — are stops in `SESSION_CYCLE_GROUP` at orders **8…11**, between the Z4 toolbar (0…7) and the Z2 status cells, which is exactly where the bar sits on screen (the cycle reads the card upward from its bottom edge). This is worth stating as a rule, because the first attempt got it wrong: **a new surface on a card joins the card's authored order — it never declares a parallel one.** A private group in the base mode "worked" in the sense that Tab moved within it, and was wrong in every way that matters: two orders on one card, no spatial order at all on the new one, and ⌥⇥ walking a set of stops the user could see but not reach.

**Tab splits by the KIND of surface, not by whether it is empty.** This entry used to read "an empty text field spends Tab on movement", with the field handing the gesture to its host to enter the cycle at its own seat. ## Commands & Chords

**D126.** **Which chord a command gets is derived from a modifier algebra, not chosen from what happens to be free.** [L30] made every chord a registry fact, which settled *where* chords live and said nothing about *which* chord a command should get — so the chords accreted, each one taking whatever was near a mnemonic letter and climbing the modifier stack whenever plain ⌘ was already spoken for. That produces a keymap that is a list of memorized facts: unpredictable for a user, and offering an author no way to tell a good grant from a bad one. **Two base tiers and two operators now generate every modifier set in use** — ⌘ the universal tier (verbs any Mac user knows, plus the highest-frequency Tug verbs; digits are places), ⌃⌘ the Tug tier (surfaces, shades, modes, themes, app-specific machinery, anchored by the macOS-conventional ⌃⌘F Full Screen), ⇧ the counterpart operator (reverse/widen/undo), ⌥ the variant operator (same verb, altered object or form) — and every remaining set is a composition with a derived reading: ⌥⇧⌘ both twists ("…as Plain Text"), ⌃⇧⌘ the counterpart of a Tug-tier command, ⌃⌥⌘ the advanced form of one. Plain ⌥ letters (glyph typing) and plain ⌃ letters (the caret's emacs set) are **closed forever**, with ⌥⇥ and ⌃\` grandfathered as non-printing exceptions that would not be granted today. The argument for adopting this rather than inventing something is that it was already half-latent in shipped bindings — ⌘V → ⌥⌘V → ⌥⇧⌘V, ⌘Z → ⇧⌘Z, ⌘W → ⌥⌘W — so writing it down moved nine chords and explained the rest. Six rules ride with it, and the load-bearing two are **pairing** (a ⇧/⌥-composed chord shares its key with the base it twists; a chord with no base to vary is a plain-⌘ or ⌃⌘ candidate, never a taller stack chosen because the short one was taken) and **scarcity** (plain ⌘'s free slots go only to commands hit many times an hour, so the frequency claim is part of the grant). The rest: the arrows exemption (⌥⌘↑/↓ has no ⌘ base because ⌘↑/↓ is composer currency; ⇧ still means "to the extreme"), closed sets stay closed, ⌘. parity, and **menu placement is a chord decision** — a `menuEligible` chord preempts every scoped binding regardless of focus ([commands.md](commands.md), four-layer resolution), so one decision records both the tier and the `menuEligible`/`scope` choice.

**The algebra spends exactly the band [D124] cleared, and re-homes both chords [D124] placed.** That entry deleted ⌃⌘S/B/C/G/H "which is what leaves the ⌃⌘ band free", gave ⇧⌘P to the composer's Prompt route, and moved `cycle-permission-mode` to ⌃⌘P *in both doors* because either alone leaves the menu bar swallowing the chord. The continuity is the point rather than an accident: **Prompt Route moves ⇧⌘P → ⌃⌘P** (route selection is Tug machinery; ⇧ was carrying nothing, since there is no ⌘P base for Prompt to be the counterpart of) and **Cycle Permission Mode moves ⌃⌘P → ⌃⌥⌘P**, debuting the advanced tier — permission modes govern agent autonomy, the quintessential expert feature — and vacating ⌃⌘P is precisely what lets Prompt Route land on its own tier. Both doors move again, for [D124]'s reason. **Show/Hide Changes ⇧⌘C → ⌃⌘C** and **Show/Hide History ⇧⌘H → ⌃⌘H** (shade toggles are machinery; the twins move together), **Generate a Commit Message ⇧⌘M → ⌃⌘M** (still composer-scoped, now joining one mnemonic cluster: ⌃⌘C the shade, ⌃⌘M the message, ⌃⌘A the claim), **Next Theme ⌥⌘T → ⌃⌘T**, and **Insert File ⌘I → ⌃⌘I**, which frees ⌘I from its italic baggage under scarcity. Freed and returned to the pool: ⇧⌘P, ⇧⌘C, ⇧⌘H, ⇧⌘M, ⌥⌘T, ⌘I. Every move is a registry-default edit; **user overrides are untouched and no migration exists**, because an override is a per-command binding list in tugbank where *absent means registry default* — a moved default is exactly the case the override design already absorbs.

**Next Theme's chord enters the registry, because a chord that exists only as a Swift construction literal is invisible to the app that owns it.** `next-theme` carried `menuItemId: "view.nextTheme"` with **no bindings at all** — ⌥⌘T lived solely in `buildMenuBar()`, so the keymap pane could not show it, `resolveChord` could not reason about it, and no user could rebind it. It gains a real binding (⌃⌘T, `menuEligible`, `preventDefault`), which is sufficient on its own: `host-menu-state.ts` publishes a chord claim for a **non-`mirrored`** entry too, since presence in `menuChords()` is what the push tests. Construction literals for all four moved menu items are edited in the same change — they are pre-first-push defaults only, but a cold-start menu bar must never flash a chord the registry no longer holds.

**Claim All ⌃⌘A and Disclaim All ⌃⇧⌘A become registry commands rather than buttons the keyboard cannot reach.** Both are `routing: "first-responder"` with composer-responder-scoped bindings, registered in `tug-prompt-entry.tsx` beside the existing `commit-auto-message` registration under the *same* `commitActive` gate — because raising the Changes shade **is** entering commit mode, and the shade is a **passive** sheet that leaves the composer holding focus, so the composer's responder is where the chords are genuinely live. **Registration and handling live in different components, unlike `commit-auto-message`** (which does both in the composer): these two are handled in `session-card.tsx`, because the card is the only component holding `changesController`, and the chain makes the split work — the composer's responder sits below the card's, so a first-responder action the composer does not claim falls through. The gate is where the surface is; the semantics are where the controller is. **⌃⌘A is deliberately stronger than either shade button.** The shade wires two bulk buttons (claim-all-unattributed and claim-all-orphaned); the chord claims **both buckets at once**, because a single keyboard verb meaning "make everything claimable in front of me mine" is worth more than one that mirrors one button and sends the user to the mouse for the other. The buttons remain the granular path. **The pair is not an inverse on one set** — ⌃⌘A acts on what is *not yet* this session's, ⌃⇧⌘A on what *is* — so ⇧-as-counterpart is carrying "the opposite bulk verb of this shade", not "the same set, reversed"; the algebra promises a shared key and an opposite sense, never set inversion, and this pair is the reason to say so out loud. Both no-op on an empty path list or a pending claim/disclaim round-trip, read non-reactively from `changeset-verb-store`. Bindings are the door, so `lintCommandTable` passes with no `internal` declaration; the keymap pane shows them as scoped, non-rebindable rows.

**⌘. parity is a matcher change, not a routing change.** Five components hand-matched `metaKey && key === "."` even though `cancel-dialog` owns both ⎋ and ⌘. in the registry — `tug-alert.tsx`, `tug-confirm-popover.tsx`, `tug-sheet.tsx`, `tug-placard.tsx`, `tug-editor-context-menu.tsx`. ## Model Work

**D127.** **Auxiliary model work runs on SharedAgents over the user's own subscription, never on a model Tug ships.** Tug's non-conversational model work — pulse intent headlines, shell-command arbitration, and whatever comes next — runs on an app-scoped pool of persistent, job-constrained headless `claude` workers authenticated by the Claude Code subscription the app already requires. **Tug does not ship, download, host, or update model weights.** The retired arrangement was an on-device MLX pack (qwen3-4b): ~2.4 GB resident and 2.28 GB on disk to run a model markedly weaker than the one the user is already paying for, behind a catalog, a downloader, a progress UI, a Configure Tug wizard step, and a second Swift inference backend that existed only to feed it. The subscription is a hard prerequisite of the whole app, so the remote path adds no dependency that was not already load-bearing — which is the argument that makes this a subtraction rather than a trade. **Cost accepted, explicitly:** these features stop working offline, degrading to the absent posture they were already designed to have.

**A SharedAgent is job-constrained by construction, not by convention.** `AgentSpec` names a model and a fixed `&'static [JobSpec]` table; `JobSpec` carries a job's instructions, its timeout, and its slow-mark. **No API anywhere accepts an arbitrary prompt** — `run(job_name, input)` looks the job up in that table, and a caller holding the pool cannot ask it for anything the table does not already name. That is what keeps a shared pool from becoming a general-purpose model endpoint inside the app, and it is why adding a second agent (the Sonnet one) is a second `AgentSpec` over the same machinery rather than new machinery. **Workers are persistent because a cold turn cannot meet the latency contract**: measured against CLI 2.1.222, a cold turn is 2327 ms — more than classify's entire 2 s budget — against 867–989 ms warm. Warmth is the feature; the pool exists to hold it — so **nobody ever waits on a cold start**. A job whose ceiling is shorter than one is never handed a worker that has not answered yet: its turn becomes that worker's warmup and the caller degrades on the spot. Lanes are otherwise warmed ahead of any caller (`ensure_warm`, called on traffic that precedes the job — a card asking for the login-PATH set warms the classify lane), and stay warm across a recycle because the replacement is warmed before the old worker stops answering. Workers recycle at `MAX_TURNS_PER_WORKER` (40) so a transcript cannot grow without bound, reap on idle per class (30 min for classify, whose ceiling cannot pay a respawn; 5 min for summarize, whose can), and respawn no faster than `RESPAWN_MIN_INTERVAL` (5 s) so a persistently failing spawn cannot become a fork bomb.

**Workers carry a job class, and classify never queues behind summarize.** The two jobs have contracts an order of magnitude apart (`CLASSIFY_TIMEOUT` 2 s against a user waiting on a keystroke; `SUMMARIZE_TIMEOUT` 6 s against a background cadence), so a single FIFO would let one in-flight summarize spend a classify's whole budget before it was even dispatched. `JobClass` splits the pool: a classify arriving during a slow summarize gets a same-class worker, never the summarize worker's queue. The rule is one `match` and it is the one thing in the pool a unit test caught wrong — `classify_with_grammar` fell into the summarize lane, which is precisely the collision the affinity exists to prevent, and which nothing but a test would have surfaced.

**A worker is isolated because it runs `claude`, and `claude` is an agent.** `--disallowedTools '*'`, `--strict-mcp-config`, `MAX_THINKING_TOKENS=0`, and a neutral Tug-owned cwd at `base_data_dir()/shared-agent`. The isolation is not precautionary: the unisolated posture *actively misbehaved* in the bringup spike — the worker invoked Bash on a tool-baiting prompt, and with the cwd left in a repo it read that repo's `CLAUDE.md` and appended a decoy token to its answer. A summarizer that inherits project instructions is a summarizer whose output is a function of whatever directory it happened to start in. The neutral cwd also parks worker transcripts under one encoded directory rather than scattering them through the user's projects.

**D131.** **Bullseye is a temporary *presentation* layered over whichever geometry mode a pane already holds — never a fourth stored mode.** The deck could place a card four ways and size it four ways, and still had no gesture for the thing a writing app calls a focus mode: *put the thing I am working on in front of me, at a comfortable column, and push everything else back — for now.* **⌃⌘B** and **Window ▸ Bullseye** are that gesture. Two actions rather than one is now correct for the reason the original gave for one being enough, read the other way: a button can name a Pane the selection is not in, and a chord cannot. The button carries `data-on` / `aria-pressed` from the derived id, so it says what the geometry says.

## Session Identity

**D132.** **A session has one identity, produced by one resolver and rendered by one component family at a declared density tier — led by a live pulsing dot, titled `<name> : <callsign>`, and said in two lines beneath.** Tug named a session seven ways across fifteen surfaces, under five near-parallel precedence rules no two of which agreed: `sessionChipDisplay`, `sessionRowTitle`, `sessionEntryTitle` (a hash-equality *sniff*, which is what a rule looks like once nobody remembers what it was for), and two more in Rust. The 8-char short id was computed independently in three places and stored in none. D132 is [D123] — *a pane's name is one string produced in one place* — applied to the session, and the five rules are deleted rather than reconciled. **`resolveSessionIdentity(sessionId) → SessionIdentity`** is the one producer; **`TugSessionIdentity`** is the one renderer family — `chip` and `line` are its two tier values, and the row and masthead densities are compositions of them (`TugSessionRow`, `SessionMasthead`) rather than further tiers on the component; **no surface composes a `project/tag` string of its own**, which is a grep gate rather than a convention because that is the only form the discipline survives in.

**Two registers, not two formats.** A surface that *is* the session — the masthead, a picker row, a Lens row — renders the identity as typography: no enclosure. A surface that *refers* to a session from foreign context — a Overview ref, a History commit line, the Changes card's orphan hint — wraps the same identity in the **session atom**, a rounded pill. An enclosed chip reads as a link to the thing elsewhere; on a surface that *is* the thing, that reading is a lie. The tier implies the register, so a caller picks a density and never a format.

**The mark is a live pulsing dot, and it is the same mark on both registers.** It says what the session is *doing* rather than what kind of thing it is, which is the one thing a static glyph could never do. `useSessionPhase(sessionId)` is the session-keyed door onto it and returns the flattened phase **key** rather than the snapshot, which is what makes it affordable on a Changes card carrying one citation per row: React bails out unless the *reading* changed. **Unknown liveness reads `idle`, never danger** — no bound card, services not yet constructed, a closed or external row — because red is the error channel and spending it on "we do not know" makes every ordinary closed session look broken. A card that exists whose transport is genuinely offline still reads danger; that is a real failure rather than doubt. Retired with the dot, *do not re-propose*: the **chatbox icon** (`MessageSquareText`/`MessageSquareOff`), which spent a second mark on a job the dot does better, and the **`OFFLINE_PHASE_INPUT` fallback** that painted doubt as danger.

**The title is `<name> : <callsign>` in TWO runs, and which run gives way depends on the register.** A user-supplied name is the user explicitly saying what the session is called; it cannot rank below a callsign Tug minted for itself. The callsign stays visible beside it because it is the permanent citable handle a rename never changes. Under a width squeeze the two registers truncate **differently, by design**: on a *title* surface (the line tier — the masthead, the Lens rows, the picker rows) the callsign is the handle a reader scans a list by, so it survives and the user's name elides; on the *atom* (the chip tier) the user's own words survive and the minted handle elides — the tooltip and every copy path still carry it whole either way. An unnamed session renders the bare callsign, which may then elide because it is the only run there is. `sessionTitleParts` produces the pair; two runs rather than one joined string is what lets them be sized separately, and a filter highlight is painted **inside each run** — joining first would put the ` : ` separator inside a mark and defeat the truncation rule. **No `project/` prefix in title ink.** That prefix is `sessionIdentityLine`'s, and that string is a different channel: the pane-title channel the tab strip, the Window menu, and the slot-stack picker read, which is not a notification path and is documented as **constant for the life of a binding** — changing it would make the tab strip stale on rename. It survives unchanged, and so does the prefix, in the tooltip, the citation, and the telemetry popover. Retired: **`<project>/<callsign>` as one text node**, which was right while the two halves were a path and wrong the moment one of them became the user's own words. **Monospace still belongs to flat text only** — never to session chrome.

**The callsign is immutable and the UUID never leads.** A legacy tagless row degrades to its 8-char short id and **never** to the full UUID. Permanence is not aspirational: `sessions` rows are hard-`DELETE`d by trash, three cascade paths, and cap/age eviction, so a unique index over that table frees a tag when its row dies — and a recycled tag makes a two-year-old commit's citation resolve to a *different* session, which is a confidently wrong answer and strictly worse than an unresolvable one. So an **append-only `minted_tags` table is the all-time arbiter**: every mint path — spawn, fork, external backfill — inserts into it in the same transaction as the row it names, its `PRIMARY KEY` violation is the collision signal a mint retries against, and **nothing anywhere may delete from it** (`no DELETE FROM minted_tags` is a grep gate). `sessions_tag` survives as the live-row invariant only. On a genuine collision the server **rerolls a complete fresh `adjective-noun`** — the bare `-N` suffix backstop is retired, along with the silent NULL tag it landed on at exhaustion. *Do not re-propose either.* The guarantee is honestly **per-ledger** (`sessions.db` is per-instance): a trailer written on one machine and read against another's ledger simply misses, which renders as the slashed atom and is safe.

**A rewind-fork inherits its parent's callsign verbatim.** The callsign names the line of work, not the JSONL file, so it transfers to the fork and never accretes; provenance lives in the `forked_from_session_id`/`fork_point` columns, never in the spelling ([D154]).

**The citation is the only sanctioned flat-text form**, and the only place monospace appears: `<tag> (<shortid8>)`, project-prefixed when the context does not supply the project, degrading to the bare short id for a legacy tagless row (a doubled hash is noise). Every Tug commit carries **two** trailers — `Tug-Session:` (the citation, for a human) and `Tug-Session-Id:` (the full uuid, for a machine, never displayed) — which tugcast parses server-side into typed `GitLogCommit` fields exactly as it already did for `Tug-Dash`, **and strips from the displayed body**, because `%b` retains trailer lines and that is why the History card used to show raw trailer ink. Reading a citation is two steps with a wire between them: `resolveCitedSession` is **pure grammar** over the trailer text — machine field first, then the parenthesized token (36 chars = a legacy one-line trailer, which therefore still resolves exactly; 8 hex = a short id) — and turning that id into a session is the **ledger's** job, over the `resolve_sessions` verb. Legacy commits live in history forever and had to keep working; they do. Transcript exports become `tug-session-<callsign>-<shortid>` — a file named after a hash is a file nobody finds again.

**Resolvability is a ledger answer, and a short id is expanded server-side.** *Do not re-propose* deciding either from the client's caches. The tag store and the binding store hold only the sessions some listing, push, or card binding happened to mention this run, so a chip judged against them is resolvable or slashed depending on whether the picker had been opened — which is not a fact about the reference. `resolve_sessions { ids }` answers `{ sessions: [{ queried, session }], unknown }`: keyed by the spelling asked (a short id and its row's full id are different strings), and **naming its misses**, which is what lets `session-citation-store.ts` cache a negative instead of re-asking on every repaint. Expansion belongs there for a second reason — only the ledger can see that two sessions share eight hex characters, and an ambiguous prefix therefore **resolves to nothing** rather than to the first row found, the same "wrong-but-resolvable is worse than unresolvable" rule the callsign's permanence rests on. A resolved row also seeds the name / callsign / description stores, which is the fourth such seed path beside the spawn ack, `list_sessions_ok`, and the card-binding rows, and it is how a citation names a session no card is bound to. The resolver answers from `sessions` first and falls back to `external_scan_cache`: cap and age eviction hard-delete `sessions` rows while the transcript stays on disk and the picker keeps listing it, and a citation must not go dark on a session the picker can still resume — the fallback row is synthesized exactly as the picker union synthesizes an external row.

**Liveness is not identity.** The record carries no phase field, and that survives the dot becoming the mark. Phase lives on a per-**card** `codeSessionStore` whose snapshot is the whole `CodeSessionSnapshot`, and an identity hook that subscribed to it would wake the chip, the line, the row, and the masthead on every transcript event; the dot is isolated in a leaf subscription so a reducer wake repaints the dot alone. `useSessionPhase` is the join — session → card → services → snapshot → key — and it lives beside the resolver rather than inside it precisely so the two stay separable. Identity and liveness are two subscriptions with two keys, and **the component is where they meet**: the dot arrives as a child, never as a field.

**The React entry point is the hook, and that is part of the spec rather than an implementation note.** `resolveSessionIdentity` reads three stores imperatively; called from a render body it hands back a snapshot with **no subscription**, so a `/rename` updates the stores while the surface repaints never. That failure passes every unit test and appears only as a stale name in the running app, so `useSessionIdentity` — `useSyncExternalStore` over each backing store **by id**, never by whole-store version token, which would wake every identity surface in the app on any session's rename — is the only door a component may use ([L02]). *No component calls the bare resolver*: grep gate.

**The Session card's chrome is a fixed 72px masthead, and the pane owns the slot while the session owns what is in it.** Three lines — the dot-led title with the pane controls, the description, the activity with its tape — plus a trailing telemetry **popover** carrying branch, stamps, the rendered atom, and the citation on a `TugCopyBadge`.

**One row shape, three mounts.** The masthead, the Lens rows, and the new-session picker rows show the same thing, so `TugSessionRow` authors the shape once and all three compose it — the component library is the consistency mechanism rather than a convention three files are asked to remember. The masthead is seated in chrome through the knobs the row's own primitive publishes (block and inline padding, the indicator gutter, the flush hover, the stack's block pad) rather than by reaching into its rules, and it raises the sub-line indent from the rail's to the dot's full advance because a card-wide tier can afford to hang its two lines off the *title* where a rail cannot. Retired with the shape, *do not re-propose*: the **three-level stack** (a standing goal beside the description read as a second goal-shaped line — the intent survives in the recent-pulses popover, where it heads its run of beats), the **four-line row** (its metadata facts are the activity line's rest form now), and the four **audition fits** `gutter`/`reveal`/`wash`/`duplex` with their comparison meter — only `inset` ships. **The stack's type is stated once, on the row, and no mount restates it**: title, description, and activity are the ambient sans at the row size, one size down, one size down again, and the step off the title is small enough that the pair beneath still reads as one group. The activity line therefore **drops `TugPulse`'s condensed face** on this stack — condensed is right for a PULSE that is a bar of its own, where width is scarce, and wrong for the third line of a paragraph whose other two lines are sans. Three mounts that each named their own sizes is exactly how the three surfaces came to differ from one another and from the gallery. Composing a list row into chrome also means **turning off the row's rail reflexes, the pointer poses included**: the flush hover wash and the `:active` press layer both answer a click that acts on a row, and a title bar's click activates or drags the *card* — left on, the press painted the entire chrome tier accent-blue on every press, the ones that begin a drag included. A pose that lives on a pseudo-element is invisible to a probe that reads `getComputedStyle(el)`, and `:active` cannot be reached by a synthetic event at all, so the assertion that guards this holds a real button down and reads the row's `::after`.

**The activity line says something true at rest.** `<turns> turns, <size>. Last updated: <stamp>. Ready.` — the turns segment **always prints** (a fresh session's line is `No turns, 8 KB. Ready.`; "no conversation yet" is a fact, not an absence, and the zero is spelled as prose rather than as a digit, which reads as a measurement that came back empty), an unknown size drops its segment, the labeled stamp appears only for a session with turns to have been updated by, and **`Ready.` always closes the line** — the session is on disk and one gesture from another turn wherever the row is read. `Last updated:` is labeled because a bare date-time beside a size and a count is ambiguous about which of the three it dates, which is also why the relative-age form (`3h ago`) went with the metadata line it opened. During a turn the live beat replaces the sentence — on every mount of the row, the picker's included; the picker's state lines survive only for rows this app cannot see into (a terminal's) and for failed rows. **The bare turn-end marker `Done` is not a beat and is never shown** (`sessionActivityBeat` filters it at every mount): it is the *absence* of one, it says a run ended and nothing about when, it sits there unchanged for however long the session then stays quiet, and it is precisely the state the rest sentence describes with the facts in it. The marker itself is untouched on the wire — the ledger, the recent-pulses popover, and a copied line all still carry it; only this reading changes. That grammar is what makes [P10]'s server work load-bearing: both facts are scan-derived, so tugcast re-derives them **at turn end** from the same incremental entry points the picker scan uses, and `build_session_updated_frame` reads the `(file_size, turn_count)` pair from the scan cache on **every** push — because the client replaces its cached row wholesale, so a push that omitted a fact would blank a known size or knock a scan-derived count to a sparse `0`.

**`PULSE` is an internal name and never user-facing ink.** Stores, modules, feeds, class names, and constants keep it; labels, legends, and stand-ins lose it. With the activity line always carrying something true to say, nothing needs a placeholder word — and a band that names itself is furniture where a sentence belongs. A grep gate (`lib/__tests__/pulse-ink-gate.test.ts`) keeps it out, stripping comments first and exempting gallery cards, which are where the vocabulary is discussed.

**The controls cluster is the same on every pane, masthead-bearing ones included.** The width control was suppressed on a masthead for a while, on the reasoning that the first row is identity plus its own telemetry wave and width competes with the name for it. That was reverted (`1693707dc`): the Session card is the pane whose width is retuned most often, so the one surface that most needed the control was the one that did not have it, and a control that appears on some panes and not others is a cluster the eye cannot learn. It renders on every pane that *has* a width — rails excepted, and not because they bear a different tier but because a rail takes its width from the allocator and has no preset to set. The **slot-stack badge**, the **`…` section menu**, and the **close X** are likewise unconditional: the badge describes the *slot* rather than the card, and a Session card standing in a stack is entitled to say so — it is the only way into the panes behind it. Assertions about the cluster name the control they mean by testid, never an equality check on the cluster's list, which is legitimately longer or shorter depending on whether the card stands in a stack.

**The masthead generalizes past the Session card, and a rail gets a tier of its own.** Three tiers ship: a 36px tinted bar for a **utility** card, a 72px masthead for a **document** card — Text, File viewer, Diff, and the Session card, whose masthead is the one described here — and a 32px flush bar with racing stripes for a **rail**. A document masthead is the same object as the session's, mounting the same `TugSessionRow` on the same `masthead-frame.css` tier, differing only in what its three lines say: a name, where the document lives, and one quieter fact. **The description ladder generalizes with it**: a document card that can name no place publishes a *stand-in* rather than nothing — the tier is a fixed three lines, so an empty second line is a hole between two filled ones, not a shorter masthead — and a stand-in paints a step quieter, exactly as the session's own last rung does, plus **italic** on the document tier, where the line's real content is a path and the absence of one deserves to differ in type rather than only in gray. (Italic is safe *here* because IBM Plex Sans Italic is bundled at 400, the weight this line inherits; a `font-style: italic` landing on a weight with no bundled face paints nothing at all in the app's WKWebView, which is why the guard for it is a pixel count in `at0212` and not a computed-style read.) The wording rule that follows is that a line never claims an act that did not happen: an unwritten buffer's third line reads **Draft**, not "Saved". Rail-ness is read from the card registry's `layoutRole: "sidebar"` — what the card *is*, not `sidebarSide`, which says only where it currently stands, and would flip a released Lens out of its livery mid-gesture. Both tiers stamp their role on the pane element as well as the bar, because the height must be declared where the scrim, the sheet clip, and the banner can see it and `:has()` will not carry it up. Racing stripes are settled — flush ground, three 1px stripes on a 3px pitch, neutral ink only, focus signalled by brightening and never by the accent color; *do not re-propose*. `pane-model.md` § "Chrome has three heights" is the doctrine.

(The telemetry popover shipped as a `TugPopover`, not a `TugPlacard`: a hover-dismissed surface puts its own copy button out of the pointer's reach, and `TugPlacard` renders in place, which a clipping 72px chrome tier cannot host.) The height is **ratified and fixed, never content-driven**; the masthead never reflows and overflow truncates. Chrome remains the Pane's ([L09]), so `TugPane` opens the taller slot when its **active** card publishes a masthead sidecar and mounts a tugways `SessionMasthead` into it — which is what keeps the PULSE feeder, the dwell queue, the compaction pin and the telemetry popover out of chrome code. In a multi-tab pane the chrome follows the **frontmost** tab, swapping 36↔72 on tab switch: a pinned 72px chrome over a Text tab would caption one card with another card's identity. The height travels as a pane-scoped `--tugx-pane-chrome-height` so the four chrome-offset consumers (the title bar, the pane scrim, the sheet clip's top, the pane banner) follow it while the four that are really measuring *a tab row* or *a square button* stay on `--tug-chrome-height` — the masthead and the tab bar **stack** (72 + 36), they do not merge. Once the masthead carries the voice the Z2 `SessionPulseStrip` comes out entirely, with the dwell queue moved *as code* rather than rewritten; its focus stop is retired rather than re-homed, since the masthead is chrome and takes no card-cycle stop.

**The description is a rolling synopsis, and the incipit is retired as its source.** A first prompt describes where a session *started*; a description has to be current, which is the whole complaint. One job on the SharedAgent's sentence lane composes a standing line from a session-lifetime digest — `compose_synopsis_digest`: the newest ask as the subject, the arc of earlier asks behind it, the opening for context, and the newest activity lines as explicitly-labelled background — paced at once a minute, and persists to a `synopsis` column on the session's ledger row. The register is a summary's rather than a headline's: articles and conjunctions are allowed, the budget is `MAX_SYNOPSIS_CHARS`, and the line names an undertaking and its object. This is the **only** model ask the subsystem makes.

**The name and the description are two fields on two lines, and the rename freeze is gone.** `SessionIdentity` carries `customName` (the user's `/rename`) and `description` (the agent's synopsis) as independent fields — the merged `title` is **removed**, not deprecated, so the compiler enumerated every reader. The freeze existed because they competed for one line of chrome and a generated line must not speak over the user's word; they occupy different lines now, so both enforcement points are gone — the `AND name_user_set = 0` clause in `record_synopsis` and the pre-model early return in the synopsis feed. Leaving it would have given every renamed session a permanently dead description line on its most-visible surface. *Do not restore it as a "fix".* The description's own precedence is its three rungs: the synopsis, else the session's **own first prompt** (load-bearing at the picker, where a freshly-scanned external session has never been summarized and its first prompt is the only human-meaningful text the row holds), else `Created <stamp>`. The lower two are marked `data-stamp` and painted a step quieter, to say they are facts standing in. **The stamp rung has to work on a session with no turns**, which is the only state in which it is the *only* rung available — and both of the deck's sources were structurally blind to exactly that session: the card's replay anchor reads the first turn's timestamp out of a JSONL a zero-turn session has not written, and the ledger's workspace listing deliberately omits a content-empty row so nobody is offered an abandoned session to resume into. The listing rule stays; the spawn-time `session_updated` push is **kept rather than discarded** (`SessionLedgerStore.detachedRows`) and answered by id through `findRow` / `useSessionLedgerRow`. A card asking about *its own* session is not the picker browsing a workspace, and only one of those two questions the empty-row filter was written for. The line **always occupies its height**, so a description arriving does not move the line below it.

**The description shipped riding a headline's machinery, and the headline is now deleted rather than renamed.** It is worth recording how that came about, because every step of it was locally correct. `dash/archive/pulse-improvements.md` built two renderers for a per-stretch PULSE **headline** — the card strip's bright leading run and a Lens intent line — and the description was then added as a second job beside it, taking the headline's emit completion as its trigger and the headline's text as one line of its digest. `dash/archive/session-identity.md` replaced the Lens line with the description, and this decision retired the Z2 `SessionPulseStrip` and had `tug-session-row.tsx` deliberately withhold `TugPulse`'s `headline` level. Nobody swept the producer. The headline's whole output chain was dead while its emit loop went on running — a second Haiku call a minute, writing to a ledger cache with no reader — because two of its functions had become load-bearing **by accident**: a completion nobody watched was the description's clock, and a line nobody read was a line of its evidence. So the consolidation re-homes both — the trigger onto the beats directly, the digest line onto the newest activity lines — and deletes the rest: the `summarize`/`summarize_done` jobs, that cache and its restore chain end to end, and the eval's retrospective lane. **Do not rebuild the headline chain**; a second per-stretch line is a new proposal that must argue for itself, not a restoration.

**The description no longer rides the PULSE kill switch, and that is a deliberate behavior change.** It gated on PULSE only because it was composed inside the emit loop, which is machinery rather than intent: a user who turns off the commentary strip did not ask for their session rows to go nameless. The subsystem now emits no PULSE at all and reads one switch of its own, the `synopsis` tenant. What stays rejected, *do not re-propose*: a **second** collection pass — the digest is one cut of evidence the module already holds, and a parallel JSONL reader on its own schedule is the shape that was refused. **And the write still has no fallback row key:** ledger rows are keyed by *claude's* session id, the resolver answers it, and a resolver that cannot answer means the ask is **skipped entirely** rather than aimed at the tug id. The resolver returns `None` both for "no such entry" and for a contended lock, and after a rewind fork the tug id names the *parent's* row — so guessing it would write one session's description onto another's, and the session that waits a minute for its line has lost nothing.

**Due-ness is derived and defers rather than being swallowed.** A session is due when it has moved since its last ask, or when a settled stretch has a refresh pending; the once-a-minute pacer only decides *when*, never *whether*, because the beats that made a session due are consumed at spawn and not before. The predecessor swallowed the post-settle refresh outright whenever it fell inside the window, which is why a session that went quiet could sit under a stale line indefinitely. Burst and idle thresholds are gone with it: under a one-minute pacer they were arithmetic that could not change an outcome. Originating plan: `dash/session-synopsis-consolidation.md`.

**The atom paints in text ink, and the dot is its only color channel.** The pill keeps its rounded shape and drops the theme's session tone: the run takes the ordinary text color and the border a `currentcolor` mix. A colored pill around a colored dot was two tints saying one thing, and the dot's tint is the one carrying information. The theme-authored `session` tone on the `atom` slot — four `--tug-color(violet, …)` recipes per theme, aliased in one hop to `--tugx-session-identity-*` ([L17]) with `ELEMENT_SURFACE_PAIRING_MAP` entries — **stays authored** and is simply not consumed by this component; retiring the tokens is a separate question. Still rejected, *do not re-propose*: a **per-session hashed tint** (color is a semantic channel; a hashed hue reads as meaning while meaning nothing), and a bespoke `--tug-session-color` role token with the component deriving three of four values by `color-mix` — not a `--tug7-*` target, moves per-theme tunability into component CSS against [L20], and is invisible to the contrast audit, which cannot see through `color-mix`.

**A DOM paste has to ask the pasteboard, because the event cannot see the atom.** Inside Tug.app an atom copy is written natively to the Tug-private `dev.tug.prompt-atoms` type — the whole reason that path exists is that WebKit's pasteboard normalization swallows custom MIME types. The unnoticed consequence was symmetrical: a DOM `paste` event's `clipboardData` cannot see that type either, so `getData(TUG_ATOMS_MIME)` came back empty for a clipboard demonstrably carrying an atom, and the paste fell through to plain text — a session atom copied from the Session Summary panel landing in the composer as its citation *string*. The editor's own ⌘V responder action always read the bridge and did the right thing; every other route into a paste (a menu Paste, a keystroke WebKit handled before the chain saw it) reached the DOM event instead and lost the chip. So the DOM handler now consults the native bridge as its last branch before plain text: only inside Tug.app, only after the DOM has had every chance, with the bridge's own plain text as the fallback — a clipboard with no sidecar still pastes exactly what it would have, one async hop later. Both routes insert through one `insertSidecar`, because two implementations of one paste is one edit away from two behaviors.

**Wherever an atom is a mounted React chip, it is a subscribed one.** Its dot reads the session's phase this second and its name tracks renames — the Overview ref, the History line, the Changes list row (one chip *per row*), and the masthead's telemetry popover, all four for the price of the hook, because all four compose `TugSessionCitation`. **The composer's pasted atom is explicitly excluded and stays baked ink**: an atom in the prompt editor is a CodeMirror `AtomWidget` whose `toDOM` returns an `HTMLImageElement`, and the bake is not a styling choice but how an atom survives being *editor ink* — one `root.render` for the app's life ([L01]), a replaced inline element whose caret and selection semantics CodeMirror owns, and a copy/paste round trip through document text. A pasted atom's dot is a snapshot at paste time and its name the name as of paste, which is honest for a thing that is now text in a draft. *Do not propose mounting a live subtree there* without first solving the second-React-root problem.

**An unresolvable citation keeps its shape and says so.** Same pill, dashed border, muted ink, a forced idle dot, fully inert, tooltip *Session not found* — and it still shows whatever callsign the commit recorded, because a reference that cannot be followed is more useful naming what it named than showing a bare hash. The **slashed mark is retired** with the icon it slashed: there is nothing left to slash, and shape alone states the failure, which it already did alongside the slash. **Liveness is never a property of a reference**: sessions are never dead, only unfindable.

**Right-clicking the masthead's title copies the atom.** The full flavor set, through the same `useCopyableText` every other Tug chip uses — the atom should be reachable without opening anything, and right-click is the idiom already in place. The telemetry popover additionally *displays* the rendered atom above the flat citation, so the two copyable forms sit side by side, each labeled by what a paste of it yields.

**That panel is titled `Session Summary`, and it is a KEYED table, not a log.** Six rows in the gallery's order — `STATE` (the ledger's word and what the session is doing, `live · working`), `TURNS` (count and size), `CREATED` (or `COMPACTED`), `BRANCH`, `ATOM`, `CITATION` — with the keys small, letter-spaced, and in the ambient sans, and monospace reserved for the citation exactly as everywhere else in identity. There is no `LAST USED` row: the activity line a few pixels above the panel says `Last updated: …` at rest, on the same card. Two things the shipped panel got wrong are worth naming because both are structural rather than cosmetic. It composed `TugPopupListFrame`, **which paints everything but its own titlebar in mono** — right for the tabular logs it was built for, and it silently made this panel the one identity surface set in monospace, so the panel takes its type back explicitly. And its rows clipped: a value cell with `overflow: hidden` elides a run of text correctly and **cuts a bordered chip off mid-curve**, which is what happened to the atom's pill and the citation's badge. **D135.** **A settle tween may smear a frame's raster only within a capped distortion; past the cap the frame crosses by real geometry, and a rail mode flip is a fade plus one true height change.** The FLIP settle's acceleration has a price the deck had stopped naming: the compositor rasterizes a frame once and animates the *texture*, so a translation is pixel-identical to moving the element but a **scale is a screenshot smear** — every border, corner radius, and glyph stretched rather than re-laid out, correct at no intermediate size. [D134]'s `sy` put a ~100% vertical stretch on the frame densest with small type and thin rules, and it read as what it was. **The policy is a numeric cap, not a judgment call per gesture**: distortion is `max(s, 1/s) − 1` — symmetric, a halving and a doubling both read 1.0 — and a scale term may ride in the transform tween only while distortion ≤ `MAX_FLIP_SCALE_DISTORTION` (0.2). Split across two effects the transform runs on the compositor and the size on the main thread, and the pinned edge slides by however far they drift; that is a card moving when it does not have to, which is the one thing this settle exists to prevent. The separation this replaces was written to protect acceleration, and it protected nothing: a frame carrying a real size term is re-laying out its subtree every frame regardless, so acceleration was never on the table for it and all the split bought was a second clock. Fading in, the held pose is the final tile the commit already put it at. **D157.** **A conflict is a complete block or it is content; and a resolution this dash already made is replayable on exact stage identity, above rerere.** Two findings from reading Jujutsu's source (Apache-2.0) against the landed conflicts-as-data round. First, `has_conflict_markers` matched any line *starting with* `<<<<<<<`, `=======`, `>>>>>>>`, or `|||||||` — and `=======` is markdown's setext heading underline, which two files in this repository carry today. The damage was worse than a wedged workshop: `is_clean_merge` is what rungs 3, 4, and 5 use to validate their **own output**, so a file whose three stages `git merge-file` merged perfectly cleanly was rejected because the clean result contained an underline, and the path fell through every machine rung to `unresolved` — the AI seam handed a conflict rung 3 had already settled. Detection is now structural, jj's `parse_conflict` shape: a marker line is a run of ≥7 identical marker characters at column 0 followed by end-of-line or a space and a label, and a conflict exists only where a complete ordered block does (opener, optional base section, separator, closer), with a second opener abandoning the block it interrupts. Git only ever writes complete blocks, so completeness *is* the signature. The trade is that a half-dismantled block reads as content, which an advisory names rather than refuses — and that advisory deliberately ignores a **lone `=======`**, because the separator is the one marker with a life as ordinary content and an advisory that fired on every conflicted markdown file would reintroduce the noise one channel over. Second, conflict validity is strict head equality, so any base motion invalidates the chain and the ladder starts over — cheap for the machine rungs, and fatal for the resolver's committed checkpoints, which are taught to nothing and are the most expensive resolutions in the system. A **salvage rung** replays them wherever the three stage oids and modes are byte-identical to the current ones and the path is marker-free at the prior tip: strictly narrower than rerere (object identity rather than textual preimage), and cheaper (one blob read rather than a scratch worktree and a real merge), so it sits above it. It is computed as a batch because `rerere_rung` is itself a batch call above the per-file loop, and skips that call entirely when salvage covers every path. Checkpoint work only — a prior run's machine-rung results re-derive through their own rungs. The prior chain is read raw at ladder entry, upstream of both `clear_conflict` writers. jj's N-way `Merge<T>` algebra, marker round-tripping, and marker-length escalation on write are deliberately not ported: git materializes our markers and resolvers rewrite whole files, so detection is the whole need. `tugrust/crates/tugdash-core/src/resolve.rs` (`scan_conflict_blocks`, `marker_kind`, `orphan_marker_lines`, `salvage_rung`, `ResolvedBy::Salvage`). `dash/archive/dash-hardening-2.md` [P01]–[P06].
