# The Focus Language

*The single keyboard-focus model every interactive surface in the app obeys: the visual signature of focus and selection, the two planes keyboard motion moves on, and how commit is separated from movement. Read this before adding a focusable control, a dialog/sheet/alert, or any surface a keyboard user navigates.*

*Cross-references: `[L##]` → [tuglaws.md](tuglaws.md). `[D##]` → [design-decisions.md](design-decisions.md). The visual overview lives in the **Focus Language** gallery card (`gallery-focus-language.tsx`); the full design history is `roadmap/tugplan-focus-language.md`.*

---

## Why one language

A keyboard user needs to answer two questions at every moment: *where am I?* and *what is chosen?* Before this model the app answered the first with one global orange outline on whatever held DOM focus, and conflated the second with the first. The focus language separates them and makes both answers consistent across every archetype — a button, a text field, a radio group, a list, a dialog box — so the treatment a user learns on one control reads correctly on all of them.

The engine (the `FocusManager`) is unchanged by this language: it owns the key view, the cursor, the per-card scope stack, and projects them as DOM attributes. The language is **appearance** ([L06]) — CSS keyed on those engine attributes. No component sets a focus style from React state.

## The signature: focus is a ring, selection is a fill

Two independent marks, never conflated:

- **Keyboard focus** = a **ring** (role color) plus a faint **behind-tint** (role color) on the focused component. It says *the keyboard is here*.
- **Committed selection** = the component's **native fill** — a radio dot, a choice/tab pill, a checkbox/option fill, a row fill. It says *this is chosen*.

They are orthogonal: a ring can sit on an already-selected item (it is offset just outside the item so it survives atop a fill — which is what lets multi-select work with no extra checkmark).

### The element marks; the container does not — [D122]

One mark answers one question. **Which element** is answered by the leaf ring and the movement caret, both at **full accent**. **Which container** is not answered by a mark at all: an item-group container paints nothing while it holds the keyboard, because the element mark is *inside* it and therefore already says which container it belongs to. The element mark rides **Accent** and a committed selection fill rides **Key**, and they must stay distinguishable in every theme, so a focus mark can never be misread as selection — that half of [D122] is a constraint on theme authoring as much as on components.

**Three container marks were tried and all three failed the same way.** The first was a perimeter stroke at full accent, which put a bright rectangle around a bright ring — two different questions asked in identical vocabulary at two scales, and the eye reads the big rectangle before it finds the small one, exactly backwards since the cursor is what the next keystroke acts on. The second gave the two questions two different *kinds* of mark, making the container's a background wash so neither had to win; that reasoning is sound and it lost to the surfaces, because **an area mark is a colour laid over a whole region, and at any strength that reads it also tints every pixel of content sitting on it** — the treatment came out brown over a mid-tone sheet, grey-tan over a pale one, and every correction toward one surface made it worse on the next. The third separated them by **degree**: a quieter, thicker container stroke against a brighter, tighter element one. It shipped, and it still read as two rings, because tone is not enough separation between two closed rectangles a few pixels apart.

**The fourth answer is to stop drawing it.** What all three were buying was the answer to "which container holds the keyboard", and the element mark was already giving it away for free. Removing the container mark costs nothing that was being read, and it removes the one mark in the language that could be mistaken for another mark. It also retires a surprising amount of machinery: `TugListView`'s perimeter needed a sticky overlay child, a JS-measured scrollport height and scrollbar width, a two-layer band split by the scroller's clip, a z-index lift, an inner-overlap offset the cursor caret had to read, and a suppression rule for carries — none of which has a subject now.

**In CSS this is a suppression, not an absence.** A group holding the key view still carries `data-key-view-kbd`, so the global leaf-ring rule in `focus-ring.css` would stroke it. Every item-group's own CSS therefore declares `outline: none` on its root at one-class-plus-one-attribute specificity, which outranks the global rule. `data-key-within` is suppressed by the same rule on the same components — the global within-mark stays for containers that are *not* item-groups (a sheet holding an open popover), which is the case it was written for.

**Leaf vs. item-group:**

- A **leaf** (button, text field, checkbox, switch, slider) rings the **whole component** — box *and* label together, never just the glyph. It also carries the faint behind-tint; a leaf gets both marks because it is one element.
- An **item-group** (radio group, choice group / tab bar, option group, list, accordion, tab-view sidebar, dialog answer list) paints **nothing on the container** and marks the **cursor item** inside it. It draws neither the leaf ring nor a container ring nor a border-colour change, in any theme.

**The shape of an element mark follows the shape of the item.** Full-width row containers — `TugListView`, `TugAccordion` — mark the cursor with a **leading-edge bar**. Inline chip groups — radio, choice, option, tab — mark it with a **ring**. Both are element marks; only the geometry differs, because a ring around a full-bleed row reads as a second container and a bar on a chip reads as a fragment.

**The caret is the loudest mark on the surface, deliberately.** It is the one thing that answers "where am I", and nothing competes with it — the container it sits in draws nothing. `--tugx-focus-cursor-bar-width` is its own knob and was never tied to the retired container ring's thickness: two marks answering different questions had no reason to share a weight, and sharing one only ever made the caret quieter than it should be. It is a plain leading-edge rectangle: one constant width (`--tugx-focus-cursor-bar-width`), running the item's full height. A tapered trapezoid was tried — widest at the item's mid-height, narrowing toward each end, on the theory that a pointed silhouette reads as *aimed at* the row rather than as a rule beside it — and it did not read that way at the widths a caret may occupy; it was a few pixels of bevel and four extra knobs. Keep the width small: a large value makes a slab that competes with the content.

**A selection wins the pixels it covers.** Where two area marks in different hues overlap, the result is a colour nobody chose, and alpha only adds — no third translucent layer can take it back out, so the fix has to be structural. A `TugListRow` that paints a selection paints an **opaque ground** first (`--tugx-list-row-ground`) and lays its wash over that, so the selection composites against the surface and nothing else. This is the same call one level down, where a striped list drops the band under a selected row for the identical reason.

This rule was learned from the container wash, which is gone: at 6% behind an 18% selection wash, ~5% of the accent survived *through* the blue and a selected row went muddy the instant its list took focus. Nothing paints behind the rows any more, so that particular collision cannot recur — but the ground stays, because the rule is general and the next thing to paint behind a row will find it already settled. The ground comes from `--tugx-ambient-surface`, published by whichever host actually paints the surface (`TugSheet`, `TugAlert`, `TugPopover`, the Lens band, the session picker) — a publish/subscribe contract, single writer and many readers, because a row cannot see what it sits on. A host that paints its own surface and does not publish it gets selections one step off their neighbours.

**An empty group never holds the keyboard, and with no container mark it would show nothing at all.** With the container unmarked, the *only* focus indicator an item-group has is the mark on its cursor item — so a group with no items to cursor would take the keyboard and paint nothing, which is a WCAG 1.4.11 failure as well as a usability one. The guarantee that a cursor item always exists lives in the **focus registration**, not in CSS: a surface refuses the focus group to a group with nothing to cursor — the Lens sections gate theirs on `navigable`, the post-filter row count, so a list filtered to zero drops out of the Tab walk and the Cmd-L seed entirely (`lens-section-content.ts`). Any new surface that lets an item-group take the key view while empty must gate the same way, or it owes the language a visible fallback mark. This constraint got *stricter* when the container mark was retired, not looser.

## One role axis, default `action`

There is no role-less branch. Every focusable's ring, selection-fill, and behind-tint resolve from a single role axis whose default is `action` (the interactive blue). Role-bearing controls (checkbox, switch, radio, choice, option, and role buttons) color both the fill and the ring with their role (`danger`, `accent`, …); a role-less control simply rides the action default. A text input is role-less by default, but its **validation** state maps onto the axis — an invalid field is the `danger` role and focuses red.

## Buttons: fill is the live control; the default rests at a tint

A pure action control has no separate "selected" state, so the cursor takes over the fill — but **solid fill is reserved for selection and the live (focused) control**. Three resting states:

- **Rest** — outlined.
- **Recommended default** — the button `Return` fires while the cursor rests elsewhere — rests at a **tint** (`primary` emphasis) with a ring. This is the `persistentDefaultRing` treatment; the engine owns the `data-default-ring` attribute so the one-filled-ring-per-scope invariant is structural. The ring is a **promise, and it must be honest**: `persistentDefaultRing` both paints the ring and registers the button as the scope's Return-home, so it must be set only while `Return` really fires that button. A surface whose `Return` is consumed elsewhere mid-flow gates it — the question wizard's Submit wears the ring only at the review step with every question answered (`Return` on a live question commits-and-advances; before review the ring would lie). **This half is currently unpinned**: at0202 pinned it, together with the reveal that scrolls the newly-lit Submit into view, and was retired in the 2026-08-11 app-test cull; the honesty rule itself is pinned for the two entry-shell wearers by at0398.
- **Live / focused** — promotes to its **filled** role style + a role-colored ring; siblings demote to outlined.
- **Chord default** — the button a **chord** fires when a plain `Return` does not: the same ring, dotted, resolving to solid while the chord's modifier is held **alone**. See [the chord ring](#chord-ring).

A whole **container** that becomes the key view (popover, sheet, alert, inline-dialog box) can't fill: it wears a box-shadow ring that hugs the radius with no reflow, and the quiet "within" variant when it merely contains the active control.

### The chord ring — a conditional promise, stated conditionally {#chord-ring}

The double ring says **`Return` fires this**. Some defaults are fired by a chord instead, and the composer's Z5 is the case that matters: `returnKeyAction` is a user setting shipping as `newline`, `resolveEnterAction` flips the base action on Shift, so at the default it is **`Shift+Return` that submits** and a plain `Return` inserts a line. A solid ring there is the language's one promise stated falsely on its most prominent wearer.

The answer is to qualify the mark rather than drop it or invent a second one. A chord default wears the **same double ring, dotted** (`--tugx-focus-ring-chord-style`, the single knob for the whole treatment), and while the chord's modifier is **physically held** the ring resolves to **solid** — because at that instant a `Return` really would fire it. The ring is therefore never false at any moment, and holding Shift becomes a gesture that *shows* the user what `Return` is about to do, which is the discoverability the chord otherwise lacks entirely.

**The chord is exclusive, so the resolve to solid is exclusive too.** `Shift+Return` means Shift and nothing else: `Cmd+Shift+Return` and `Opt+Shift+Return` submit nothing, because every keystroke path disqualifies stray modifiers — `chordMatchesEvent` compares all four flags exactly ([P09]), the editor's Enter handler passes any other modifier combination through untouched, and the bubble pipeline's Stage-2 default-button activation matches a wearer's `data-default-chord` the same exact way (a chord wearer is *not* fired by a plain `Return`, and a non-wearer is *not* fired by a modified one). So Shift held **with** Cmd must leave the ring dotted — going solid there would promise a keystroke that does nothing, which is the exact falsehood the dotted ring exists to prevent. This is why the latch tracks all four modifiers though only one is painted on: exclusivity is a claim about the modifiers that are *absent*, and a Shift-only latch cannot make it.

Three pieces, all appearance, none in React state ([L06]):

- **`data-default-chord`** on the wearer, e.g. `"shift"` — the button's own **static declaration**, never engine-owned, so it composes with the engine's `data-default-ring` without touching the projection. One attribute serves both paint paths (`persistentDefaultRing`'s and the entry shell's), so the two look identical for the same reason their base rings do.
- **`data-mods`** on `<html>` — the held-modifier latch (`modifier-latch.ts`): the **whole** held set, space-separated in a fixed order, read as `[data-mods="shift"]` — an exact match, never the `~=` membership test, which would match every superset and light the ring under `Cmd+Shift`. It reads the four modifier flags off **every** key event rather than watching for `key === "Shift"`, so a missed modifier keyup self-corrects on the next keystroke instead of sticking the ring solid; window `blur` covers the ⌘Tab-while-held case no key event can.
- **Only the outline's style and width move.** Colour, offset, the filled promotion, and the background-window stand-down all stay the plain default ring's — this *is* that ring wearing a qualifier.

**At most one control on screen may promise `Return`** — solid or dotted, both are claims on the same key, and two lit at once leaves the user no way to tell which one means it. The invariant is structural rather than arbitrated: the engine projects `data-default-ring` onto at most one node, and the entry-shell path lights only inside the shell that holds the keyboard, so the two cannot coincide. Promoting the entry-shell path into the engine's default-ring stack would be the other way to guarantee it and [P14] rules it out — that stack holds *standing* mount-scoped claims, and two mounted shells would contend for one slot to express something that is not standing at all. So the guarantee stays structural and the focus manager's projection carries a dev-only check that records `return-promise-collision` when it breaks.

Like `data-default-ring` itself, the chord ring is **outside the KBF mode gate**: it names `Return`'s home, not a focus position. The rejected alternative was a `⇧⏎` keycap badge at the button's trailing edge — it names the key, but it adds a second vocabulary to say what the existing one can say by qualifying itself, and it says nothing at the moment the user is actually holding the modifier.

Pinned by at0398, which drives the real Z5 through dotted → held-Shift-solid → dotted, confirms the find bar's honest default neither declares a chord nor flinches under Shift, and counts the promises. The held-Shift half needs the harness's `withModifiersHeld` (press and release as separate RPCs); `holdModifier` buffers its inner verbs into one call and so cannot look at the app mid-hold.

## Motion: two planes, explicit commit

### The mode division comes first — [KBF]

**Rings exist if and only if keyboard-focus mode (KBF) is engaged — and a blinking caret and a focus ring are mutually exclusive.** Those two sentences govern everything below them, and together they are the difference between an interface with a mode and one that re-decides on every keystroke.

- **Mode OFF.** Text surfaces own their keys unconditionally. A caret keeps all four arrows whatever its content and wherever it sits in its document; no ring, cursor bar, or containment mark paints anywhere in the deck; the keyboard is either in a text surface or nowhere. Nothing about the *content* of a field enters into it.
- **Mode ON.** The engine owns the movement keys. Rings paint, arrows move the ring along the spatial plane, `Tab` walks the linear order, `Space` commits.
- **Mode ON with a granted caret.** The mode holds — the trap or registration that engaged it is still true — but the **paint stands down**: no `data-kbf`, no rings, the caret is the focus mark. The keyboard belongs to the text surface (that is what `dom-granted` means), so painting engine marks around a live caret would promise steering the engine is not doing. The next park brings the paint back. See [the paint keys on the route](#kbf-paint-route).

The mode is **derived, never latched** — `FocusManager.kbfEngaged()` recomputes on every read from four inputs: accessibility keyboard-access mode (permanently engaged), the manual bit (⌥⇥ or View ▸ Keyboard Focus), a **trapped** mode entry on the active context that has not opted out with `kbf: false`, and the key card's `kbfAtRest` registration. Being derived is what makes a surface closing *be* the disengagement: there is no state to strand.

#### The whole inventory of entering and leaving {#kbf-transitions}

Four derivation inputs are not four gestures, and the difference is where this gets missed: three of the inputs are conditions that hold or don't, and only the **manual bit** has transitions in the ordinary sense. So the complete list is short, and it is worth having in one place because a missing exit reads to the user as a stuck ring rather than as an absent rule.

These tables are **derived from the writers, not from memory**, and they carry their sites so they can be re-derived: a `grep` for `setKbfManual|toggleKbfManual|clearKbfManualForPointer|kbfAtRest|kbf: false|hasEngagingTrap` must find no site a row does not name. That check is the audit — the first version of this inventory was written from the design and was already missing a real exit (the trapped-surface one, below) by the time it was committed.

**Each site is named by file and symbol, never by line.** The first version carried `file:line`, and within a day of the follow-on commits roughly half the numbers were stale by six to seventy-five lines — a table that reads as precise and is not, which is worse than one that reads as approximate. A symbol survives every edit that does not rename it, and it is what the audit `grep` above actually matches on; a line number is a second copy of a fact the file already holds, kept beside it, which is the drift seam this document warns about everywhere else.

**Engages:** {#kbf-engages}

| | mechanism |
|---|---|
| Accessibility keyboard-access mode is on | permanent — the mode never disengages while this holds. `setKeyboardAccessMode` (`focus-manager.ts`), fed from the platform store (`responder-chain-provider.tsx`) |
| ⌥⇥, or View ▸ Keyboard Focus | the manual bit — `toggleKbfManual` (`focus-manager.ts`), from the action (`action-dispatch.ts`'s `CYCLE_FOCUS_MODE` handler) and from a card already inside a cycle (`use-cycle-mode.tsx`'s `toggle`). A live caret makes it *re-engage* rather than toggle off, **and the gesture parks the stop the caret is on** (`parkAtKeyView`, `focus-manager.ts`) so the ring appears where the keyboard is and the now-`engine-routed` route lets the second ⌥⇥ read as the toggle's other half ([P09]). Without the park the bit went up with nothing painted and could never come down — a `dom-granted` route forces every toggle back to `true` |
| `Tab` / `⇧Tab` from a single-line `INPUT` or from the **nowhere** state; View ▸ Next / Previous Keyboard Focus | `advanceKeyViewFocus` sets the bit before it steps (`focus-manager.ts`), so the chord (`focusWalkListener`, `responder-chain-provider.tsx`) and the menu items (`NEXT`/`PREVIOUS_KEYBOARD_FOCUS`, `action-dispatch.ts`) behave identically ([P07]) |
| A card's own focus cycle is entered | `use-cycle-mode.tsx`'s `pushMode` sets the bit as the cycle goes up. The mirror that turns the bit into this card's cycle only fires while the card's context is at its **resting mode**: the bit is deck-global and goes up for reasons that are not this card's, and entering while a floating surface holds a mode above it would push the cycle ON TOP of that surface's trap — the walk would then service a mode whose stops all sit behind a modal overlay, so every one fails the interactivity filter and `Tab` moves nothing. Same wrong target the ⌥⇥ action refuses at `action-dispatch.ts`; this is the other door. The cycle mode itself is pushed `kbf: false` — the mode is on because the *bit* is, not because the cycle traps, which is what keeps the engagement non-circular |
| A **trapped** focus mode entry on the active context | Class A, `hasEngagingTrap` (`focus-manager.ts`): a sheet, dialog, popover, or menu, unless it opts out with `kbf: false` (`use-cycle-mode.tsx`'s `pushMode` and the Open Quickly dialog, `tug-modal-input-dialog.tsx` — the two typing-first carve-outs) |
| The key card becomes a card that declares `kbfAtRest` | Class B — the last clause of `kbfEngaged` (`focus-manager.ts`), settled on every key-card change by `adoptKeyCard`'s `settleKbfEngagement`. Arriving there engages with no gesture at all, and the arrival seeds a ring if the card has none |

**Class B is a registration, not a list of cards** (`kbfAtRest` in `card-registry.ts`). The current members, so the class can be recognized on sight: **Lens** (`lens-register-card.tsx`), **Jots** (`jots-card-registration.tsx`), **Overview** (`overview-card-registration.tsx`), **DevTools** (`devtools-card.tsx`), **Keyboard** (`keyboard-card.tsx`), **Settings** (`settings-card.tsx`), and two gallery cards (`gallery-registrations.tsx`). The shared property is that the card is *navigated* rather than typed into: its resting state is a set of stops, so a ring is what it should wear at rest.

**The obligation the registration carries: a Class B card must offer stops.** The mode engages on arrival, and "an empty group never holds the keyboard" applies at card scale too — a card that engages with nothing to ring puts the user in a mode with no visible position. Overview was exactly that case (`kbfAtRest` with no `useFocusable`, no list, no seed) and now registers its composer field and Ask button (`overview-card.tsx`, `OVERVIEW_FOCUS_GROUP`). Its transcript posts and their ref chips are still not stops; that is a gap in coverage, not a violation, because the card does hold the keyboard somewhere the user can see.

**Sidebar cards are where Class B is felt**, since their shortcuts move the key card without any focus gesture:

| gesture | what the mode does |
|---|---|
| ⌃⌘L / ⌃⌘J / ⌃⌘O — the three-state sidebar shortcut (`sidebar-toggle.ts`) | *show-and-activate* and *activate* both transfer the key card to a Class B card → **engages**, no gesture, ring on the rail's remembered key view. The third state, *hide*, transfers away → **disengages**, unless the manual bit is independently set |
| ⌘L (`FOCUS_LENS`) | the same engagement going in; its second press — focus back out to the stashed card — is the disengaging leg, by the same key-card rule |
| ⌘J (`NEW_JOT`) | activates Jots **and** opens a jot's editor, so Class B engages and the editor's own descend claim then grants a caret. This is a *seed*, not a movement, so the stop does not park ([P12]) — the card holds the mode and the caret holds the keys |

|---|---|
| ⌥⇥ again, from a parked stop | the toggle's other half (`focus-manager.ts`) |

| A printable character — or `Escape` — at a parked text stop | the grant ([P12]) — the keystroke asks for the caret, and a caret is mode OFF. **The caret lands where the ring stands**, never at the card's resting editor: Escape with the ring parked on the find bar's query field leaves the caret blinking in the query field. This holds at every rung the ladder can reach a parked text stop from: rung (2a) (`responder-chain-provider.tsx`, sited ahead of a trapped surface's own `onEscapeDismiss` when no Class A trap is on the stack — so inside the typing-first modal input dialog, the Escape that means "stop steering" never closes the surface — and gated on the mode **painting**, because that gate is the rung's whole licence to outrank a modal surface's dismiss: in a modal state Escape exits the modal state, and the only thing that outranks that is a ring on screen saying the keyboard is somewhere else. | **An engaging trap is left** — a sheet dismissed, a dialog closed, a menu put away | two halves, and the second one is easy to miss. Class A is **derived**, so the input simply stops holding; but the **manual bit** is stored, and it can be set on either side of the surface — ⌥⇥ pressed *inside* it, or a mode the user turned on before the gesture that opened it. Either way the bit would outlive the surface and leave a ring on the deck the user just came back to. So `popFocusMode` **clears the manual bit** when the popped entry is a trap that engages (`focus-manager.ts`), and lets the derivation answer from what is still true — a Class B card underneath keeps the mode on its own authority. The rule is about returning to **rest**, not about any pop. (Note also that a plain `Tab` inside a trap does **not** set the bit — `advanceKeyViewFocus` sets it only when the mode is off, and inside a trap it is already on; ⌥⇥ is the gesture that writes it there.) |
| The key card changes away from a Class B card | derived — the input stops holding, settled by `adoptKeyCard` (`focus-manager.ts`) |
| A cycle mode is popped (`useCycleMode`'s exit) | the cycle clears the bit it set, in the relinquish layout effect (`use-cycle-mode.tsx`), except when the exit was itself a caret grant, which it yields to |
| **A card is created** | a new card brings its own resting focus, so a ring left over from the gesture that opened it points at the deck the user just replaced (the card-construction hook, `responder-chain-provider.tsx`). Hung off card CONSTRUCTION, not off the deck's several add paths, so a path added later cannot miss it |

It projects as one attribute, `data-kbf` on `<html>`. CSS reads it only as `html:not([data-kbf])` suppressions; the ring's own trigger is **withheld at the projection** instead, which is why the gate cannot miss a rule and why no painting rule's specificity changes (see the contract table below).

#### The paint keys on the route {#kbf-paint-route}

The attribute answers *is the mode painting*, not *is the mode on*, and the two diverge on exactly one axis: is a caret live. `kbfPainting()` (`focus-manager.ts`) is `kbfEngaged() && route === "engine-routed" && !hasLiveNativeGrant()`, and it — not the engagement — is what `computeProjection` writes as `data-kbf` and folds into the ring trigger. The third clause exists because the route alone under-counts carets by one class: a **bare native text control** (a `TugInput`, a filter field) is granted real DOM focus by `focusKeyView`'s native branch while its route deliberately stays `engine-routed` — dispatch and the watchdog's legality predicate are built on that symmetry — so the paint reads the live grant directly. A granted caret therefore reads as mode-paint-off (caret blinks, no rings anywhere) and a parked stop as mode-paint-on (ring, no caret), with the mode itself unmoved throughout. **The movement stages answer to this division too, and getting that wrong is a caret theft nothing paints** — see [arrow ownership](#motion-two-planes-explicit-commit) for the structural split that gives a live caret its own keys. This is what dissolves the seeded-sheet coexistence without touching the seed rule: a `useSeedKeyView` sheet still opens trap-engaged and caret-holding — a seed is a placement, so the stop grants rather than parks ([P12]) — but the paint no longer contradicts the caret, and the first `Tab` parks and brings the rings up. The ⌥⇥ re-engage carries its own route flip — the gesture parks the granted stop (`toggleKbfManual`'s `parkAtKeyView`), so its paint arrives with the press rather than waiting for a later movement; the ⌘F grant resolves at the moment its route flips, as before. The `data-default-ring` promise is deliberately outside this gate — it names Return's home, not the mode — so a seeded sheet shows exactly a caret plus the default ring, which are the two keys that actually work.

**Accessibility mode is exempt**, as it is everywhere else: Class C grants every text stop a caret with the marks up, so there the pair is legal and `data-kbf` stays projected.

Mechanically, the route is written through one setter (`FocusContext.setRoute`), which repaints on every flip — including the two no placement covers: a grant landing on the *same* key view (`setKeyView`'s unchanged-pair early return skips its reproject) and the watchdog's grant-lost fallback. JS asks the truth question of `kbfEngaged()` (exposed to tests as `__tug.kbfEngaged()`); an assertion about what the user *sees* reads the attribute. The dev-mode backstop is in the caret layer: a painted caret while `data-kbf` is projected records a `kbf-caret-divergence` deck-trace event, the KBF sibling of `caret-responder-divergence`. Pinned end to end by at0397 over the rename sheet — the canonical caret-first seeded surface.

This division replaced three ambient mechanisms that between them decided the same question from DOM state on every keydown — an arrow-release policy keyed on whether a field was empty, a two-press boundary latch at a document edge, and emptiness-conditioned `Tab`/arrow handoffs from a text surface to its host. Each existed to compensate for the absence of a **parked** state, and all three are gone.

Keyboard motion then moves on two independent planes, and **commit is a separate act**:

- **Tab plane (linear).** `Tab` / `Shift-Tab` moves the **key view** through the focusable stops of the current focus mode, in author-declared order. The walk is contained to the current focus mode — it never escapes into another card or a dismissed surface.
- **Arrow plane (spatial).** Within a focused item-group, the arrows move a **cursor** over the members. The order is **author-declared, not geometric** — named rings (closed loops along an axis) and seams between rows, with optional per-node neighbor overrides. A roving cursor never changes the selection.
- **Commit.** `Space` commits the ringed member; `Enter` fires the scope's default (the recommended-default button). **A bare arrow never selects; a modifier-extended arrow is a selection gesture.** On a `multiSelect` list, Shift+Arrow / Home / End EXTENDS the selection to the row the cursor lands on, and ⌘+Arrow / Home / End WALKS the cursor past rows while leaving the selection standing — the pair that makes a discontiguous selection reachable from the keyboard, with `Space` picking up the rows the walk stops on. Either modifier, pressed with nothing selected, first takes the row the cursor is already on: extension names where the cursor LANDS, so without that seed the row the user was looking at when they pressed is the one row the walk can never select. **The seed is the movement key's doing, not the modifier's, and under ⇧ it is the whole press.** A bare `Shift` keydown carries `shiftKey: true` and no gesture at all, so a seed keyed off the modifier would select a row for resting a finger on the key; and a first `⇧↓` that seeded *and* moved would select two rows, which is never what it means. So the seed runs on `Arrow` / `Home` / `End` only, and under ⇧ the cursor stays where it is — ⌘ moves, because it extends nothing and leaves the seeded row the only member.

**`Escape` clears a standing selection first, and the list — not the chain — is what makes that reliable.** Every rung of the Escape ladder sits above the chain's `CANCEL_DIALOG` dispatch, which is the only rung a consumer can register on; so a `multiSelect` list whose surface holds the keyboard mode (rung (6), the Lens's case) would have its selection-clearing Escape spent on leaving the mode, while the same selection made with the mouse cleared correctly. That difference is invisible to the user and unattributable to anything they did. A `multiSelect` list therefore **captures** `Escape` for exactly as long as its set is non-empty (the same `captures` predicate the type-select shadow uses), clears through `multiSelect.onClear`, and hands the ladder back the moment there is nothing left to clear. The other half of the same guarantee is at the root: a selection that outlives the keyboard's presence on the list — the Lens's layout selection survives the click that fronted a card and took the keyboard with it — is cleared by a `CANCEL_DIALOG` entry `deck-canvas` registers CONDITIONALLY, present only while a set stands. Conditional is the whole safety argument: the chain gives a handler no way to decline, so an unconditional root entry would mark every `Escape` in the app handled. An attached filter's query is more local still and keeps its own first `Escape`.

**In the Lens, `Escape` shrinks state in one stated order, and only ever shrinks it.** Filter text, then the layout selection, then focus out of the Lens — one table (`components/lens/lens-escape.ts`), consulted by every handler that can answer the press, and recorded here because the failure it fixes is not a bug in any one handler but a disagreement between them. Two rules make the table hold. **A programmatic focus restore never creates a selection.** The focus-out rung re-activates the card that was fronted before ⌘L, and the deck attacher reads a content-card activation as "the user moved on" and collapses the selection onto it — so the rung that spent the press *made* the set the next press would clear, and Escape alternated between clearing and selecting forever. A restore arms `lensSelectionStore.suppressNextAutoSelect()` before its transfer; the attacher consumes the one-shot on the next first-responder transition. The general form: an activation the user did not perform is not evidence about what they meant. **And "is there a set?" is a question about the set, not about the rows on screen.** A list's `selectedIds` is a projection over its visible rows, so a selection the filter has hidden projects to nothing while standing perfectly well; a consumer whose set outlives its rows answers through `multiSelect.hasSelection` instead, and Escape clears what the user actually has.

**At the base focus mode, `Escape` still asks the key view first.** `captureListener` dispatches a `CANCEL_DIALOG`-matching Escape straight into the responder chain, and it used to do so unconditionally whenever the focus mode was `BASE_FOCUS_MODE` — bypassing the `captures` predicate in the most common state there is: no dialog, no descend scope, just the deck. So a list's "while there is a set, Escape is the list's" claim held inside a popover and not on the plain deck, and which arbiter answered depended on mode state the user cannot see. The capture listener now consults `focusManager.keyViewCaptures` — the same predicate `actDispatchListener` consults — and yields when it captures. One arbitration story for every mode is worth more than the shortcut.

The carve-out is narrow on purpose and the mechanism enforces it. The spatial navigator and the liveliness net both decline a modified arrow, so a selection arrow can only ever arrive at the list's own key-view delegate; a list with no `multiSelect` prop passes ⌘ straight through to the chord layer as before; and ⌃ is never a selection modifier anywhere.

**`Space` and `Enter` are different acts, and a multi-select list may not collapse them.** `Space` TOGGLES the cursor row's membership and stops — toggle rather than replace, because replace would leave the keyboard unable to build a set at all, and with nothing selected the two readings coincide anyway; `Enter` runs the row's default — on the Lens's Cards list, fronting its card. A list that acts on both leaves the keyboard no way to say "this row is what I mean" without also opening it, which is precisely what a selection is for. A row the consumer declines to select (a group header among selectable rows) falls back to the ordinary commit path, so `Space` there still means what it always did.

**The liveliness net is the floor under the whole arrow plane, everywhere — not a property of declared scopes.** An arrow that nothing claims moves the key view one step along the current mode's linear walk order (Down/Right advance, Up/Left retreat, both wrapping, both mode-bounded). It applies inside a declared spatial order, at the edge of a group in a scope that declared none, and on a surface with no order at all — realized in `moveKeyViewSpatial` and in a post-delegate stage of the document keyboard pipeline (`arrowFallbackListener`), which runs after the key-view delegate so descended row scopes and `KeyViewBehavior.onKey` consumers keep their arrows and the net catches only what is genuinely unclaimed.

Two things follow. Declared orders are still where *better-than-linear* movement is authored — the net never overrides a resolvable override, seam, or ring, and dialogs and sheets should still declare one. And the net is genuinely enough for a surface whose linear order *is* its visual column: it carries the ring off the last row of one group into the next for free, with no authoring at all. **Every list registers its cursor handle** for the same reason — the handle is what makes a list's edges visible to the navigator, and the edges are what hand the arrow onward. A list declares its handle **vertical-axis only**: the resolver reads a one-column group as a 1-D run any arrow can step, so without that a Left on a full-width list would mean "cursor up."

**"One column" is a claim about the layout, and the Lens is the cautionary case.** The Lens looked like the net's ideal subject — a rail of stacked sections, walked top to bottom — and rode it for exactly as long as it took someone to press Down on a section band. A band is a **row**: the band, its filter field, the section's own controls, its fold cue, read left to right. So the walk order ran *across* the band before it ran down into the rows, and the net, which cannot tell Down from Right, spent a Down on stepping sideways into the filter field. The section's rows sat directly under the band and Down did not reach them.

The lesson is not that the net is wrong; it is that "my linear order matches my visual column" is a claim to check against the *widest* thing on the surface, not the general shape of it. One row of side-by-side controls anywhere in a column is enough to make the two orders disagree, and the disagreement is invisible until an arrow lands somewhere the eye did not point. The Lens now declares a plane (`lens-spatial-order.ts`): each section contributes a band row and its body rows, `rowGridOrder` does the rest, and one edge is declared by hand — **Left off a body stop returns to its band**, as a *seam* rather than an override, precisely because seams resolve after a group's own cursor (a vertical-axis list declines horizontal arrows and takes it; a horizontal tile group claims them and never sees it). It is also the first order declared on the **base** mode rather than inside a trap, which is legitimate: an order registers on the declaring card's own `FocusContext`, so it governs that card and nothing else.

**A declared plane over a surface that grows should be DERIVED from the registry, not kept beside it.** A hand-maintained table of which stops are on which row is a drift seam whose failure is silent in the worst way: a control left out of it is simply off the plane, `nodeInOrder` is false, the liveliness net catches its arrows, and the surface quietly reverts to linear movement with nothing on screen to notice and nothing in the console to read. So the Lens does not keep one. It reads each section's live focus orders back off the engine (`FocusContext.focusOrdersInGroup`) and splits them by sign — **negative orders are the band's row, non-negative orders are the body's rows, one each** — which is not a new rule but the one the section registry's constants already encode, since the band's stops are negative precisely so they sort ahead of the body's `0`. A control authored into a section's focus group is therefore on the plane the moment it registers, in the position its own order gives it, and adding one costs no edit anywhere else. The residual obligation is the one that exists anyway: **a distinct order per stop within a group**, because two stops sharing an order share a focus key ([Q12]) and the engine resolves a key to exactly one of them.

Deriving it is also why the Lens builds its order in a **layout effect** rather than in render: the sections' own `useFocusable` registrations are layout effects, and a child's runs before its parent's ([L03]), so by the time the parent's runs every band, field, control, and list of that commit has registered. Building it during render would read the *previous* commit's registry.

**Arrow ownership.** A capturing control — a slider on its value axis, a list roving its cursor — keeps its arrows while it holds the key view. A **focused text editor** keeps them for its caret, and in mode OFF it keeps them *unconditionally*: all four directions, at every caret position, whatever the document holds. There is no edge to cross out of and no press to spend crossing it, because in mode OFF there is no ring for an arrow to move.

**A LIVE caret keeps its caret keys in mode ON too, and this is [P07]'s split applied to the arrow plane.** "Is a ring painted" and "is the engine steering" are two questions, and they come apart in exactly the state [the paint route](#kbf-paint-route) exists for: the mode is engaged — a trapped sheet, a Class-B card — and a caret is nonetheless granted, so the marks stand down and the keyboard belongs to the text surface. The movement stages have to answer the second question, not the first. The split is structural, by the KIND of surface:

- **Horizontal** arrows belong to any caret. A text surface has a left and a right, and that is what a caret moves along — the same sentence the attached-list contract already makes for its own reason.
- **Vertical** arrows belong to a **multi-line** surface (contentEditable / `TEXTAREA`), which has lines to move between — including one that is multi-line for *wrapping* rather than for indenting, since a wrapped line is still a line. A single-line `INPUT` has no second line, so its ↑/↓ stay with the plane, exactly as its `Tab` does. There is no `data-tug-tab-release` counterpart here, and there should not be: `Tab` is genuinely ambiguous on a multi-line surface (indent, or leave?) and a vertical arrow is not.

Parking is what hands the arrows back, and it is the whole rule in one gesture: with the ring on a stop and no caret live, the same key that was the caret's a moment ago moves the ring. What this replaced was a stage that gated on engagement alone, so wherever a surface declared a spatial order the engine steered straight through a live caret — ↓ in the question dialog's answer field carried the ring off to a button and took the caret with it, and the ↑ back left the stop *parked*, so a user mid-sentence could not type. Nothing painted at the moment of the theft, which is what kept it invisible for a phase: the state with no marks on screen is precisely the state the engine had no business moving in. Pinned by at0402, which drives both halves against the real dialog.

**In a text editor, plain arrows are caret keys and nothing else.** Command history rides **Cmd-Up / Cmd-Down**, which keep their editing function (`cursorDocStart` / `cursorDocEnd`) and mean history only at the edge they are already moving toward, where that function is a no-op; repeats keep walking, since a recall lands the caret back on that edge. **Opt-Up / Opt-Down** remain the position-independent walk. The rule exists because two overshoots used to share one key: walking the caret up through a draft recalled history the moment it arrived, and holding the key made it certain.

**One exception, and it is declared rather than sensed: the attached list.** A text field may declare that the list beside it is *its* list, by stamping `data-tug-attached-list` on the wrapper holding its input. While the caret is inside, ↑/↓ drive that list's cursor and never leave the field — **in both modes, and regardless of whether the field is empty**. Horizontal arrows are untouched; they are caret keys and a list has no left or right. The field's delegate does the moving (`attachedListMoveCursor`), the commit stays the field's own, and the highlight rides `data-attached-cursor`, which is exempt from the mode gate because it is not a focus position: it is the field's statement about which row its next `Return` means. Open Quickly, the session picker, the resume sheet, Jots, and every Lens section filter work this way, as does every **combo box** — its dropdown is a list beside its field by construction, so `TugComboBox` declares the contract itself whenever that list is open (and in `menuMode` while closed, since there the closed-field ↓ is the gesture that opens it).

**The contract runs both ways, and the upward half is type-select.** Typing at a focused list narrows it — the Finder gesture — **and the list keeps the keyboard**. The field *shadows* what was typed; it does not receive it. That distinction is the whole feature and it is easy to get wrong: the reason to type is to find a row and act on it, so `Return` must still reach the list's cursored row and ↑/↓ must still move it. Granting the caret to the field instead narrows perfectly and then strands the user — the row they were hunting is behind a Tab, and `Return` presses the surface's default with the selection still parked wherever it was before they typed. In the session picker that means typing a session's name and getting an empty new one.

So the field half of the binding is a set of **mutators**, not a focus target: `appendChar` / `deleteBackward` / `clearQuery`. The list calls them and the field writes its own input value and fires its delegate's change notification — the same path a real keystroke in the field takes. There is still exactly one value authority (the `<input>`'s DOM value) and one filtering path, and nothing is mirrored: what the field shows IS the query. After the query changes the list re-seeds its cursor onto the first match, running the same preference ladder the attached cursor's seed runs (`initialSelectedIndex` → selection → first cursorable row) — which is what skips "New session" and lands on a real result.

Three rules make it safe rather than clever. The shadow is chained **last** in the list's `KeyViewBehavior.onKey` — after the list's own movement keys and after the consumer's `onKeyViewKey` — so a list's single-key verbs win by construction and never need an exclusion list (Jots keeps Space for *new jot* and Backspace for *delete jot*), and any verb a list grows later is safe for free. **Escape and Space are claimed only while a query exists**, via the list's `captures` predicate, because the act dispatch resolves both ahead of the key-view delegate: Escape then drops the query and the ladder above it — dismiss the sheet, fold the section — stays reachable the moment there is nothing left to clear, and Space is a character mid-query (so a multi-word title types straight through) while keeping its commit meaning when there is no query, which is why a query can never *open* with one. And a list with no attached filter claims nothing and behaves exactly as it always did.

Both halves come off **one binding** (`useAttachedFilter`, `attached-filter.ts`), handed to the field as `attachment` and to the list as `attachedFilter`. That is deliberate: authored as two independent wires the halves can drift, and a surface wired one way and not the other fails silently in exactly the way the paragraph below describes. For a pair the component tree cannot hold in one place — a Lens section, whose field is in its band and whose list is in its body — the binding is group-keyed in `lens-section-content.ts` instead, beside the handle it already published.

**A field with a list beside it that does NOT declare this is a silent breakage, and the combo box was the worked example.** Nothing errors: the field keeps its caret, the list simply stops answering its arrows, because a bare arrow in an engaged mode belongs to the plane and the plane has no idea the list is there. The session picker's path field spent from the mode's landing until the audit in that state — you could not arrow through the recents at all — and it went unnoticed because the failure is a key that does nothing rather than a key that does something wrong. When a surface pairs a caret with a list, the declaration is not a refinement; it is the thing that makes the pair work. The unconditionality is the whole point — it is what replaced a rule that read the field's contents on every keystroke.

**`Tab` in mode OFF splits by the KIND of surface, never by its content.** A **multi-line** surface (contentEditable / `TEXTAREA`) and anything advertising `data-tug-tab-consume` own `Tab`, because indent and completion-accept are real `Tab` meanings. A **single-line `INPUT`** does not: a plain field has no indent, so a `Tab` there is a request to leave — it engages KBF and takes one step, exactly like the **nowhere** state (an active card with no caret). The split is structural, so it is not the emptiness rule in another costume.

**A multi-line surface may opt out with `data-tug-tab-release`, and only it can.** Some surfaces are multi-line for *wrapping* rather than for *indenting* — the question dialog's free-text answer field is the case: it has no indent to insert and its `Tab` has to reach the dialog's buttons, or the field is a jail with the mouse as the only way out. The declaration has to be **positive**, and that is the correction: the field had carried `tabMovesFocus` from the day it was written, but all that prop did was withhold `data-tug-tab-consume` — and an *absence* cannot outrank a structural rule that never consulted it. The walk now reads `data-tug-tab-release` **before** the kind test, because the surface is the one that knows what its own `Tab` means. Pinned by at0400.

**The engine never hands `Tab` to WebKit.** A `Tab` the walk cannot spend is consumed, with a dev-log warning, rather than yielded: a native `Tab` would land DOM focus somewhere the engine does not know about, which is the state the whole model exists to prevent. An empty walk is a tripwire — some subtree was never authored as engine stops.

**A text stop the engine MOVED to is parked; a seeded one grants.** This is the state the mode restores, and the rule an author cannot derive from "rings exist iff engaged" alone:

- **Arrived at by engine movement** — a spatial step, a linear step, the `Tab` walk — a text stop is **parked**: the ring paints on it, the sink holds `document.activeElement`, and the editor has **no caret**. `Return` grants the caret without typing; a printable character clears the mode, grants the caret, and types itself. While engaged *and* a caret is live in a stop, the stop wears **both** ring and caret.
- **Seeded or explicitly placed** — `useSeedKeyView`, a commit-home seed, a deliberate `realizeTarget`, a pointer placement — it **grants**. A surface that seeds its own key view onto a field is declaring a text-first entry point and must open with a caret. The rename sheet, the resume sheet, the gallery sheet, the attachment preview, and the session question / permission dialogs all do, and every one of them is an auto-engaging trapped surface: an unqualified park rule would open every text-first sheet in the app ringed and unable to type.

The distinction is carried as an **arrival kind recorded on the placement**, never inferred. An inference over "did the key view change by one step" would be exactly the ambient-predicate class the mode exists to delete.

**Engaging the mode is not a movement through it.** ⌥⇥ turns the ring on where the keyboard already is: the stop that holds the key view keeps it, and only a card entered from nowhere — no key view to keep — seeds its first stop. The ring's job is to say where the keyboard IS, so a gesture that engages *and* relocates has answered a question the user did not ask, and left them somewhere they now have to walk back from. The landing is nonetheless a **movement** arrival, so a text stop entered this way parks: from a caret in the composer, ⌥⇥ rings the editor and takes the caret away. That is also what keeps ⌥⇥ a toggle — a live caret makes the gesture re-engage rather than disengage, so the mode could not be turned off from the place it was most often turned on. The park is not the cycle entry's private property: `toggleKbfManual` itself lands it, so the modes with no cycle to enter — a trapped dialog's typing-first field, a Class-B card — ring on the press exactly as a card cycle does.

> **History.** Entry used to seed the **commit-home** unconditionally, from the pre-mode design where ⌥⇥ *started a tour* and a tour needs a starting line. That it silently moved the user's place went unnoticed for as long as it did because the ring it moved *from* was invisible: the composer's editor was still carrying a blanket `outline: none` from the retired "a text editor never wears a ring" axiom, so the only visible effect of ⌥⇥ was a ring appearing on the submit button, which reads as a seed rather than as a jump.

**A flush editor insets its ring, and has to find a box that survives.** An editor filling its host edge to edge — the entry shell's composer, the Text card — has no room outside its box for the standard outset ring, which would paint over the card's neighbours or off its edge entirely. It insets by the ring's own width instead. Where it *draws* is then a question of what covers what, and the answer differs per editor because an `outline` paints in its own element's layer and nothing on an ancestor can lift it above a descendant:

- The **composer** draws on the CodeMirror substrate (`.cm-editor`), not on the stop element, because the substrate is an opaque in-flow child covering the host to the pixel — an outline inset on the host paints underneath it and is never seen.
- The **Text card** cannot use that box either, because `.cm-gutters` is a `position: sticky`, `z-index: 200`, opaque child of it and covers the ring's left segment: the result is a rectangle missing its left side, with its top and bottom edges starting at the gutter's right boundary. So it draws a positioned pseudo-element on the stop itself, in a stacking context on the host, at a layer above the gutter's. That is legal *because it is on the stop* — an `::after` border on an editor's inner box would be the same ring drawn a second way, which the ring language rules out.

All of it is geometry, not policy — the trigger is the same `data-key-view-kbd` every other stop uses, and the rule to carry away is that a flush editor's ring needs a box chosen by measurement, not by analogy with the last one.

**Accessibility mode never parks.** An engine-routed key view there mirrors real DOM focus onto the key-view element, so parking a text stop would put focus on the field's *wrapper* and leave an assistive-tech user with no caret in any field until they typed. Text stops grant exactly as they always did.

> **History — why this doctrine used to say the opposite.** This section read *"a text editor never wears a focus ring, in any state"*, on the reasoning that a blinking caret is a full carrier of keyboard focus and a ring beside it is an illegal state rather than a redundancy. It was broken from three directions — a rule that ringed any editor authored into a focus group; the opposite "fix" that noticed an embedded editor showed no ring and *added* one; and the stop's own `::after` ring on the input-area wrapper, which drew the same rectangle one element up. Each round made the axiom look more load-bearing.
>
> It was right about the state it could see and wrong as an axiom. Because a text stop always granted its caret, there was no caret-less state a ring could mark — and *that* is what forced every arrow reaching an editor either to grant the caret or to be pushed back out, which is what the boundary latch, the empty-input release, and the `Tab`-when-empty handoff all existed to arrange. Restoring the parked state retires the axiom and the compensation network together. The half that was always true survives as the rule above: **a caret-holding editor wears no ring.**

**Three carriers, and the third is the wash.** A surface that holds the keyboard is wearing one or more of:

- the **caret**, when the surface itself has the keyboard and is being typed into;
- the **ring**, on any stop while KBF is engaged — a chip, a cell, a button, and a **parked text stop**, which has no caret precisely so the ring can say where the keyboard is;
- the **wash** — the surface tint an entry shell adopts while the keyboard is anywhere inside it — which says *this composite control is the live one* while the caret inside it answers *where in it*.

They are not exclusive: a text stop wears ring *and* caret while the mode is engaged and the caret has been granted. What is exclusive is the mode itself — in mode OFF the ring is not one of the options.

The wash is what makes a bottom-docked entry legible at a glance in a deck showing several of them: the caret is one blinking hairline and the eye finds the lit panel first. It is the [D122] container/element split applied to a compound control — the wash marks the container, the caret marks the position.

The wash is **not** a substitute for the ring, and trying to make it one is a recorded dead end: when the ring was briefly deleted from the parked text stop, a wash was tried in its place and proved invisible — the resting shell already sits at 65% of the focus surface, so lighting it moved nothing the eye could find. A parked stop wears the ring; the wash keeps its own job. What the wash carries is the shell-level answer — *this composite control is the live one* — and the shell's `data-tug-entry-default` promotion keys on it. The wash keys on the engine mark (`data-entry-keyboard`, `data-key-view` mirrored onto the shell root by observation) and not on `:focus-within` alone, which WebKit withholds in a window that is not key even while `document.activeElement` is correct.

**One entry shell is lit at a time, and the lit one owns `Return`.** With the find bar open a card shows two shells, each with a field whose own keymap owns `Return` — submit in the composer, find-next in the query field. So `Return`'s home genuinely follows the caret, and the button that promises it follows the caret too: the shell holding the caret lights its default button (`data-tug-entry-default`, the same offset ring + filled promotion `[data-default-ring]` paints — dotted if a chord rather than a plain `Return` fires it, [#chord-ring]), and the other stands its fill down to outlined. Two filled accent buttons on screen read as two live controls; exactly one may be. This is deliberately *not* the engine's `persistentDefaultRing`, which is a standing mount-scoped claim on one scope-wide Return-home — two shells would fight over that slot to express a state that is not standing at all.

**A surface that appears on a card joins the card's authored order; it never declares a parallel one.** The session card's ⌘F find bar is the worked example, and it is recorded here because the first attempt got it wrong. The bar's four controls sit at orders 8…11 in the card's one cycle group — between the Z4 toolbar and the Z2 status cells, which is where the bar sits on screen — registered through a second `CycleScope` sharing the card's mode id, with their own row in the card's `rowGridOrder`. The rejected alternative was a private focus group in the base mode: it "worked" in that `Tab` moved within it, and it was wrong in every way that matters — two orders on one card, no spatial order on the new one, and ⌥⇥ walking a set of stops the user could see but could not reach. If a new surface's stops feel like they need a walk of their own, the question to answer is *where in the existing order do they belong*, not *what group should I invent*.

A corollary for anyone writing tests or diagnostics against this: `data-tug-focus-key` is stamped only on stops authored with a group, so several perfectly ordinary stops (the Z2 status cells among them) carry none. Identify a landing by **element**, never by reading a focus key off it.

**A descend is a position, not a jail — and an arrow never beeps.** Once the keyboard has descended into a list row's accessories, every movement key still has to mean something. The vertical arrows carry the ring to the **same accessory in the adjacent row** (the ordinal clamped to what that row holds, since rows are ragged), so a user can run down a column of close boxes the way they run down the rows themselves; `Home` / `End` / `Page` are list gestures, so they **ascend out of the row** and then move the list. At an edge of the **row scope** — the last row, the last accessory — the key is *consumed and nothing moves*. (That clamp is the descended scope's alone. A **list container**'s own edge no longer clamps: the arrow leaves — along a declared seam where the surface authored one, else along the liveliness net — which is what carries the ring from one Lens section into the next.) What is never acceptable is returning "unhandled": the key falls through to WebKit and macOS beeps at a user who pressed an arrow in a list, which reads as the row having swallowed the keyboard. `TugListView` owns this for every list in the app (`handleListKey`, reached from inside a row scope through the engine's descended-scope `onKey` fallback); pinned by at0282, with the horizontal half — Right walks the row, Left off the first accessory ascends — pinned by at0277.

**Per-card key-window model.** Focus contexts are **per card**. Each card owns its own key view, cursor, default-ring stack, scope stack, **and first responder**, like windows in a windowing system; only the active card's context is live.

The first responder is the chain's *single global* register (see [responder-chain.md](responder-chain.md)), but the key-window model makes focus per-card — so card **activation must restore the first responder** alongside the key view, as the fifth per-card axis. The engine does this in `FocusManager.adoptKeyCard` ([P21] activation): it promotes the responder that contains the activated card's key view (a resting card's editor; a sheet's focused control → the sheet's responder). Without it, a first-responder-routed accelerator (Cmd-W `close`, Cmd-. `cancel-dialog`) is dropped on the just-activated card while the engine's Escape ladder — which reads the active context directly — still works. The first responder must NOT be left to ride DOM `focusin`: that does not fire when the activated key view is a focus-refusing control (a dialog button) or when the activation `.focus()` is idempotency-skipped (DOM focus already on target).

## The card's focus destination — one rule

A card has **one focus destination at any moment**, and it is a rule, not an element: the context's **pushed key destination** when it owns one — a pending card-modal dialog's trap (Question / Permission), a mid-flow focus cycle, a descended scope — and the **resting editor** otherwise ([P20]). Every path that places focus "back on a card" must resolve the destination through that rule:

- **Activation** (click, tab switch, pane promotion, cross-pane move, window blur→focus, cold boot) dispatches through `applyBagFocus`, whose first act is `adoptKeyCard`: a context that owns a pushed destination gets its key view focused and the resting-editor claim is skipped.
- **Lifecycle reclaims** — a sheet/banner `didHide` over the card, a pane drag/resize commit (`cardDidMove` / `cardDidResize`, which fire even for a zero-move title-bar click), the body's mount claim — run the same gate before falling back to the editor (the session card consolidates this as `reclaimFocusDestination`).

**A keyboard activation shows its landing.** The modality of a restore is the modality of the *gesture*, never the modality the key view was left with. A keyboard-driven activation (⌘L into the Lens) dispatches its transfer with `modality: "keyboard"`, and `adoptKeyCard` re-asserts the card's retained key view as a keyboard destination (`FocusContext.assertKeyboardDestination`): the position does not move — the key view, including a descended scope, stays exactly where the card remembers it — but the ring paints, the engine reveals it, and the keyboard lands. Without this, a pointer interaction inside the card (a click on a Layouts tile) leaves the retained key view pointer-flavored, and every later ⌘L return is an invisible focus mark — the card activates, nothing lights, and the user has to Tab to find the keyboard. Stale state heals first: a non-trapped descended scope whose key view no longer resolves (its row re-rendered away while the card was in the background) ascends level by level, a dead key view at the base clears, and a keyboard dispatch whose saved snapshot names a target that is *gone* falls through to the default walk instead of arming a ghost — a keyboard activation never ends with the keyboard nowhere, and ⌘L is never a silent no-op. Pointer and lifecycle activations keep the quiet restore: replayed modality, no ring, no scroll ([L23]). Pinned by at0278.

**The activating click drills down.** A click on a card that is not the first responder does two things at once, and it used to do only the first: it activates the card, *and* it lands the keyboard on what it hit. The gesture interpreter classifies it `placement: "place"` and leaves the browser's mousedown default alone when the click lands in a **text surface** — a contenteditable, an `<input>`, a `<textarea>` — because a user who aimed at a field and pressed has already said where they want the keyboard, and asking for a second click on the same pixel is the interface refusing to hear it. Order carries this: the activation transfer runs synchronously at pointerdown *before* any consumer reads the record, so it restores the card's recorded destination and the place that follows moves off it to the click's target.

Every OTHER target keeps the suppression, and that half is what keeps the rule safe. A click on transcript prose is a click on *the card*: the destination it wants is the card's recorded one, not a ring parked on whatever list sat under the pointer — and on genuinely unaddressable content `placeFromPointer` falls through to placing `none`, which would undo the transfer's restore and leave a freshly-activated card holding no keyboard at all. Widening the rule from "a text surface" to "anything the engine can address" is exactly the change that breaks at0201. The mousedown default matters for the same narrow class: CM6 reads `defaultPrevented` and declines to move its selection, so preventing it was precisely what landed the card without landing the caret. Pinned by at0344, bounded by at0201.

A raw "focus the editor" claim is a bug even when it *looks* harmless: under a modal scrim the entry stands down, so the claim cannot move DOM focus — but its **responder promotion still fires**, the chain seed re-points the key view at the editor, and the dialog silently loses its ring and arrow walk while DOM focus sits correctly on the dialog. Symptomless in the DOM, dead to the keyboard.

**The modal barrier covers pane chrome.** While a card is card-modal, a pointerdown anywhere in its pane *outside the bright dialog island* — the scrimmed transcript, and equally the pane's **title bar, frame, and resize edges** — is a stray click: the chain redirects its promotion to the dialog island as a programmatic (non-pointer) promotion, so the seed yields to the dialog's finer key view and the ring survives. Only the pane whose *visible* card is modal participates; a background tab's dialog does not capture its pane. The click still activates the pane / starts the drag — it just never re-places the keyboard.

Boundaries pinned by tests: window blur→focus (at0148), resting-card activation clicks for every click target (at0201). The cross-card case — click away from a modal card and back onto it, title bar and content, both dialog kinds — was at0203's, retired in the 2026-08-11 cull, and is **unpinned**; the modal-barrier rule above is the one to re-derive a suite from if it regresses.

## A stop is a place you can see, and a shade names itself {#shade-focus}

Two rules that a passive shade broke in two different ways, and that generalize past it.

**A stop that is covered is not a stop.** The Session card's shades rise from the entry region's top edge and cover everything above — transcript, header, and the Z2 status bar. History is modal, so the walk is trapped into it and the question never arose; **Changes is passive**, and the five Z2 status cells stayed registered underneath it. Tabbing past the Changes chip then produced five consecutive landings whose ring painted on a covered element: nothing moved on screen, five times, and then the sixth Tab returned to the editor. That is a **ghost tab**, and ghost tabs are always a bug — a stop you cannot see is indistinguishable from a key that does nothing. The cure is never to paint harder; it is to leave the walk. A region that a surface covers **unregisters its stops for as long as the cover is up** (`statusRowFocusGroup` goes `undefined`, which is how a component leaves the walk entirely). The corollary is the test: every Tab landing must paint a mark somewhere in the stop's own subtree, which is what at0399 asserts across the whole live cycle.

**A stop must also be worth landing on.** The History shade's scrolling commit list was a stop, and it earned two rings: the list's own keyboard ring, plus — because the key view was a **non-button** — the persistent default ring the engine then projected onto Done beneath it. Both painted at once. The list had no act of its own; it is a reading surface, and what it should mean to Tab into one is a real question with no answer yet. So it left the walk, Done became the shade's seeded key view and its only stop, and Done's single ring now says both *where the keyboard is* and *what `Return` does*. **One keyboard, one mark.**

**A shade signal carries the shade's NAME, never a boolean.** `data-shade-open` stood the composer's default ring down on the premise that "the shade owns the default". That is true of History, which has a Done; it is false of Changes, which has no Done at all and whose act — the commit — is performed by the **composer's own Z5**. The bare boolean took the ring away and gave it to nobody, which is why the Changes Z5 wore none. The attribute now reads `"history"` / `"changes"`, the stand-down keys on `="history"`, and commit mode's Commit button declares `data-tug-entry-default` with its `shift` chord exactly as the prompt route's submit does — the two are never co-mounted, so exactly one entry default lights ([#chord-ring]). The general form: when a signal is read to answer *who owns something*, a boolean can only ever assert that **someone** does.

**A yielded default yields the KEY, not just the ring.** The stand-down above answers who *wears* the default ring while a shade is up, and answering it in paint alone is half an answer. History's carve-out deliberately leaves the composer live beneath the shade, and the composer's shipped Return is the `newline` setting — so a Return with the caret back in the composer broke a line while the only ring on screen said Return dismissed the shade. The editor substrate's default-button defer ran on the `submit` branch alone, which is precisely the branch that setting never takes. So the host that gives the ring away also gives the key away: `TugTextEditor`'s `defaultButtonOwnsReturn` makes a plain Return consult the pane's default button under `newline` too, and the Session card drives it from the same `shadeView === "history"` state the CSS stand-down keys on — one state, both halves, no way to move one without the other. The button's declared chord still governs at this site as at every other ([#chord-ring]): a plain Return presses a chordless button and nothing else, so the composer's own Shift+Return submit can never be fired by the key that writes a line, and the newline comes back the instant the shade closes. The general form: **a mark that says what a key does is a claim about the key, and it is the surface's job to make the key true from wherever the keyboard is** — including from a surface it deliberately left live.

Pinned by at0399.

## No dead surface inside a text substrate

A text editor's interactive surface is its **host**, not its content box. CM6 owns pointer selection and (previously) drag acceptance only within `contentDOM`, which is content-sized — so a host taller than its content (the Dev prompt opens at a min-height) had a blank band that *looked* like editor but ate the caret on click (WebKit's mousedown focus default blurred to body) and refused file drops. The rules:

- **Clicks land the caret.** A primary-button mousedown anywhere inside the host that no finer surface claims (content → CM6 selection, gutters → line select, scrollbar band → native) focuses the editor and lands the caret at the nearest document position (`host-click.ts`). The band advertises `cursor: text`. A read-only editor (the prompt stood down behind a card-modal dialog) claims nothing.
- **Drags target the host.** The drop extension's listeners ride the host (`drop-extension.ts`), so the accept ring and drop caret work over the whole editor, blank band included.
- **A composite entry is ONE drop surface.** The prompt entry layers one entry-root set of drag handlers over its chrome (attachment strip, toolbar, status row); the substrate claims drags over the editor first (`defaultPrevented` is the layering contract), and everything else routes into the same editor pipeline, cued by the editor's own ring + drop caret at the clamped nearest position. Help the drop land — never make the user hunt for the magic pixel.

Unpinned since the 2026-08-11 cull retired at0204, which drove both halves (a blank-band click keeps the caret; drops accept on the band and on the toolbar).

## Drag and the keyboard

**A drag is a content gesture, not a focus gesture — on both ends.** Starting a drag does not activate the card the drag starts in; dropping does not activate, focus, or move the key card of the card the drop lands in. A drag from an inactive card leaves it inactive. A drop into an inactive card inserts the content and leaves no caret behind. A drop into the key card inserts at the drop point and the caret follows only because focus was already legitimately there. No drop handler may call `activateCard`, `setKeyCard`, `place()`, or a raw `.focus()`.

This is the platform's rule, not ours to reinvent. Apple's HIG says content should be draggable from inactive windows "without necessarily bringing those windows to the front," and dropping from an active window into an inactive one leaves activation and focus on the source. The WHATWG drag-and-drop model specifies no focus or activation semantics at any point in the drag; the `drop` default action for an editing host is to insert the data "in a manner consistent with platform-specific conventions" — the web defers to the platform, and our platform is macOS. Our handlers `preventDefault()` and perform insertion themselves, so no per-browser default focus behavior runs: the outcome is entirely ours, and it is *insert without focusing*.

**A carry suppresses the movement cursor's bar.** While a block reorder is in flight, the container declares `data-tug-carrying="true"` and the cursor's leading-edge bar stands down until the drop. This is the language's one appearance exception, and it is narrow on purpose: the mark only stands down, it is never *moved*, because nothing about the keyboard has changed — the key view is exactly where it was and the bar is back the moment the gesture ends.

It exists because a drag introduces a mark of its own in the same hue, the drop caret, answering a different question. The focus marks answer *where is the keyboard*; the caret answers *where will this land*. The cursor bar is a stripe of accent along the leading edge of a row the carry may be about to move — mid-gesture it reads as a mark on the drop, pointing at a row that has nothing to do with where this will land. A drop the user cannot aim is worse than a focus mark they can reconstruct in a keystroke, and here they need reconstruct nothing: the keyboard's answer is unchanged throughout and is drawn again at the drop, on whatever was set down.



The attribute is a **declared** state, in the `data-tug-*` family with `data-tug-placement` and `data-tug-focus`: the carrying host stamps it, and the components inside read it. `useBlockReorder` is the only writer; `TugListView`'s stylesheet is the reader, because a container's focus marks are the container's to draw (see the authoring contract below) and a host must never hand-roll the suppression against a component's internal focus attributes.

**A carry ends with the keyboard on what was set down.** This is not an exception to the rule above it, because a carry is not that kind of drag. The content-gesture rule governs a **payload** moving between surfaces — a jot's text into a session prompt, a file onto an editor — where the platform's answer is that the destination does not come forward. A carry moves the surface's **own furniture**, inside one list, inside one card, and its whole subject is the block under the pointer. Nothing crosses a card boundary, and nothing activates: the placement passes no `activation`, so a carry inside a background card only *records* and moves no focus at all.

What it restores is a landing the gesture itself suppressed. A press on one of these surfaces normally places the keyboard on it — a band click focuses its section's list, a row press moves the list's key view — and a carry cancels both halves of that on purpose: the arm cancels the pointerdown, and the drop swallows the trailing click so a drop is never read as an activation. Without an explicit landing, a carry is the one gesture on the surface that leaves the keyboard nowhere. So `useBlockReorder` takes a `landKeyboard` callback and calls it the moment the commit lands — after the settle's keyframes are measured, so a placement free to scroll cannot move the ground they were computed from, and **before** the settle plays, because where the keyboard is must never wait on an animation ([L13] keeps the two separate; a window that is not in front plays no motion at all, and its drops must still land the keyboard). It fires on every release, changed order or not, and **never** on an Escape abort: a gesture the user took back must not leave the keyboard somewhere new. The callback belongs to the surface, because only it knows what focusing a block means there (a section places on its own focus key; a list moves its movement cursor), and it places through `place()` like everything else ([L22]).

**Pointer selection commits on pointerdown.** A list moves its committed selection — the `data-selected` fill, the delegate's `onSelect` — on `pointerdown`, not on `click`, exactly as `NSTableView` selects the row a mousedown lands on and then drags what it selected. Click-gated selection makes selection structurally unreachable from any gesture that becomes a drag (a drag fires no `click`) and from any first-click-activates gesture (the activation `mousedown` `preventDefault` eats the `click`). The click path stays as an idempotent fallback for synthetic clicks that arrive with no preceding pointerdown — `Space` on a focusable child inside a cell bubbles one — but pointerdown is where selection is decided.

**Activation defers for gestures on draggable content.** The Mac "first click activates" convention is implemented by `preventDefault()`ing the activation `mousedown`, and a `preventDefault`ed mousedown is also the browser's signal *not* to begin a native drag — so a naive activation click swallows the whole first drag. The gesture interpreter therefore resolves the ambiguity the way macOS does, after mousedown rather than at it: a `pointerdown` inside a `[draggable="true"]` element in a non-active card **arms** a pending activation instead of committing one and skips the `preventDefault`; a `dragstart` **cancels** it (the gesture is a drag — the source card stays inactive, macOS background-drag semantics); a `pointerup` **commits** it, running the same activation transfer the synchronous branch runs. The two endings are mutually exclusive by construction: once a native drag begins the browser ends the gesture with `dragend`, never `pointerup`.

Two consequences are intended, not accidents:

- A plain click on a draggable row in a background card raises the pane on pointer**up**, not pointerdown — the same as clicking an icon in a background Finder window.
- Because the gesture keeps the browser's mousedown focus default, the browser walks up from the click target and focuses the nearest tabindex'd ancestor — the background card's container. The watchdog corrects it, but **quietly**: this is browser churn from a gesture the engine deliberately let through, not a raw focus write by our code, and ledgering it as a steal would warn on every drag about a writer no author could fix. The engine knows the window is open because the interpreter opens it (`beginDeferredGesture`) and closes it when the gesture resolves.

**The first click after a native drag has no `pointerdown`.** A native drag session consumes the pointer stream's release: WebKit's pointer-event state machine still holds the pointer "down" when the drag ends, so the next press emits only `mousedown` (its release delivers the catch-up `pointerup` that re-syncs the machine). Every pointer-gesture layer in the deck — activation classification, chain promotion, engine placement, list selection — rides capture-phase `pointerdown`, so without correction the entire first post-drag click is invisible: no activation, no selection, no caret. The gesture interpreter heals the stream in one place rather than teaching every layer a mousedown fallback: a trusted primary `mousedown` with no preceding `pointerdown` synthesizes the missing `pointerdown` on the same target, synchronously, before any other mousedown listener runs. Authors must not add per-component mousedown fallbacks for this case — the healed stream is the contract.
- **Chain promotion defers with activation.** The responder chain's `pointerdown` promotion is skipped for the same gestures — draggable content in a non-key card — because the deferral would otherwise split the registers: the chain first responder would land on the drag source while the deck first responder stayed on the key card, mis-routing the next accelerator. If the gesture resolves as a click, the activation-moment settlement ([P21]'s framework half, `settleFirstResponderForActivation`) owns the chain register, which is its designed job; if it resolves as a drag, nothing was touched and the outgoing card's registers are undisturbed.

## The contract — engine attributes → CSS

For any focusable, the engine projects these attributes; CSS reads them ([L06]). Components do not invent their own focus attributes.

| Attribute | On | Renders |
|-----------|----|---------|
| `data-kbf` | `<html>` | nothing directly — it is the **mode gate**. Present iff KBF is **painting** — engaged with no caret granted ([#kbf-paint-route]). CSS reads it only as `html:not([data-kbf])` suppressions, anchored on `html` so they outrank the item-group rules on specificity |
| `data-key-view-kbd` | a **leaf** | ring (role) + faint behind-tint (role) |
| `data-key-view-kbd` | an **item-group container** | nothing — the leaf ring is suppressed; the cursor item carries the whole mark |
| `data-key-cursor` | an **item** in a chip group | ring (role), offset so it survives atop a fill |
| `data-key-cursor` | an **item** in a full-width row container | leading-edge **bar** (`--tugx-focus-cursor-bar-*`), shared by list and accordion |
| `data-selected` / native checked-active state | the component | the component's **native fill** in the role color |
| `data-default-ring` | a button | the recommended-default ring (engine-owned; one per scope). Its **chord variant** is `data-default-chord` on the same button — component-owned, never engine-owned ([#chord-ring]) |
| `data-mods` | `<html>` | the modifiers physically held, space-separated. Read only by the chord ring, as `[data-mods~="shift"]` ([#chord-ring]) |
| `data-key-within` | a container that is **not** an item-group | the quiet "contains the active control" outline |
| `data-key-within` | an **item-group** (descend target or not) | nothing — suppressed |
| `data-tug-tab-release` | a **multi-line text surface** | nothing — it is a **contract**, not appearance ([L24]): "my `Tab` is not mine". Read by the walk ahead of the surface-kind test, and the only way a contentEditable gives `Tab` back |
| `data-attached-cursor` | a row of an **attached list** | the same leading-edge bar the movement cursor draws — and **exempt from the mode gate**, because it is a text field's statement about which row its `Return` means, not a focus position |

**`data-key-view-kbd` means "a ring is painted here", not "the key view is here".** It is withheld outright in mode OFF — and while a caret is granted ([#kbf-paint-route]) — which is how the gate stands ~40 component selectors down at once with no cascade change — prefixing the paint rules with `html[data-kbf]` instead would raise the leaf rule above every item-group suppression and repaint the double ring this language spent three attempts removing. The **unflavored** `data-key-view` is the position record and is stamped in both modes; every behavioral reader uses it, and so must any test asking *where is the keyboard* rather than *is a ring painted*.

`data-key-cursor` and `data-key-within` are the other way round: they carry position and containment truth in both modes, so in mode OFF their **paint** is suppressed rather than their attribute withheld. `data-default-ring` is exempt from the gate entirely — it is a promise about `Return`, not a focus position — and so is its chord variant, for the same reason.

The item-group row above is not a gap. For a chip group the mark reaches the container only as a transient artefact: `data-key-within` lands on the container a scope was descended *from*, a chip group's items are never descended into, and a trap re-pushed while the key view is already inside it captures the group before the on-open seed moves the key view away. For a descend target the mark is real but wants no stroke either. Leaving either to the global rule is not neutral — that rule is an outline, so the group would ring, which would put the retired container mark back on the app's least important state. Every item-group therefore names both attributes in one `:is([data-key-view-kbd], [data-key-within])` suppression.

**A descend goes deeper into a container, not out of it.** When the keyboard descends from an item-group onto a control inside one of its items — a list row's accessories, an accordion section's content — the container drops the key view and wears `data-key-within`. What says the control still belongs to that group is the **cursor mark holding its place** on the item that was descended from: `TugListView` and `TugAccordion` keep their cursor bar up through the descend (the same `:is([data-key-view-kbd], [data-key-within])` selector that suppresses the container mark also gates the bar), so the descended control is always addressed by a lit item above it. A lone ring on an accessory with nothing lit around it is a control with no address.

Role resolves from a prop (or a validation class) to the matching `--tug7-…-filled-{role}-*` family; default `action`. The geometry/color knobs are the `--tugx-focus-*` tokens.

## One writer, one interpreter, one truth

The engine has exactly **one focus-write primitive**: `FocusManager.place(cardId, target, opts)`. A placement records the card's `FocusTarget` (a serializable descriptor: a focusable id, a stable `group:order` focus key, a `data-tug-state-key`, a responder, the card's engine surface, or none) and — iff that card is the key card — realizes it transactionally: the target is **resolved first** (the named focusable registered and rendered, the responder reachable, the state-key element connected), and only a resolvable target commits key view, route, and focus in one pass. An unresolvable target returns `unrealized` and changes nothing — a ring is never lit over a destination that is not there. A claim for a background card records (and caches its key view for the [P20] activation restore) but moves nothing. The persisted `bag.focus` is just the serialized target, so restore, activation, tab switch, and cmd-tab return are the same operation; a keyboard placement naming a not-yet-mounted focusable realizes declaratively when the matching focusable registers.

**One interpreter — who may classify a pointer gesture.** `gesture-interpreter.ts` owns every document-level pointer listener in the deck (the post-drag resync shim, `pointerdown`, `mousedown`, `pointerup`, `pointercancel`, `dragstart`, `dragend`) and classifies each gesture exactly once into a `GestureClassification`: where it landed, whether it activates / defers / deselects / does nothing, whether the chain promotes from the target or a redirect, whether the engine may place, whether the paired mousedown's browser focus default is prevented, and the named reasons behind each. Consumers — the pane-focus controller, the responder chain, `TugListView` — **read** that record; none re-derives a gesture fact from the event. Four independent walks that had to agree by hand is what produced activation `preventDefault` killing native drags, a gate that refused the engine's own sink, and a cross-module one-shot latch handing placement suppression between modules. Consumers reading one record cannot disagree, and registration order stops being a correctness input.

Two consequences authors must uphold: a surface that wants a gesture-level policy **declares** it (`data-tug-placement="suppress"` on chrome whose clicks must not move the key view, re-declared `"place"` on the surface inside it that must; `data-tug-focus="refuse"`; `data-tug-fr-preserve`; `data-no-activate`) rather than installing its own document listener to intercept the stream. And the interpreter's listeners must fire first: they register from `usePaneFocusController`'s `useLayoutEffect` in `deck-canvas.tsx`, a *child* of `ResponderChainProvider`, and child layout effects run before the parent's. Moving the install site into the provider would silently invert the order.

**Deselect is a deliberate classification.** A pointerdown deselects only when its target **is** the deck canvas's background element (`data-deck-canvas-background`, matched by identity, not containment). A gesture that merely misses every pane — a portal gap, an overlay seam, geometry below the fold — classifies as chrome and changes no activation. Deselect used to be the *absence* of a pane under the pointer, which made a click that missed silently clear the active card.

**The router is the target, not `document.activeElement`.** Keys dispatch from the engine's `FocusTarget`; DOM focus is a peripheral the engine points at one of two places, derived from the target's class — the **route**:

- **`engine-routed`** — every non-text target (buttons, lists, tab bars, chips, containers). The engine parks `document.activeElement` on the **key sink** (`[data-tug-key-sink]`, a visually-hidden always-mounted register rendered by the provider; a focus-jailing surface hosts its own sink inside the jail, and the engine parks at the innermost). Keys reach the component through the key-view delegation channel (`KeyboardRoute`, `KeyViewBehavior.onKey`), not through element keydown handlers — an engine-routed element under the sink never sees its own `keydown`. The park is hygiene, not a routing precondition: keys route from the target whether or not the park has landed. Focus resting on the sink is the **engine** holding the keyboard, never the user focused on a control — every consumer that classifies `document.activeElement` must treat it that way. `FocusManager.mayClaimActivationFocus` counts a parked sink as nothing-to-steal, like `<body>`: an activation click that finds the sink under `activeElement` proceeds to its focus dispatch and lands its caret in one click instead of stranding with settled registers. A live engine keyboard behind the park — a ringed list mid-arrow-walk — is protected downstream instead: `resolveBagFocus` resolves to `none` when the engine already holds the target card's key view, so a permitted dispatch realizes the recorded target ([P20]) and its generic default-focus walk can never displace a live ring (the walk would land on the first tabbable — a section's filter input — and yank the ring off the list the same gesture just placed it on).
- **`dom-granted`** — text surfaces only: a responder with a registered **focus contract** (the CM6 editors), or a `state-key` / engine-surface target. The engine GRANTS real DOM focus (contract first, generic walk second, always `preventScroll`) and stands back; the surface owns its caret, selection, and IME.

The **repealed rule**: "every ringable stop must be DOM-focusable" is dead, and with it the tabindex sprawl. Engine-routed stops render **no `tabindex`** — the ring is the engine's promise that keys route there, not that the element can hold DOM focus. (WebKit's mousedown default focuses any tabindex'd ancestor; not rendering one removes that steal class by construction.)

**A ring nobody can see is not a focus mark — the engine reveals.** Focus writes still never let the *browser* scroll (every grant passes `preventScroll`, because a browser auto-scroll is an unbounded write on a scrollport the engine does not own). The engine instead performs the reveal itself, explicitly, whenever a **keyboard** key view changes: `revealFocusTarget` (`focus-reveal.ts`, called from `setKeyView`) walks the new key view's scrollable ancestors innermost-out and scrolls each by the *minimum* delta that brings the target inside — clearing any sticky header currently stuck over the port's top band, leaving room for the ring's outside-the-border-box halo, and releasing follow-bottom through the scroller's registered `Scroller` façade first so SmartScroll's next pin cannot yank the reveal back to the live edge. It is self-gating: an already-visible target produces no writes, so the reveal costs nothing on the common move. Two exclusions are deliberate — a **pointer** key view is not revealed (the user just clicked it; it is by definition on screen), and a `preventScroll` placement suppresses the reveal, because a reactivation-class restore must leave the user's scroll position exactly where they left it ([L23]). Surfaces therefore stop hand-rolling per-dialog reveal effects: a stop that can be reached by keyboard is a stop the engine will show.

**Raw `.focus()` is legal only inside a granted window.** A substrate may claim its own surface (CM6 `view.focus()`) while its responder's focus contract makes it the dom-granted target — the engine legalizes that claim (`focusin` promotion, key-card-gated). Everything else — every "put the keyboard somewhere" write — routes through `place()`. There is no legal raw focus write to an engine-routed element.

**Grants are idempotent.** No engine-realized grant may call `.focus()` on a surface that already contains `document.activeElement`. WebKit drops focus to `<body>` when an already-focused contenteditable is re-`focus()`ed, so a redundant grant does not "reassert" anything — it destroys the state it was meant to restore, and the watchdog declines to correct `<body>`. The guard belongs in the substrate that owns the view (`paintMirrorAsActive` guards on `view.hasFocus`), not at each call site, so every engine-hook consumer inherits it; the selection and scroll re-asserts that follow a grant are already idempotent and stay unconditional. This is why an engine `place()` may keep invoking the hook unconditionally: the hook is safe to re-run.

**One truth — the DOM is a projection, not a second model.** Every focus mark (`data-key-view`, `data-key-view-kbd`, `data-key-within`, `data-focus-mode`, `data-default-ring`) **and** the one legal `document.activeElement` are computed together by a single pure derivation over engine state (`computeProjection`) and applied by a single convergence pass (`reproject`, diff-then-write). Projection is **state-driven, not transition-driven**: any caller may reproject at any time and the DOM converges to the model. This is what makes a transient key-card change harmless — the marks are an image of state, not a residue of the transitions that wrote them, so a card that goes away and comes back derives the same record it started with. Authors never write a focus mark; mutate state and let the projection follow.

**The watchdog is the reconciler.** `checkFocusInvariant` runs the same derivation the projection does, in two registers. It first heals the **marks** — reprojecting whatever drifted — **quietly** (`debug`, never the steal ledger): mark drift is our own missed transition, and ledgering it would blunt the budget assertions the app-tests rely on. It then enforces the **register**: it computes the one legal `activeElement` for the current route (engine-routed → a sink; dom-granted → the granted surface by containment; accessibility mode → the key-view element itself) and **reasserts** it when an illegal element holds it — re-park, re-grant. Every register correction is attributed in the **steal ledger** (`getFocusInvariantReport().steals`, offender → count, surfaced in the dev panel and budget-asserted in app-tests): any `warn`-level steal is a bug in the writing code, never noise to suppress. Browser focus landing on the engine's own stop (a clicked key view) is corrected quietly (`debug`) — ring and router agree; only the register was off.

**Corrections never fail silently.** A correction the watchdog wanted to run but could not — most concretely, a re-park that finds no `[data-tug-key-sink]` to park on and returns `false` — records a `warn`-level ledger entry naming what it wanted to do and why it couldn't. A watchdog that classifies a steal correctly and then no-ops without a trace converts a caught bug into an uncaught one: that is exactly how an illegal caret survived a correctly-detected steal. The ledger is already surfaced in the dev panel and budget-asserted in app-tests, so a failed correction becomes a test failure for free.

**The reconciler's carve-outs are named contracts, not undocumented exceptions.** Four survive, and each is a rule with a reason:

- **The deferred-gesture window.** While the interpreter has parked a gesture's activation (draggable content in a background card), the browser's own mousedown focus default is deliberately let through, so the focus move it produces is corrected **quietly** — browser churn from a gesture the engine chose not to prevent, not a raw write any author could fix. The window opens and closes with the gesture (`beginDeferredGesture` / `endDeferredGesture`), and the interpreter is its only caller.
- **The reassert budget.** A bounded number of corrections per settled state, so the reconciler stands down instead of fighting a peer focus enforcer (a Radix `FocusScope`) at event cadence. Exhausting it is itself a `warn` — a stand-down is reported, never silent.
- **Standing legality classes.** A park on any sink, a bare native control, and `<body>`/`null` are legal without further inspection: the first two are the engine's own registers, and the last is the transient the browser leaves behind between writes.
- **The chrome allowlist.** `data-tug-chrome="non-focus-capturing"` is the one DOM input to the activation-permission query — chrome that holds DOM focus without meaning to own the keyboard. It shrinks as the interpreter models more chrome gestures; it never grows to describe new element kinds.

**Activation permission is an engine query.** Whether an activation may claim focus is answered by `FocusManager.mayClaimActivationFocus(cardId, deckState)` from engine state — deck focus and focus-destination status, the key card, the target card's recorded target and route, plus the one allowlist above. It replaced a nine-branch taxonomy of element kinds that tried to enumerate "configurations where DOM focus is really the engine": every branch was a place for the DOM model and the engine model to disagree. Refusal remains the default and logs its reason at `debug`, so a refused activation is diagnosable without a scratch test.

**Accessibility: focus-follows is the primary screen-reader mechanism.** In `accessibility` keyboard-access mode ([P10], `keyboardAccessStore`, tugbank-backed, host-switched by the Swift side's `NSWorkspace.isVoiceOverEnabled` observation via the `voiceover-changed` control frame), the engine grants real DOM focus to every engine-routed key view — the element regains a `tabindex="-1"` at grant time, the mirror tracks every key-view move, and the watchdog's legal set becomes the key-view element. Real focus on real widgets is the one pattern every assistive technology handles; the sink is never focused while a key view exists. The sink itself carries a quiet `aria-label`, no `aria-activedescendant` (invalid from a sibling), and is never `aria-hidden` (a focusable element must not be).

Consequences authors must uphold:

- **Never pair a paint half with a focus half by hand.** The historical `setKeyView(id, true)` + `focusKeyView()` shape is exactly the drift class this design removed; call `place()`.
- **Never handle keys on an engine-routed element.** Element-level `onKeyDown` on a stop under the sink is structurally dead code; declare a `KeyViewBehavior.onKey` (or a list's `onKeyViewKey` delegate) instead.
- **Never render a `tabindex` on an engine-routed stop.** Focusability is granted (accessibility mirror, dom-granted surfaces), never declared statically.
- **Never grant focus to a surface that already has it.** Guard the `.focus()` in the substrate on the surface's own focus predicate — see "Grants are idempotent" above.
- **Never claim focus from a drop.** A drop inserts content; it does not activate, focus, or move the key card — see "Drag and the keyboard."
- **The ledger is permanent.** Treat any attributed steal as a bug in the writing code path; fix the writer, never widen the legal set.

Enforcement is the watchdog + ledger, the pinned app-tests (at0246 boot honesty, at0247 relaunch, at0250 steal trap, at0252 accessibility mirror — the dialog-budget case was at0251's and is unpinned since the 2026-08-11 cull), and reviewer judgment against this section — deliberately **not** a lint rule; a mechanical checker must never gate correct code, and the watchdog sees actual drift (including from browser defaults no lint could model).

## Known edges — load-bearing assumptions with no tripwire

These are not open bugs. They are the places where the one-interpreter / one-truth design rests on an assumption that nothing currently *checks*, recorded at the close of the rework that established it so a future focus bug has somewhere to look before the investigation starts from scratch. Each names the assumption, the shape of the failure if it breaks, and the direction of the fix. If you are debugging a focus or gesture problem and the cause is not obvious, read this list first — the failure modes below are quiet by construction.

- **Interpreter-before-consumer ordering is positional, not enforced.** The whole "consumers read, never re-derive" contract depends on the interpreter's listeners firing before every consumer's, which holds only because `installGestureInterpreter` runs from `usePaneFocusController`'s layout effect in `deck-canvas.tsx` — a *child* of `ResponderChainProvider`, and child layout effects run before the parent's ([L03]). Nothing asserts this. Hoisting the install site into the provider (or into any ancestor) inverts the order silently: consumers would read a stale record or `null`, and `promoteOnPointerDown`'s no-interpreter fallback would mask the breakage as "promotion works, placement doesn't." **Symptom to watch for:** clicks promote the responder correctly but never move the key view. **Fix direction:** a dev-mode assertion in the provider's effect that the interpreter is already installed.

- **The gesture record outlives its documented lifetime after a synthetic mousedown.** `currentGesture()` is documented as `null` between gestures, and the pointer-up / drag-end / cancel handlers clear it. A `mousedown-only` classification (the record the interpreter synthesizes for an untrusted synthetic press it deliberately does not heal) has no paired `pointerup`, so that record stands until the next `pointerdown` replaces it. No live consumer reads outside a pointerdown, so nothing is broken today — but a future consumer that reads the record on a later event would see a stale gesture and believe it. **Fix direction:** clear on `mouseup` as well, making the documented invariant literally true.

- **`preventMousedownDefault` is the last DOM taxonomy in the interpreter.** Its branch tree still enumerates surfaces — card host exempt, sheet exempt, pane chrome prevented — because it is a faithful union of the two listeners it replaced, and preserving that behavior exactly was worth more than generalizing it. It is now in one place with named reasons, which is the improvement. It is still the one classification stage that answers "what kind of element is this?" rather than "what did the author declare?" **Rule going forward:** if it needs another branch, that is the signal to invert it into a declared attribute the way placement policy became `data-tug-placement` — do not add the branch.

- **The jots editor's placeable re-declaration is one-shot and depends on another component's DOM.** The jot row's chrome declares `data-tug-placement="suppress"`, and a mount-time layout effect re-stamps `"place"` on the CM6 root inside it so clicks in the *text* still place. That stamp runs once and targets an element `TugMessageEditor` owns. If the editor ever recreates its CM6 root, or mounts it after that effect, the marker is gone and clicks in the jot text classify as suppressed. **Symptom to watch for:** the caret stops following clicks inside an open jot while clicking its chrome behaves correctly. CM6 does not normally recreate its root, so this is latent rather than live.

- **Two notions of "the front card" coexist inside one classification.** The activation decision reads `store.getFirstResponderCardId()`; the draggable-background promotion skip reads `getFocusManager().keyCard()`. They agree in every reachable state today (a deselect nulls both), and keeping the key-card predicate was a deliberate choice to preserve Cmd-drag behavior exactly. They are nonetheless two sources for one question, inside the module that exists to end that pattern. **Symptom if they diverge:** a gesture whose activation defers while its promotion runs eagerly — the chain first responder lands on the drag source while the deck first responder stays behind, mis-routing the next accelerator.

- **Two seams from the founding diagnosis are still open, by decision.** The default-focus **claim** still walks the DOM selector chain; only the first-responder settle resolves from the engine's focusable registry. Routing the claim through the registry as well is a behavior change, not a refactor — the registry head of a button-class card is nameable, so the card would acquire a key view merely by coming forward and the first `Tab` would advance *past* its first authored stop. And leaf acts are still synthesized by forwarding the keydown to the key-view element (`deliverToEngineLeaf`) rather than invoked from a declared act contract on the focusable. Both are known, both are deliberate, and both are where "engine-shaped, not DOM-shaped" has further to go.

## Authoring contract

Building a control or surface that participates in the language:

- **Appearance is CSS only** ([L06]). Style focus/selection by selecting on the engine attributes above. Never drive a focus style from React state.
- **Author controls into a focus group.** Give every focusable a `focusGroup` (the enclosing surface's group) and a `focusOrder`; that is what puts it in the `Tab` walk and the spatial plane. A control with neither is a native-only stop and will read as "Tab skips it."
- **Seed the opening key view** with `useSeedKeyView(\`${group}:${order}\`)` — the field for a form, the list for a picker, the default button for a button-only surface. For a Radix-trapped dialog, prefer `onOpenAutoFocus` → `event.preventDefault()` + `focusManager.armKeyboardRestore(...)` so the engine, not Radix, owns the seed.
- **Mark the commit button** with `persistentDefaultRing` (and `primary` emphasis) so it holds the default ring and owns `Return`. Danger confirmations seed the default on **Cancel** so `Return` can't fire a destructive action. Gate the flag when the surface's `Return` is consumed elsewhere mid-flow (a wizard whose options commit on `Return`): the ring must light only when `Return` truly fires the button — see "Buttons" above.
- **Never focus the resting editor directly from a lifecycle trigger.** Any reclaim that can fire while a card-modal dialog is pending must resolve the card's focus destination through the [P20] gate (`adoptKeyCard`, or the session card's `reclaimFocusDestination`) — see "The card's focus destination — one rule."
- **Declare the arrow order** with `useSpatialOrder(rowGridOrder([...]))` (or a hand-built `SpatialOrder`) wherever the movement should read better than linear — which is every dialog, sheet, and alert, and any surface with rows of side-by-side controls. A surface whose walk order already matches its visual column can rely on the liveliness net instead, but check that claim against the widest row on the surface before you make it — see the Lens under "Motion" for how quietly it fails. For a **dialog/sheet/alert**, the `useSpatialOrder` call must run **inside** the trap's `FocusModeScope` — mount a small null-rendering registrar there (see `AlertSpatialOrder` / `ConfirmPopoverSpatialOrder`); calling it in the component body binds the order to the mode *above* the trap ([L03]).
- **A text field beside a list declares the attached-list contract, in both directions.** Build the pair with `useAttachedFilter(() => listRef.current)` and hand the one binding to both participants — `attachment` on the `TugFilterField` (spreading `binding.delegate` into its delegate) and `attachedFilter` on the `TugListView`. Never reach for anything that inspects the field's contents: the declaration is what makes ↑/↓ drive the list from the caret in both modes, and it is the sanctioned replacement for every "when the field is empty…" rule. Taking both halves off one object is also what keeps a site from wiring the downward half and silently omitting the upward one. The upward half is type-select and **must not move the caret** — see the exception above for why.
- **A typing-first trap passes `kbf: false`.** A surface that traps the keyboard auto-engages KBF, which is right for a surface made of engine stops and wrong for one whose caret is the point. `TugModalInputDialog` (Open Quickly) is the one such surface today (`tug-modal-input-dialog.tsx`, the `kbf: false` on its trap); the next typing-first HUD must opt out the same way or the engine will claim its arrows and its own key handling will never run.

  Such a trap **manages its own manual bit**, which is the corollary that is easy to miss. `popFocusMode` clears the bit only for engaging traps, so a ⌥⇥ pressed inside a typing-first surface would outlive it and leave a ring on the deck the user came back to. `TugModalInputDialog` captures `kbfManual()` when its trap goes active and restores it at teardown, standing down when `kbfClearedByPointer()` says the pointer already answered — restore rather than clear, because a user who turns their card's cycle *off* inside the surface is owed it back just as much.
- **A card declares `kbfAtRest` when its content IS its focus stops** — the Lens, Jots, Settings, Keyboard, Overview, DevTools. Do not declare it on a card whose resting state is a caret in a text surface, and do not declare it on a card that registers **no focus stops at all**: a mode pointing at no ring is worse than no mode. That empty-group check is what keeps the diff card and the About box off the list.
- **The engine is structure** ([L22]). Key view, cursor, scope stack, the KBF bit, and cycling-mode push/pop are the `FocusManager`'s; never mirror them in `useState`.
- **A chord-capture surface is a sanctioned trap.** Settings ▸ Keyboard's capture pushes a focus mode while it is armed, and that is not a nicety — it is the only way the surface can be told to record ⌘W rather than watch the card close. A surface whose whole job is to *observe* a chord must own every chord it can see, which means a trap plus a capture-phase `preventDefault`, and it must still leave `Escape` to the ladder (`onEscapeDismiss`) so the one gesture that cancels a capture is the one gesture everything else cancels with. Capture surfaces are the narrow exception to "do not swallow keys"; everything else that wants a chord declares a binding and lets the funnel resolve it ([menus.md](menus.md)).
- **A container's focus mark is the container's to draw.** If a host thinks a component's focus mark is wrong on its surface — too quiet against the host's own background, the wrong shape for the host's clipping — the fix belongs ON THE COMPONENT or on the shared token, never hand-rolled in the host's stylesheet against the component's internal focus attributes. A host that draws another component's focus marks owns a copy of the language, and the copy is what goes stale when the language moves.

  The Lens Layouts section is the worked example, in both directions. Its stylesheet used to declare `--tugx-focus-tint` on `TugRadioGroup`'s behalf, because the shared tint really was near-invisible over the Lens's band background — a correct diagnosis, fixed in the wrong place. The override then sat at a strength nobody else could see, and when the language moved to the container wash it was the one surface that had to be found and unpicked by hand; it had also drifted well past what the wash eventually landed on, so the section had been quietly reading as a *filled* surface rather than a focused one. The right move was always to fix the shared token, which is what happened — and every group, including that one, got the benefit. Note the related but distinct rule this sits beside: [L20] says a component must not reference another component's tokens; this says a *host* must not draw a component's marks at all. Both were in play here.

Reference implementations: `TugConfirmPopover` and `TugAlert` (dialog button rows), the session-card pickers and `gallery-sheet` bodies (field + buttons), `TugListView` (item-group + cursor).
