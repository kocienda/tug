# Engine time in the motion: the set-up's forced layouts, the frame after the commit, the height crossing, and the deck that doubles in a day

**Purpose:** Five stages moved the stream's script off the main thread, and on the user's deck a new session card (⌘N) still freezes for a quarter to half a second before it moves. The 2026-10-12 evening readings say where that time goes, and it is not where the first draft of this brief put it: the largest share is style and layout that the deck's own script forces during the set-up, one whole-document layout per geometry read, on a document that has doubled since the morning's relaunch. The engine's own frame after the commit is real and second. This brief names the costs with their readers, decides how they are read per frame, reopens the height crossing with the new shape the doctrine requires, and takes the parked population that the ceiling never covered.

Stage 6 of `briefs/main-thread-headroom-program-brief.md`. Supersedes the 2026-10-12 morning draft (`1b537667a`), whose readings and framing are kept below as the before.

## Decisions {#decisions}

**[B01] ⌘N is the first gesture of record, and the set of record is four.** A new session card appearing (`show-card session`, which the `appear` drive is), fold, slot and split, read on the user's deck. The picker-to-body handoff that follows ⌘N is the second half of the same gesture and is read with it; `briefs/session-body-first-frame-brief.md` already owns its decisions and this stage takes its reading on the user's deck. The arc's first reading is the before table above, re-taken on the arc's build.

**[B02] Every frame is priced, and every forced layout is named.** `tugtool deck motion settle` gains a `--frame-phases` arm: a 1 ms native sample of the WebContent main thread across one drive, filed by frame boundary from the gap sampler's timestamps and by phase, with style, layout and compositing split into the engine's own rendering update and forced from script, the forcing API and its JavaScript caller named. The method is the one used here: a call-graph walk that assigns each sample to the topmost phase frame on its path and flags a `MicrotaskQueue`, `JSEventListener` or `JSRequestAnimationFrameCallback` ancestor. The chain census records source positions the reader can resolve: either the app serves the bundle's source map on the loopback port the eval door already gates, or the verb records function names from the stack as well as positions. A reading whose sites cannot be mapped is not a reading of record. The deck census the verb prints is taken from a count that forces no style (`__tugMotion.layers()` or the element count alone) unless `--full-census` is asked for; that is the honesty brief's rule, applied here because this stage reads the user's deck repeatedly.

*Resolved as built (2026-10-13).* The arm records with Instruments' Time Profiler (`xctrace`), whose samples carry their own times; `/usr/bin/sample`'s do not. Its probe found WebCore, WebKit and JavaScriptCore frames named and every JIT'd JavaScript frame a bare address, so the trace alone names the forcing API but never a JavaScript caller. The caller therefore comes from the chain probe: under `--frame-phases` the read drives' chain probe carries stacks, and a forced sample that falls inside a chain's paying read is named by that chain's getter and site (`in <fn>: …`, the frame itself when it is named); a forced sample outside every chain names its API and no caller. The page reports the drive's wall-clock instant with its clock's drift from `Date.now()`, because a page's monotonic clock stops across a sleep and an aged deck has slept. The first live read found the paying reads in anonymous effect callbacks named by the nearest named frame, which is React's minified `On`/`Mc` in the vendor chunk; those sites are identified by their bundle position until the reader is converted, and are not a defect in the probe.

**[B03] The set-up reads geometry once.** From the store commit to the first beat's launch, the deck's script forces at most one layout, and the frame-phase reading proves it. The readers in [F02] move or batch: the list view's render-time `scrollTop` and `clientHeight` (`tug-list-view.tsx:2935-2937`) read a value the held `ResizeObserver` and scroll listener already keep, not the live DOM; layout-effect reads of `clientHeight` and `clientWidth` across the list views happen before the commit's writes or from one shared read after them, not interleaved per component; `_revealArrival`'s read, the focus ring's `place`, `scrollToElement` and `applyRestoreTarget` read from the same flushed layout the Last pass takes, in a read phase that precedes every write. The settle's own Last pass is that one layout. The bar is the chain census on ⌘N and fold: at most one chain in the set-up, and the set-up gap no larger than that one layout plus the engine's frame of [B04]. This is where the user's quarter-second goes and it is the first thing built.

*Resolved as built (2026-10-13).* The Last pass reads first and writes after: one read phase takes every carried frame's rect and content box, every bottom-anchored scroller's distance and every list view's measure, and the planning and apply phases act on that record. Four cases the plan did not picture were settled by the decision's purpose. A settled hold is not always written "where no hold stood": `arm` holds a growing frame at its First height, so a settle that raises that hold moves the interior; those frames are measured again in the apply phase, together, after every hold is written, which costs one layout for all of them rather than one per frame. The readers that run outside the Last pass wait on a set-up span (from `arm` to the Last pass's apply phase, `lib/set-up-apply.ts`) rather than on `gestureScope.isMotionHeld()`, because the motion gate closes at the end of the Last pass and is open for the whole set-up. The list view's render reads SmartScroll's `keptScrollTop` (the top its last `scroll` event delivered or its own last write left, which a pin knows exactly) rather than `lastScrollEventTop` gated on `isScrollBaselineFresh`: the first harness reading found that gate stale after a write the browser answered with no `scroll` event, so every later render read the DOM and the list view's commit bracket paid a chain behind it. `_revealArrival`'s responder sync is left where it is, because neither harness reading named it. The bar holds on the slice arm: no chain in the set-up on `appear`, and one on fold and unfold, the read phase's own (`briefs/engine-time-in-the-motion-readings.md`).

**[B04] The engine's frame after the commit is attacked as engine work.** Candidates, in the order `--frame-phases` ranks them: the number of panes whose style the commit dirties (a frame whose arrangement did not change should not be restyled; pane frames the imposer moves by custom property versus by attribute); the population the style, layout and walk cover ([B06] removes the parked half); and the layer commit's size (a pane whose backing did not change should not re-upload). Each candidate is probed on the user's deck and the one whose removal moves the frame is the one built.

*Resolved as built (2026-10-13).* Probed on the harness rather than the user's deck, which runs no arc code. The first frame after a fold's commit was a forced style resolve of the whole deck, not the engine's own frame. The column seams, offset and strip were inherited custom properties written on the canvas and every layer, so a fold invalidated every descendant's style. Skipping unchanged writes moved nothing; freezing the arrangement halved the frame. So a column's properties are written on that slot's readers alone (`components/chrome/place-properties.ts`, the [D204] shape), and the frame fell from 107–116 ms to 77–83 ms. A frame new to a slot adopts only the values it is missing, because a seam's fallback is the equal division. The layer commit's share was 0–2 samples and was not probed. The flow strip's length is the named remainder for the arrival.

**[B05] The height crossing is reopened with a new shape.** This is the user's call and the doctrine's condition, and the readings make the case: with script off the stream it is the largest judder inside the motion, and on ⌘N the `room` beat is the same cost on every survivor. The shape is not a third bench of translation. Two candidates are read first:

- **Clip, not height.** The frame keeps its final box from the commit; the crossing animates a `clip-path: inset()` on the frame (compositor-accelerated on this WebKit if authored as a single `inset()` with keyword easing, to be verified by a bench against engine fact 2), and the neighbor below it translates to meet the clip edge. Layout runs once at the commit, no layout runs per frame, and the land hands back nothing because the box is already final. The still-crossing hold's job, keeping the interior at one definite size, is done by the commit rather than by a hold.
- **Two frames, one box.** The frame's box crosses as today, but the main-thread term is paid on a one-element frame layer whose only child is the clipped card root with `contain: strict`, so the per-frame layout is one box and the compositing walk is bounded by the frame's overlap scope rather than the document's.

Each is benched on the whale arm and the user's deck with the gap rows and `--frame-phases`, against the land as well as the motion, since the land is where translation lost. The one that holds the one-period bar inside the motion with a one-frame land is built; if neither does, the reading says why and the ruling stands with the new numbers written beside it.

*Resolved as built (2026-10-13).* Neither shape holds, so the ruling stands with the numbers beside it in `tuglaws/animation-doctrine.md` [D9]. A `clip-path: inset()` is not composited on this WebKit: a clip tween on a standing pane costs style and compositing every frame, where a transform costs none. The pane is `overflow: clip`, so the clip could not take a shrink's final box at the commit, and the box was held at the larger height instead. It removed the frame's per-frame layout, but the motion did not move and the land got worse. `contain: strict` on the held root moved nothing. The motion's frames are style and compositing, which every shape pays. Read on the harness's slice arm; the whale arm and the user's deck are owed. `at0736-height-crossing-bench.test.ts` keeps the bench and fails if the clip's premise stops holding.

**[B06] A parked pane leaves the document's style, layout and walk.** The parked half of the deck ([F04]) is not drawn and is still priced on every forced layout and every rendering update. A parked frame's content is held out of rendering, by `content-visibility: hidden` on the frame when the bench shows WebKit skips style and layout under it, or by unmounting the content to a sized placeholder that keeps the card's state and restores on reveal, which is the list view's own windowing applied one level up. The Overview's parked twin is the first case and the largest. The reveal is a set-up-and-go beat: the content is mounted before the first frame or behind the arrival's reveal gate, never mid-motion. `briefs/population-ceiling-cold-paths-brief.md` keeps the Overview's in-card window and the transcript's cold paths; this stage takes the parked frames, and the two arcs name each other.

*Resolved as built (2026-10-13).* The bench showed `content-visibility: hidden` does not skip layout on this engine, so the content of a parked workspace's panes is `display: none` while their frames keep their boxes ([D212]). The React tree stays mounted, so the reveal rebuilds boxes, not components. `CardHost` captures each scroller's offset at the hide and restores it when the box returns. A parked rail keeps `content-visibility: hidden` alone, because its content's share read at the instrument's floor. The Overview's parked twin is covered by the same rule as every parked pane.

**[B07] The standing taxes are read, then ruled.** Three readings on the user's deck with eight sessions working: the per-tick cost of the progress animations (a 1 ms sample at rest with the dots running and with them stilled by `deck motion demote`); the native caret's forced layout, which the composer does not need if CodeMirror draws its own cursor and the native caret is transparent; and the main-thread GC against a 2.9 GB process. Each becomes a decision in this brief once read: the dots keep their motion and lose their per-element timelines if the tick is theirs; the native caret goes if its animator is forcing layout; the heap is read for what holds it. A deck that is not at rest with nothing moving is the condition every other reading here is taken under, and the user's deck is in that condition all day.

*Resolved as built (2026-10-13).* All three were ruled with no build. Demoting every loop left the busy time where it was, so the dots keep their timelines. The native caret is already transparent, and its animator still forces a layout while the composer is focused, about 9 ms/s. No supported lever exists on this WebKit, so it is recorded. The GC is 0–1 % of busy time, under the tenth that would open a census. The largest cost at rest is the streaming frames' own layout, paid by its first reader, and the ruling is no build.

**[B08] The bar is the asks' bar, read honestly.** No gap over one display period from the first frame to the land, and a one-frame land, read on the user's deck fresh and aged, quiet and with three turns in flight, with the honesty rules of `briefs/motion-record-honesty-brief.md` in force: unperturbed drives for the bar, instrumented drives for attribution, the two-beat gap row so the set-up's cost is reported under the lead. The lead stays a budget, and its size is recorded beside the bar so the pause before a card moves is a number the user can rule on; today that number is 141–416 ms and the user has ruled on it.

**[B09] Every change lands with the before-and-after on the user's deck.** As the program brief's [B03] and [B04] require, with the aged deck as the deck of record: a reading on a freshly relaunched deck is the before only when the aged one is beside it.

*Resolved as built (2026-10-13).* The before was taken on the user's aged deck. Every after was taken on the harness, because the user's deck runs a Release build that predates the arc. The aged after on arc code is owed until the join and a relaunch (`briefs/engine-time-in-the-motion-readings.md`, the deck of record).

## Open Questions {#open-questions}

- **Does `content-visibility: hidden` take a parked frame out of style and layout on this WebKit, or only out of paint?** Settled by a bench: a parked twin under each shape, a forced layout timed before and after.
- **Is `clip-path: inset()` animation accelerated on this WebKit?** Settled by a bench under the falsification method: a bare `inset()` tween on a standing pane layer, read with `deck motion rest` and the forcing probe.
- **Which readers can share one layout, and which need the post-write value?** The frame-phase reading with callers named answers it; a reader that needs the post-write box reads it once, from the Last pass's layout.
- **Does the lead read as a delay to the user once it is one layout plus the engine's frame?** The user's reading; recorded beside the bar.

## Non-goals {#non-goals}

- **A third bench of height by translation.** Ruled; [F07].
